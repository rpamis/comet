# Outcome

为 Comet 增加两个彼此独立、但可以消费同一批有来源观察的能力：

1. **自进化个人记忆**：在用户正常使用 Comet 时，沉淀稳定的个人偏好、项目事实、常用操作和工作习惯。
2. **项目规则（Project Rules）**：自动发现或接受用户显式添加的团队规则，并把它们沉淀到可选的 Markdown 规则文件、现有 Agent 指令、linter、测试、构建或 CI 中。

两个能力都属于 Comet 自身，并分别作为可独立安装、启用、停用和卸载的第一方插件接入公开的 Comet 插件机制；它们与 `comet-any` 无关，也不共享它的节点、Skill Creator 或 Runtime 架构。

本次 Shape 不建立 `.comet/rules` 机器规则数据库，但支持用户手动创建 `.comet/rules/*.md` 作为可选、用户可读的项目规则来源。用户看到的能力统一称为“项目规则”；内部用于发现、选择、投递和验证规则的执行机制称为 Project Rules Harness。Comet 是学习、归纳和提出改动的层，不要求团队维护逐条规则记录。

当前 change 作为 Supervisor Change 管理整体目标，下面拆分插件运行机制、自进化个人记忆、项目规则和 Dashboard 四个可独立实现、独立验证的 child change。父级负责共同边界、依赖顺序、最终集成和整体验收，不直接承担实现。

# Scope

## 插件接入

- 自进化个人记忆与项目规则是两个彼此独立的第一方 Comet 插件，随 Comet 默认安装并启用，但可以单独停用或卸载，不作为 Comet Core 中不可移除的内置行为。
- Comet 提供稳定、公开的插件机制；第一方和第三方插件使用相同的安装、生命周期与能力接口，两个第一方插件不得依赖只有内置代码才能访问的私有入口。
- 用户可以单独安装、启用、停用或卸载任一插件；一个插件不存在或运行失败时，另一个插件和 Comet 基础 workflow 仍可正常使用。
- 停用插件立即停止该插件的新观察、上下文提供和自动处理，但不自动删除已有个人记忆或仓库规则；永久删除数据必须由用户明确执行。
- 两个插件可以消费 Comet 提供的同一批有来源生命周期事件，但各自拥有领域逻辑、存储、配置和失败边界，不能直接读写对方的内部状态。
- Comet Dashboard 的主侧边栏为两个已安装插件分别提供“个人记忆”和“项目规则”入口；每个入口打开自己的中心页面，不挂在 Classic、Native 或某个 change 下面。
- 个人记忆中心页管理当前用户的全局画像、当前项目记忆、学习与使用状态和 Git 同步；项目规则中心页管理当前项目的初始化、规则来源、验证入口和候选。两页都调用与 Skill、CLI 相同的领域能力，不保存 Dashboard 专属副本。
- 已安装但停用的插件保留侧边栏入口并显示停用状态，用户可以从中心页重新启用；卸载后移除入口但保留数据。单个插件页面加载失败不能影响另一个页面或现有工作流页面。
- 现有 Classic 与 Native 工作流页面继续保持只读；两个插件中心页只开放各自规格已经定义的管理操作，删除和永久清理仍需用户明确确认。

## Supervisor Change 拆分

- `comet-plugin-runtime` 负责公开插件机制、安装与生命周期、能力接入、兼容性和失败隔离。
- `self-evolving-personal-memory` 负责个人画像、按需记忆、自动学习、检索、作用域、隐私与非 Dashboard 管理能力。
- `self-evolving-project-rules` 负责项目规则发现、手动规则文件、显式添加、原生检查接入、规则生效与非 Dashboard 管理能力。
- `memory-rules-dashboard` 负责 Dashboard 主侧边栏中的两个独立入口、个人记忆中心页、项目规则中心页以及页面级失败隔离。
- `self-evolving-personal-memory` 和 `self-evolving-project-rules` 都依赖 `comet-plugin-runtime`；插件机制完成后，两个领域 child 可以并行推进，彼此不形成依赖。
- `memory-rules-dashboard` 同时依赖 `self-evolving-personal-memory` 和 `self-evolving-project-rules`；只有两个领域 child 都完成验证并合入 Supervisor 分支后，Dashboard child 才能创建工作区并开始实现。
- 两个领域 child 可以消费同一批带来源的轻量观察，但必须各自判断、各自存储、各自检索和各自生效；它们只提供 Dashboard 所需的公开领域能力，不提前承担页面实现与验收。
- 父级在四个 child 合入后验证完整目标、跨能力隔离和 Dashboard 集成，不把共享输入误写成共享数据模型或相互依赖。

## 自进化个人记忆

- 自动学习默认开启；用户明确说“记住”时立即生效。
- 普通执行只记录轻量事件，在成功 phase 转换、显式 checkpoint、任务完成和 Archive 等稳定检查点进行非阻塞后台复盘，不在每轮重复提取。
- 长期使用中，后台复盘自动合并重复记忆、压缩重复来源并整理已取代内容，避免详细记录随 change 数量线性增长；整理不得改变当前生效偏好，也不得让已移除内容重新生效。
- 推断偏好第一次只形成内部候选；至少两个独立且成功的 Comet change 提供一致、无冲突证据后才自动生效。
- 达到稳定条件后，自动学习自行新增、更新或替换记忆，不要求用户逐条确认；用户可以随时查看、纠正、移除或回滚。
- 后续稳定行为可以自动取代过去推断或显式保存的偏好；一次性要求、单个 change 和失败行为不能触发替换。
- 个人偏好不设置统一的时间期限，持续生效到用户纠正、移除或新的稳定行为取代。
- 独立观察使用“项目身份 + workflow 家族 + change ID”去重；Native、Classic、Hotfix 和 Tweak 都以 change 为单位，恢复会话和 profile 升级不增加计数。
- 失败或取消的 change 只能提供候选、冲突或负向信号；恢复成功后只升级同一 change 的证据状态。
- 个人偏好和通用习惯默认跨项目共享；项目事实、构建命令和路径相关习惯默认只在所属项目生效。
- 项目事实不按统一时间自动过期；使用前能够通过当前仓库核对时先核对，发现明确冲突就停止采用旧记忆并提示用户。
- 同一 Git 仓库的 worktree、目录移动和同一远端的重新克隆默认共享项目记忆；fork 和不同仓库默认隔离。
- 用户可以手动拆分误共享的项目记忆，或合并本应属于同一项目的记忆。
- 同一系统用户的个人记忆在所有 Comet 宿主间统一共享，不区分 Codex、Claude Code、Cursor 等宿主作用域。
- 多个 Comet 宿主或进程可以同时使用同一份个人记忆；并发写入必须完整保留不同内容、合并等价内容，并避免文件损坏、更新丢失和重复记忆。
- 用户手动编辑或移除个人画像内容时，该操作高于并发自动学习；相互冲突的自动更新不得静默覆盖当前画像，只作为后续稳定观察继续判断。
- 个人记忆必须跨会话、跨宿主和跨设备连续可用；记忆插件通过 Git 同步记忆文件，同一用户在另一台设备检出同一记忆仓库后可以继续使用个人偏好和项目记忆。
- 后台复盘可以临时分析当前任务内已授权的消息、工具操作、diff、测试和 Review，但长期只保存最小化结论与来源引用。
- 凭据、密钥、隐藏推理、完整对话、原始 diff 和完整命令输出不得进入长期记忆。
- 记忆只能影响当前请求已经授权的操作方式，不能成为提交、推送、删除、发布、外部消息或其他有外部影响操作的长期授权。

## 个人记忆检索与管理

- 使用“小型个人画像 + 按需记忆”的两层结构，不把全部记忆注入每个任务。
- 个人画像只包含少量普遍适用的当前偏好；项目事实、常用操作和详细来源按项目、路径、任务类型和操作检索。
- 专用私有记忆仓库默认检出到 `~/.comet/memory/`：`profile.md` 保存跨项目个人偏好，`projects/<project-key>.md` 保存对应项目的事实、命令、路径和常用操作。
- 个人画像和项目记忆都只有专用仓库中的一份可写来源；Comet 不再在项目内创建 `.comet/memory.md` 镜像，用户可以通过 Skill 或直接编辑专用仓库文件管理记忆。
- 同一仓库的其他 worktree、目录移动和同一远端的重新克隆仍通过用户级记忆识别项目，并在需要时恢复对应的项目记忆视图。
- 安装 Comet 或首次进入项目时不创建空记忆文件；第一次形成对应作用域的记忆时再创建，用户也可以提前手动创建并直接写入内容。
- 用户可读记忆文件只使用少量 Markdown 标题和列表，不要求 frontmatter、ID、状态或其他机器字段，也不展开详细历史、来源和索引。
- 用户直接修改对应文件视为该作用域内的显式纠正，下一次相关任务立即生效；CLI 和 Dashboard 使用同一份当前记忆，不得静默覆盖用户编辑。
- 用户直接新增列表项视为显式记忆；Comet 更新文件时尽量保留用户的文字、注释和顺序，不把文件重写成机器配置。
- 用户从对应文件中修改或移除内容时以用户编辑为准；移除的内容立即停止生效，过去的观察不能自动把它重新写回。
- 移除后产生的新观察仍可以按正常稳定条件重新学习该偏好，但不能复用移除前的旧观察凑足条件。
- 被修改或移除内容的详细历史暂时保留，用于查看和回滚；只有用户明确永久删除时才清除。
- 详细记忆、来源、检索索引和轻量学习事件由用户级 Comet Runtime 按需管理，不要求用户通过这两个 Markdown 文件维护内部数据。
- 不新增保存完整对话、工具调用或 diff 的记忆 trajectory；Native/Classic 已有 trajectory 继续只记录 workflow 机器状态，不能变成原始任务数据仓库。
- 自动整理保留当前记忆、必要来源摘要和可回滚历史；重复观察与过细来源可以合并压缩，具体阈值和保留量由 Design/Eval 确定。
- 自动整理失败不得影响当前任务或破坏原有记忆，下一个稳定检查点可以继续处理。
- MVP 使用结构化字段、规范化标签和关键词匹配，不依赖 embedding、向量数据库或模型自由相关性评分。
- 排序依次考虑显式/推断、项目/全局、结构化匹配精度、最近确认和稳定 memory ID。
- Comet 不猜测宿主上下文大小；常驻画像与按需结果分别使用固定的保守大小上限，具体数值通过 Design/Eval 确定。
- 学习、更新和普通加载默认安静；只有新记忆第一次实际改变 Agent 的做法，或记忆与当前要求冲突时，才简短提示记忆内容、作用域和原因，不要求用户处理。
- CLI 与 Dashboard 提供同一套查看、本轮使用情况、纠正、删除和回滚能力。
- 自动学习、检索和删除相互独立；整体关闭只暂停学习与检索并保留数据。
- 自动学习和记忆使用同时提供全局与按项目控制；用户可以只暂停某个项目的学习或使用，不影响其他项目。
- 暂停不会删除已有数据，恢复后继续使用原有记忆，不要求重新学习。

## 项目规则来源

- 项目规则属于仓库，不属于任何 Comet change；读取、选择、执行和手动维护规则都不要求先创建、切换或恢复 change。
- 用户可以手动创建 `.comet/rules/*.md`；每个文件可以包含多条自然语言规则，使用普通 Markdown，不要求 frontmatter、规则 ID、状态或其他机器字段。
- 每条规则可以在普通 Markdown 段落中写一行可选的 `适用范围：...`，例如 `适用范围：server/**`；省略时由 Comet 根据文件主题、标题、任务和实际访问路径推断。
- `.comet/rules/*.md` 是可选的用户可读来源，不是一条规则一个文件的数据库，也不是使用 Comet 的前置条件。
- 团队也可以继续只维护熟悉的 Agent 指令和原生检查配置，不需要学习 Comet 专用规则 schema。
- 需要 Agent 判断的指导优先进入已有 `AGENTS.md`、宿主指令文件或路径级指令文件。
- 能够确定性检查的要求优先进入项目技术栈已有的 compiler、formatter、linter、静态分析、schema、测试、构建插件、构建生命周期或 CI 配置；包括但不限于 Maven Plugin、Gradle Plugin 和各语言生态的检查插件。
- Comet 不按工具名或固定命令列表实现检查；它从项目 manifest、构建文件、脚本、文档和 CI 中发现当前项目实际采用的验证入口及其作用域。
- 没有合适载体时，Comet 提议创建技术栈原生配置、测试或主流 Agent 指令文件；只有用户选择规则文件时才创建或修改 `.comet/rules/*.md`。
- Comet 把 `.comet/rules/*.md`、现有 Agent 指令和原生检查配置作为同一仓库中的不同规则来源，不要求迁移，也不复制成多个宿主副本。
- 观察、候选、评估记录、索引和缓存保存在 `.comet/runtime/`，不成为团队日常维护界面。

## 项目规则初始化与自动发现

- 自动发现与非阻塞评估默认开启，用户可以关闭。
- 已启用 Comet 的项目在首次使用时自动执行一次有边界的基线盘点；后续在任务成功结束以及可获得 Review、检查或 CI 结果时增量复盘，不依赖某种 workflow 或 change 状态。
- 用户可以说“初始化项目规则”或运行 `comet rules init`，显式初始化当前项目并执行同一盘点；重复执行保持幂等，不创建 Comet change、规则文件、检查配置或依赖。
- 用户可以说“重新扫描项目规则”或运行 `comet rules scan` 重做盘点；可以说“查看项目规则状态”或运行只读的 `comet rules status` 查看启用状态、上次盘点、规则来源、验证入口和候选摘要。
- Skill 自然语言入口与 CLI 调用同一领域能力；CLI 和 Dashboard 都不是正常使用项目规则的前置条件。
- MVP 不常驻后台扫描，也不在每次工具调用或文件写入后分析。
- 基线盘点和增量复盘会识别用户创建或修改的 `.comet/rules/*.md`，不要求运行登记命令。
- 自动发现只在 Runtime 中创建或更新候选，不能直接修改仓库或启用阻塞检查。
- 仅从代码模式推断项目规则时，第一次独立成功观察只保留内部候选；第二次来自另一任务或仓库修订的一致、无冲突观察后，才形成一份非阻塞建议。
- 现有 Agent 指令、原生检查配置、已合并 Review 和用户显式添加不受重复观察限制；它们按各自已有来源直接识别或立即生成改动提案。
- 证据优先级为：明确团队决定和已采用仓库文件 → 实际检查配置与结果 → 已合并 Review → 多次独立任务或仓库修订中的稳定代码模式 → 版本匹配的行业基线。
- 低层来源不能通过数量或模型评分覆盖高层来源；冲突由 Comet 自动解决，不要求用户逐条处理：实际检查结果优先，明确范围优先于推断范围，更具体路径优先于宽泛规则，仍然相同则使用仓库中更新较新的团队决定。

## 用户显式添加项目规则

- 用户可以在任何 Comet workflow 中直接说“把这条加入项目规则”或表达同等明确意图。
- 显式添加不等待重复观察；Comet 立即判断合适载体并生成一份可读的普通仓库 diff。
- 能用现有工具确定性检查的内容，改动对应的项目插件、linter、测试、构建任务或 CI；需要 Agent 判断的内容，改动最相关的 Agent 指令文件。
- 用户明确指定目标文件或检查工具时，只要与仓库兼容，应优先遵循。
- 用户也可以直接创建或编辑 `.comet/rules/*.md`、已有 Agent 指令或检查配置；保存后立即成为当前工作区的项目规则，不要求通过专用命令登记。
- 这些文件都是普通仓库改动；是否提交、Review 和合并由团队现有 Git 流程决定，规则系统不创建或要求 Comet change。

## 规则生效与执行

- 自动候选本身只保存在 Runtime；用户要求加入后，Comet 才修改最合适的规则源或原生检查配置，形成普通仓库 diff。
- 稳定候选首先由当前 Comet Skill 在任务完成等稳定结束点发送一条简短、非阻塞通知；同一任务存在多个候选时合并为一条摘要，不连续逐条打断用户，也不要求用户打开 Dashboard 或运行 CLI。
- 用户可以直接在 Skill 对话中说“查看、加入、忽略、稍后”或表达同等意图；“加入”表示同意把候选写入合适的规则源或检查配置，不创建独立 change。
- “忽略”和“稍后”只出现在 Comet 于任务稳定结束点主动提出一条自动发现候选时：“忽略”处理这条尚未生效的候选，“稍后”保留候选供以后再次提示。它们不能停用已保存规则，也不能跳过 compiler、linter、测试、构建或 CI 失败。
- 用户要修改、停用或删除已经生效的规则时，直接编辑对应 Markdown、Agent 指令或原生检查配置；这与处理自动候选是两条独立路径。
- 候选详情和完整证据按需读取，不把待评审列表整体注入 Agent 上下文；Dashboard 和 CLI 只是可选的批量查看与管理入口。
- 未加入候选不得成为团队共享的阻塞要求，也不得静默改写 Agent 指令或检查配置。
- 工作区中的规则文件保存后立即供当前 Agent 使用；提交并合并后通过 Git 与团队共享。Comet 不维护另一份需要同步的生效副本。
- `.comet/rules/*.md` 与其他仓库规则文件地位相同；其中能够确定性检查的规则可以继续迁移到原生检查工具，避免只依赖 Agent 判断。
- 可确定检查的规则由原生工具报告和阻塞，沿用其严重级别、输出、例外和修复方式。
- 原生验证入口成功时，其中的 warning 保持工具定义的非阻塞语义；只有工具、构建或 CI 判定失败时才要求 Agent 修复并重跑。团队需要更严格时，应在原生插件或检查配置中把对应 warning 升级为失败。
- Comet 不维护覆盖项目工具的第二套严重级别，也不把所有 warning 擅自提升为阻塞错误。
- Agent 在完成相关代码改动后、声明完成前运行项目自己的相关验证入口；检查失败且由当前改动引起时，Agent 读取原生诊断、在当前授权范围内修复并重新运行，直到通过或确认存在无法自行解决的阻塞。
- 检查命令和调用方式由项目自身定义，例如 Maven 项目可能使用绑定插件的 `verify` 生命周期，其他技术栈可以使用完全不同的命令；Comet 不要求统一成专用命令。
- 非确定性指导通过同一个上下文路由按需选择：任务开始按请求与项目粗选，目标路径明确后补充路径相关规则，验证前补充与检查、发布或高风险操作相关的规则。
- 支持动态上下文的宿主由唯一 Comet Hook Router 及时投递；无 Hook 但支持宿主 Rule 的平台安装一条轻量项目级规则加载器，由 Agent 按任务和路径读取同一份 `.comet/rules`；Hook 和 Rule 都不可用时，Comet Skill 直接调用同一选择器。
- 规则加载器只包含如何选择和读取相关规则的短指令，不复制整套项目规则；不同投递方式共享同一规则源、上下文上限和原生检查流程。
- 动态 Hook 只对已经启用 Comet 的项目生效。仅在系统中全局安装 Comet Skill、但当前项目没有 `.comet/config.yaml` 时，Router 必须安静跳过，不注入上下文、不阻止操作、也不创建文件；用户仅手动创建 `.comet/rules/*.md` 而未初始化项目时，仍可在显式使用 Comet Skill 后读取规则，但不会获得项目 Hook 的自动注入。
- 同一会话不重复提供未变化的规则，选择结果使用固定保守上限；具体上限由 Design/Eval 用真实任务确定。
- 正常匹配、规则投递和检查通过默认保持安静；只有规则实际改变 Agent 的处理方式，或原生检查失败并触发修复时，才向用户简短说明。
- 修改、回滚和废弃通过普通仓库变更完成，历史由 Git 保留。

## 空白项目基线

- Comet 根据 manifest、lockfile 和框架配置识别技术栈与版本，并提出兼容的行业基线建议。
- 建议展示上游来源、适用版本、检测依据和不确定性。
- 基线可以非阻塞评估，但不得自动安装依赖、修改配置或启用阻塞检查。
- 用户选择加入时，生成技术栈原生配置、测试或 Agent 指令的普通仓库 diff，再按团队现有 Git 流程处理。

# Non-goals

- 不依赖或复用 `comet-any` 架构。
- 不为跨设备记忆引入 Comet 账户、登录或用户中心。
- 不建设 Comet 记忆中继或托管同步服务；跨设备同步复用 Git 和用户现有的 Git 凭据。
- 不把个人画像或项目个人记忆默认提交到用户正在开发的团队项目仓库。
- 不在开发项目内生成第二份可写的个人记忆镜像。
- 不为两个第一方插件保留绕过公开插件机制的私有加载、生命周期或数据访问路径。
- 不把 `.comet/rules/*.md` 设计成一条规则一个文件或要求团队维护机器字段的规则数据库。
- 不实现通用向量数据库或保存无边界任务数据的托管服务。
- 不把所有自然语言指导转换成 linter。
- 不在 Comet Core 中重写语言生态已有的 compiler、linter、测试或 policy engine。
- 不让一次普通行为、失败轨迹、代码频率或模型自评直接成为长期偏好或团队阻塞要求。
- 不自动覆盖用户维护的 Agent 指令、CI、linter 或测试配置。
- 不保存凭据、密钥、隐藏推理或无边界任务轨迹。
- 不合并 Native 与 Classic 的状态机、阶段或 Guard。

# Acceptance examples

- 用户可以通过 Comet 安装、启用、停用和卸载一个第三方插件；同一插件机制也管理个人记忆与项目规则两个第一方插件。
- 用户只停用个人记忆插件后，Comet workflow 和项目规则插件继续工作；停用项目规则插件也不会中断个人记忆或基础 workflow。
- 用户说“记住：只暂存本次改动文件”，个人记忆立即生效，并保留明确来源。
- Comet 只在一个 change 中观察到小范围暂存时只形成内部候选；第二个独立成功 change 再次出现一致行为后自动生效，第一次实际影响 Agent 做法时才简短提示。
- “偏好中文回复”可以进入小型个人画像；“项目 A 使用 `pnpm build`”只在项目 A 的相关任务中按需加载。
- 项目 A 的 `~/.comet/memory/projects/<project-key>.md` 可以显示“构建使用 `pnpm build`”；用户直接改为 `npm run build` 后，下一次项目 A 任务使用新命令，其他项目不受影响。
- 项目记忆文件只出现在专用私有记忆仓库的 Git diff 中，不进入项目 A 的普通 Git diff；需要团队共享的内容进入项目规则，而不是个人项目记忆。
- 一个没有形成任何可复用记忆的新项目不会出现空的项目记忆文件；用户手动创建对应 `projects/<project-key>.md` 并写入项目命令后，内容立即作为显式项目记忆生效。
- 当前要求与历史记忆冲突时，Agent 执行当前要求并提示被忽略的记忆。
- 用户关闭自动学习后仍可显式要求记住；关闭检索后记录继续保留但不进入 Agent 上下文。
- 用户只暂停项目 A 的自动学习后，项目 B 继续正常学习；项目 A 恢复后继续使用暂停前的数据。
- 用户直接编辑个人画像 Markdown 后，下一次相关任务使用纠正后的内容；文件中仍只保留当前画像，不展开详细历史和来源。
- 用户在个人画像的“沟通偏好”列表中手动加入“使用中文回复”，该偏好立即生效；Comet 后续更新不会删除用户注释或无故重排文件。
- 用户从个人画像中移除“偏好中文回复”后，该偏好立即停止生效，过去的任务观察不会自动把它加回来；用户仍可通过回滚恢复，或明确永久删除相关历史。
- 用户曾显式保存“偏好中文回复”，后续多个独立成功 change 持续表现出新的稳定偏好时，Comet 自动更新画像，不要求用户先确认。
- 项目 A 从 `pnpm` 改为 `npm` 后，当前仓库文件与旧构建记忆冲突，Comet 不再采用旧命令并提示该记忆已经不符合项目现状。
- 用户在同一仓库的新 worktree 中继续工作时可以使用已有项目记忆；切换到该仓库的 fork 时默认不加载原项目记忆。
- 用户在 Codex 中形成的个人偏好，在另一会话、另一宿主或另一台已连接设备上通过 Comet 工作时继续生效。
- 连续运行大量 change 并重复观察相同习惯后，个人画像和每轮注入量仍保持固定上限，详细记忆不产生重复项；当前偏好、必要来源和回滚能力仍然可用。
- Codex 与 Claude Code 同时写入两条不同记忆时两条都被保留；同时写入同一条记忆时只形成一条；用户并发手动移除偏好时，旧的后台观察不会把它写回来。
- 长期记忆不会生成保存完整对话、工具调用、原始 diff 或完整命令输出的新 trajectory 文件；专用仓库中的项目记忆文件也不会被写成任务流水账。
- 用户在设备 A 形成“偏好中文回复”后，记忆插件把记忆文件提交并同步到配置的 Git remote；设备 B 检出同一记忆仓库后，新 Comet 会话直接使用该偏好，不需要重新学习。
- 专用私有记忆仓库包含 `profile.md` 和 `projects/` 下的项目记忆；同步不会在用户正在开发的项目仓库中产生个人记忆提交。
- 用户只安装个人记忆插件时可以正常学习和检索记忆，但不会出现项目规则的自动发现、候选提示或上下文路由。
- 用户说“把『domains 层不得直接访问文件系统』加入项目规则”，仓库已有架构 linter 时，Comet 生成对该 linter 配置或测试的改动，而不是创建 `.comet/rules`。
- 用户说“数据库迁移必须同步更新回滚说明”，该要求需要 Agent 判断时，Comet 生成对最相关 Agent 指令文件的改动。
- 用户手动创建 `.comet/rules/database.md`，用普通标题和列表写入多条数据库规则；Comet 后续盘点直接识别，不要求 frontmatter 或登记命令。
- 用户直接修改 `AGENTS.md` 或 ESLint 配置后，Comet 后续盘点能够识别新的项目现状，不要求再次登记。
- Comet 第一次从成功任务中发现某个代码模式时只生成内部候选；另一独立任务或仓库修订再次出现一致模式后形成非阻塞建议，但不自动修改规则文件。
- 用户只通过 Comet Skill 工作时，稳定候选在任务结束点以简短消息出现；用户回复“加入”后，Comet 直接修改合适的规则来源或原生检查配置，不要求创建规则专用 change。
- 用户在没有 active change 的普通 Comet Skill 任务中手动创建规则，和在 Native、Classic、Hotfix 或 Tweak 中创建规则的结果相同；规则的读取与执行不依赖这些 workflow 状态。
- 已有 ESLint、Semgrep、测试或 CI 能执行某项要求时，Comet 复用原生能力，不复制自然语言规则和自定义执行协议。
- Maven 项目通过 Checkstyle、SpotBugs 或其他插件把规则接入构建生命周期后，Comet 发现项目实际验证命令；Agent 修改代码后运行该命令，按插件诊断修复并重跑，不要求 Maven 插件实现 Comet 接口。
- Maven 插件输出 warning 但验证命令成功时，Comet 不强制扩大当前改动；团队在 Maven 配置中把该问题设为构建失败后，Agent 才必须修复并重跑。
- 行业基线与当前明确团队决定冲突时，Comet 显示冲突，不自动修改配置。
- 没有 Hook 但支持宿主 Rule 的平台通过轻量规则加载器选择相关 Markdown 段落；Hook 和 Rule 都不可用时由 Comet Skill 完成同一动作。所有平台继续依靠仓库命令和 CI 执行可确定检查的规则，用户不需要打开 Dashboard 或手动运行 Comet CLI。
- 用户只安装项目规则插件时仍可发现、读取和执行仓库规则，不要求安装个人记忆插件；停用该插件后不再自动发现或提供规则，但仓库文件和原生检查保持原样。
- 同一条带来源观察同时与两个能力相关时，个人记忆和项目规则分别处理；个人偏好不会自动成为团队规则，项目规则也不会写入个人记忆。
- 用户说“记住：以后提交后都推送”时，Comet 可以记住操作偏好，但后续任务没有授权推送时仍不得执行推送。
- 用户打开 Comet Dashboard 时，主侧边栏同时显示“个人记忆”和“项目规则”两个独立入口；切换入口会分别打开对应中心页面，而不是切换到某个 workflow 或 change 的子页面。
- 个人记忆中心页可以查看和纠正当前画像、项目记忆与本轮使用情况，暂停学习或检索，查看 Git 同步状态以及执行删除和回滚；这些操作立即反映到同一份记忆数据和用户可读文件。
- 项目规则中心页可以初始化或重新扫描当前项目，查看规则来源、验证入口和候选，并执行加入、忽略或稍后；这些操作不创建 Comet change，也不产生 Dashboard 专属规则副本。
- 用户停用个人记忆插件后，其中心页显示停用状态并允许重新启用，项目规则页仍可使用；卸载个人记忆插件后入口消失但记忆数据保留。项目规则插件遵循相同生命周期语义。

# Constraints and invariants

- 中文是本 change 的正式文档语言；命令、路径和 schema ID 可以保留英文。
- `comet init` 按所选 Skill 语言初始化项目 `.comet/config.yaml` 的 `native.language`；配置存在后，它是新建 Native change 及其 brief、verification 和证据概览等核心 Markdown 产物的唯一默认语言，只有用户显式指定 `--language` 时才覆盖，已有 change 保留创建时的语言。
- 中文产物使用中文标题，英文产物使用英文标题；Runtime 同时兼容两种标题，机器字段、命令、路径、schema ID 和验收 ID 保持稳定英文。
- 个人记忆和项目规则只共享有来源的观察，不能混成同一个文件或权限面。
- 用户明确指令高于推断记忆；仓库已采用来源高于个人记忆和自动候选；确定性检查结果高于模型自评。
- 历史记忆和显式保存的偏好都不能扩大当前任务的授权范围。
- 自动整理不得改变记忆含义、跨越项目作用域、丢失当前生效内容，或复用已被用户移除的旧观察。
- 个人记忆存储必须支持同一用户在多个会话、宿主、进程和设备上的并发访问，不允许以“一个时间只能运行一个 Agent”作为使用前提。
- 跨设备身份不能依赖 Comet 账户；多个设备通过同一记忆 Git 仓库建立同一记忆空间，并继续使用用户已有的 Git 身份与凭据。
- 个人记忆的机器状态、索引、轻量学习事件和详细来源进入用户级 Comet Runtime；项目规则的观察、候选、索引和缓存进入项目 `.comet/runtime/`。两个用户可读记忆文件不承载这些内部数据。
- Comet Hook Router 仍是唯一安装的 Comet Hook 入口；它是规则投递的可选宿主适配，不能成为项目规则读取或执行的前置条件，也不得削弱 Native/Classic Guard。
- 对所有平台，仓库命令和 CI 是可移植的最终检查面；宿主能力只提供更早反馈。
- 具体平台指令发现必须核对 Comet 的完整平台 registry，不能硬编码少量宿主。
- 公开插件机制必须具有明确的兼容性边界；不兼容、缺失或启动失败的插件给出可理解诊断并被隔离，不能让 Comet 基础 workflow 无法启动。
- Supervisor Change 只持有拆分、集成和整体验收；领域 child 保持普通 Native change 的独立状态、工作区与验证结果，最终依赖关系在插件开放范围确认后更新。

# Decisions

- 个人记忆采用“小型个人画像 + 按需记忆 + 稳定检查点后台复盘”。
- 个人记忆使用一个专用私有 Git 仓库：`~/.comet/memory/profile.md` 保存跨项目当前偏好，`~/.comet/memory/projects/<project-key>.md` 保存各项目记忆；不再生成项目内镜像。
- 专用仓库文件是唯一可写来源。同仓库的 worktree、目录移动和同一远端的重新克隆继续共享项目记忆，团队内容仍由项目规则负责。
- 不新增保存完整对话、工具调用或 diff 的记忆 trajectory；现有 workflow trajectory 继续只承担 Native/Classic 运行状态记录。
- 个人画像中的用户编辑决定当前生效内容；移除偏好会阻止旧观察自动重新写回，相关历史保留到用户回滚或明确永久删除。
- 记忆不使用统一的时间期限：个人偏好保留到用户纠正、移除或新的稳定行为取代；项目事实使用时优先与当前仓库核对，冲突时停止采用。
- 项目记忆按项目而不是本地路径识别：同一仓库的 worktree、目录移动和同一远端的重新克隆默认共享，fork 与不同仓库默认隔离，并支持用户手动拆分或合并。
- 自动学习达到稳定条件后直接维护记忆，不设置逐条确认流程；稳定的新行为可以替换推断或显式保存的旧偏好，用户保留查看、纠正、移除和回滚能力。
- 自动学习采用低打扰通知：学习和更新过程保持安静，只在新记忆第一次实际影响 Agent 做法或与当前要求冲突时简短说明，不要求用户处理。
- 同一系统用户的个人记忆跨所有 Comet 宿主共享，不建立宿主专属偏好或操作习惯作用域。
- 两个用户可读记忆文件都采用少量 Markdown 标题和列表，不使用 frontmatter、ID、状态等机器字段；手动新增列表项立即生效，Comet 更新时尽量保留原文、注释和顺序。
- Native 的 brief、verification 和证据概览模板都根据 change 语言生成，不再让模板固定使用英文。
- 自动学习和记忆使用具有全局与按项目两级控制，两者可以分别暂停；暂停保留数据，恢复后继续使用原有记忆。
- 长期记忆在稳定检查点自动去重、合并和压缩，保持常驻画像、检索结果和详细记录可用，不让重复证据随 change 数量线性增长。
- 同一系统用户的多个 Comet 宿主可以安全并发读写个人记忆；不同更新均保留，等价更新自动合并，用户手动编辑优先于并发自动学习。
- 自进化个人记忆已按完整规格定稿；后续 Shape 澄清只处理项目规则和父级整体验收，不重新打开已确认的个人记忆决定。
- 用户可见名称采用“项目规则（Project Rules）”，CLI 使用 `comet rules`；内部架构称为 Project Rules Harness，不作为用户需要理解或操作的产品对象。
- 项目规则采用“可读规则源 + 上下文路由 + 原生检查 + Agent 自动修复循环”；规则属于仓库，与 Comet change 生命周期无关。
- 可确定检查的规则复用项目技术栈自身的插件、脚本、测试、构建任务和 CI，不新增 Comet 专用插件接口；不同项目可以使用不同命令，Comet 负责发现相关验证入口并让 Agent 在失败后修复、重跑。
- 检查严重级别和通过/失败结果以项目原生工具为准；成功命令中的 warning 不阻塞，Comet 不增加独立的严重级别覆盖层。
- `.comet/rules/*.md` 是可选的普通 Markdown 规则来源，一个文件可写多条规则；不要求用户维护 Comet 专用字段、ID 或执行协议。
- 用户可以用普通文字 `适用范围：...` 提高选择精度，但该说明不是必填字段；未填写时由上下文路由自动推断。
- 用户既可以依赖自动发现，也可以显式要求添加项目规则，手动创建规则文件，或直接修改现有仓库来源。
- 仅从代码模式推断时，需要两个独立且成功的任务或仓库修订提供一致、无冲突证据后才提出非阻塞建议；明确团队来源和用户显式添加不等待重复观察。
- 自动候选不修改仓库；用户明确要求加入后才生成普通 Git diff，是否 Review 和合并沿用团队现有流程。
- 稳定候选采用 Skill-first 交互：同一任务发现多个候选时，Comet Skill 在稳定结束点只发送一条合并摘要，用户可直接用自然语言全部加入、逐个查看、全部忽略或稍后处理；Dashboard/CLI 仅作为可选管理入口。
- 用户要求“加入”候选时，Comet 直接生成普通仓库改动；规则系统不创建、选择或组织 Comet change。
- 上下文路由在任务开始、目标路径明确和验证前渐进选择规则；投递优先使用动态 Hook，其次使用轻量宿主 Rule 加载器，最后由 Comet Skill 调用同一选择器。
- 宿主 Rule 只充当项目级加载入口，不承载项目规则副本；未启用 Comet 的项目不会安装或触发该加载器。
- 规则冲突不进入用户确认流程；Comet 按“实际检查 → 明确范围 → 更具体路径 → 更新较新的团队决定”自动选择，并只在 Runtime 中保留决策依据。
- 规则成功应用默认不逐条汇报；只有实际改变处理方式或检查失败时才提供必要说明。
- 用户忽略自动发现候选后，同一候选在证据和项目现状没有实质变化时不再提示；出现新的团队决定、规则来源、检查结果或不兼容代码模式后，可以重新评估并再次提出。普通重复观察不能解除忽略。
- 个人记忆、项目事实、可复用流程、Skill 和项目规则保持独立。
- 当前 change 保持 Supervisor Change；第一波实现 `comet-plugin-runtime`，第二波并行实现 `self-evolving-personal-memory` 和 `self-evolving-project-rules`，第三波在两者都完成并合入后实现 `memory-rules-dashboard`，最终由父级统一验证。
- 自进化个人记忆和项目规则改为两个可独立插拔的第一方 Comet 插件；插件不存在或停用时，不得在 Comet Core 中留下同等能力的隐式执行路径。
- Comet 插件机制对第三方开放并提供稳定接口；第一方插件使用同一接口，既作为正式功能，也作为插件作者可参考的实现。
- 两个第一方插件随 Comet 默认安装并启用，保持自动学习和自动发现的低打扰体验；可插拔表示用户能够独立停用或卸载，而不是要求用户首次使用前手工安装。
- 这两个插件首次随新版 Comet 发布时，已有用户升级后也自动安装并启用，确保新能力立即可用；用户之后明确停用或卸载任一插件时，后续 Comet 更新必须保留该选择，不得自动重新启用或安装。
- Dashboard 主侧边栏为两个已安装插件提供独立入口和中心页面；页面按插件生命周期显示、停用或移除，并通过公开插件能力复用与 Skill、CLI 相同的领域服务。
- 个人记忆中心页覆盖画像、项目记忆、本轮使用、学习/检索控制、Git 同步和回滚管理；项目规则中心页覆盖初始化、扫描、规则来源、验证入口和候选管理。Dashboard 不是两个能力正常运行的前置条件。
- 现有工作流页面继续只读；插件中心页可以执行已定义的插件管理操作，但不得把 Dashboard 变成第二份记忆或规则来源。
- Dashboard 是受 Supervisor 管理的独立后置 change，不属于两个领域 child；其 `depends_on` 同时指向个人记忆和项目规则，不能在任一领域能力尚未完成时提前启动。
- 自进化个人记忆必须跨会话和跨设备使用；本地 Markdown 是用户可读入口，不能被当作只在单台设备成立的唯一数据副本。
- Comet 不增加账户体系；跨设备同步通过设备身份和同步介质完成，而不是登录 Comet 账户。
- 跨设备记忆使用 Git 同步，不建设配对、中继或 Comet 托管服务；用户完成一次 remote 配置后，记忆插件在稳定检查点自动拉取、合并、提交和推送记忆仓库，不操作项目仓库的分支与 remote。
- 个人记忆采用本地优先体验：尚未配置 Git remote 时仍立即启用自动学习、检索和本地历史；首次形成本地记忆后只低打扰提示一次可配置 remote 获得跨设备同步，不阻塞当前或后续任务。用户稍后配置 remote 时同步已有本地记忆，不要求重新学习。

# Open questions

- Runtime schema、规则文件检索实现、平台载体映射、固定载荷上限和检查集成方式属于 Design/Eval，需要用当前仓库、完整平台 registry 和真实任务验证后决定。
- [blocking] CONFIRM: 是否确认以上两个默认启用且可独立卸载的第一方插件、本地优先并通过 Git 跨设备同步的个人记忆、按需投递并复用原生检查的项目规则、低打扰批量候选交互、后置 Dashboard change，以及四个 child 的 Supervisor 拆分，进入 Design？

# Verification expectations

- 使用真实 Comet 任务验证自动复盘不会打断用户，也不会为无稳定信号的任务创建记忆。
- 验证显式记忆、两次独立 change 推断、作用域隔离、冲突覆盖、固定载荷上限、删除与回滚。
- 通过长序列 change 验证重复观察会被合并压缩，常驻画像与注入上下文保持固定上限，当前偏好、必要来源和回滚能力不丢失。
- 通过多个宿主或进程并发读写验证不同更新全部保留、等价更新不会重复、用户手动编辑优先，并且没有文件损坏或丢失更新。
- 通过两个设备的新会话验证已同步记忆可以直接使用，并验证并发更新、离线恢复和用户手动编辑不会静默丢失。
- 验证记忆插件只操作配置的记忆 Git 仓库；remote 暂时不可用时保留本地提交并在后续稳定检查点重试，不阻塞当前开发任务，也不推送用户的项目仓库。
- 分别安装、停用和卸载两个插件，验证任一插件都能独立工作，停用不继续运行，卸载不破坏 Comet workflow 或擅自删除用户数据和仓库规则。
- 使用与第一方插件相同的公开接口加载一个最小第三方测试插件，验证安装、启用、调用、停用、卸载、版本不兼容和运行失败隔离。
- 验证自动候选不写仓库，用户显式添加生成可读 diff，用户手动创建的 Markdown 规则文件无需登记即可在当前工作区生效，并可通过普通 Git 流程与团队共享。
- 验证可确定检查的规则复用原生 linter/test/build/CI，需要 Agent 判断的规则会随任务与路径渐进选择且不全量注入；动态 Hook、轻量宿主 Rule 加载器和 Comet Skill fallback 都使用同一选择结果。
- 验证 `comet rules init`、`comet rules scan`、`comet rules status` 与 Skill 自然语言入口使用同一领域能力；初始化幂等且不自动创建规则文件、检查配置、依赖或 Comet change。
- 验证 Dashboard 主侧边栏分别展示“个人记忆”和“项目规则”，桌面与窄屏都能进入各自中心页；页面复用现有 Ant Design 导航、紧凑指标、分隔线和普通列表，并支持亮色与暗色主题。
- 验证两个中心页与 Skill、CLI、用户可读文件使用同一数据和领域服务；修改不会产生 Dashboard 专属副本，规则页操作不会创建 Comet change。
- 验证插件停用、重新启用、卸载和页面加载失败时的导航与隔离行为；一个插件页面异常不影响另一个插件或 Classic/Native 工作流页面。
- 验证无 Hook 但支持 Rule 的平台只安装轻量加载入口，不复制项目规则；Hook 和 Rule 都不可用时 Skill fallback 仍可完成同一主流程。
- 验证规则正常应用和检查通过时不产生逐条提示，只有规则实际改变处理方式或检查失败时才向用户显示必要信息。
- 验证被忽略候选不会因普通重复观察再次提示，只有证据或项目现状实质变化后才重新进入评估；忽略不会停用已保存规则或绕过原生检查。
- 验证现有规则来源、完整平台 registry、唯一 Hook Router、Native/Classic 分离和生成 Runtime 约束。
- 分别验证两个 child 的完整行为，再在父级集成分支验证共享观察输入不会造成个人记忆与项目规则之间的数据、权限或生效规则串扰。
- 修改 Runtime、安装/路由或生成资产时，运行相关最小测试、重新生成受影响 bundle，并在最终交付前进行与风险匹配的全量验证。
