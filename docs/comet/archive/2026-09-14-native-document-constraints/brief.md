# Outcome

补齐 Native 正式文档的完整性与路径约束：遗漏必需文档或放错位置时得到可操作的诊断，不能仅凭模型声称完成就进入 Build。

# Scope

强化现有 brief、完整目标 Spec 的检查，覆盖 Shape、Build、Verify、Archive 全流程、恢复上下文提示、Hook 错误路径及旧需求兼容。每类新增阻塞必须提供用户或 Agent 能实际完成的恢复路径。完整目标规格见 specs/native-document-constraints/spec.md。

# Non-goals

不新增强制技术设计或实施计划文档，不改变 Classic，不把任意同名 Markdown 当作 Native 产物。不用结构校验代替需求语义审查、独立验收或真实宿主 Hook 验证。不追溯修改已归档需求。

# Acceptance examples

- brief 缺失、缺少必需章节、章节为空或只含模板占位内容时，Shape 准备确认被阻止，并返回对应路径、章节及补齐方式；有效的中文和英文文档均可通过。
- brief 的非目标、决策或待解决问题确实为空时，可以用明确的无相关事项说明表达；真实阻塞问题仍阻止确认。
- 没有目标 Spec 且没有适用的明确豁免理由时不能确认 Shape；不改变产品行为的工作可以记录理由后豁免，能力删除继续使用正式删除声明。
- 已声明的 Spec 缺失、为空或仍为模板占位时不能完成 Shape；确认准备之后发生的文档变化不能沿用过期确认进入 Build。
- Hook 能明确归属于当前 change 的正式文档写入若指向错误位置，则拒绝并提示配置决定的正确路径；正确路径允许按现有正式产物规则编辑。
- 普通项目文档不会仅因名为 brief.md 或 spec.md 被拦截；缺少可归属写入事件时，Runtime 仍独立执行阶段文档检查。
- 自定义 artifact_root 下的检查和纠错路径与默认目录一致遵循项目配置，不硬编码 docs；多文件写入继续整体裁决。
- 升级前已确认并处于 Build、Verify 或待归档状态的需求保留进度，不仅因新文档规范被追溯阻塞；新建需求及旧需求重新确认 Shape 时必须满足新约束，已归档需求保持兼容。
- 完整合法的文档可经过用户确认正常进入 Build；状态、报告仍由 Runtime 管理，需求变化与候选失效继续遵循现有机制。

- Build 提交候选前检查适用新约束的正式文档；缺失、为空或位置错误时拒绝候选，但必须允许补写或返回正确阶段修复。
- Verify 接受通过结论前核对正式文档、已确认需求与候选的一致性；文档漂移不能沿用旧通过结论，语义遗漏仍由独立 Verifier 判断。
- Archive 核对文档、当前验收结论和待发布 Spec；缺失或过期的 verification.md 由 Runtime 从有效状态重建，修复后可重试归档。
- 恢复任务时明确当前阶段、正确文档路径、缺失项和可执行的下一动作。
- 每类新增阻塞必须通过“触发拒绝、按提示修复、重试成功”的回归验证，不要求手改 Runtime 状态或绕过 Hook。
- 恢复动作可以安全重试并保留已有工作，不能出现“先修复才允许返回修复阶段”的循环依赖。

# Constraints and invariants

保留 Native 独立状态机、用户确认、独立验收、证据绑定与工作区保护。结构校验只能判断可机械识别的完整性，不保证文字真实充分；Spec 豁免理由与是否确实不改变产品行为仍要经过 Shape 共识及后续验收。文档允许在 Shape 中逐步填写，不在每次合法写入时要求整份文档已完成。

# Decisions

- Q1=A：仅强化现有 brief 和 Spec，不新增强制技术设计或实施计划。
- Q2=A：要求 Spec 或明确适用的豁免理由；豁免面向不改变产品行为的工作，能力删除保留正式删除声明。
- Q3=A：明确归属的错误正式产物路径立即拦截并提示正确位置；普通 Markdown 不只按文件名拦截，由阶段检查兜底。
- Q4=A：新建及重新确认 Shape 时强制检查；旧需求已确认的进度保留，回到 Shape 后补齐；已归档需求保持兼容。
- 当前使用 docs 产物根目录、中文产物、batch 澄清及 current 工作区。用户明确授权手动将需求绑定到 042；已将 change_branch 与 target_branch 更新为字符串 042，并通过 Runtime doctor --repair 修复本机状态。
- 用户同意将约束扩展到 Shape、Build、Verify、Archive 及恢复提示。
- 用户要求新增约束不能造成用户或 Agent 无法解决的阻塞；每类拒绝都必须有经过验证的恢复出口。
- 文档检查、Hook 与兼容逻辑需要共享同一契约，按一个 Native change 实现，不拆分 Supervisor 子任务。
- 用户已确认上述四项选择和完整 Shape；当前按 Runtime 进入 Build，后续仍须独立 Verify 后才能归档。

# Open questions

无未解决的需求选择。全流程与恢复要求已获用户同意；仍需刷新完整 Shape 摘要，不能沿用原九项验收的旧确认。

# Verification expectations

逐类验证“阻塞 → 修复或返回正确阶段 → 重试推进”，覆盖重复执行、正式文档恢复、报告重建以及恢复动作不会被同一规则拒绝。外部权限或可信来源缺失时，必须准确指出所需用户动作或恢复来源，不能伪造成功。没有恢复出口的新规则不能交付为已完成。

先验证缺失、空章节、占位内容、中英文标题、无待决事项、Spec 与豁免、确认后漂移、错误及普通路径、自定义根目录、旧需求兼容。执行相关源码测试及生成 Runtime 的临时项目复现，检查受影响生成物。真实宿主 Hook、发布包及模型 Eval 的实际执行情况分别报告，未运行不宣称通过。先前 Vitest 缺少 pathe 的环境情况在 Build 重新核对。
