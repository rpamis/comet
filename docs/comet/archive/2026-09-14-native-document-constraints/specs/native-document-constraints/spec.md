# Native 正式文档约束

## 目标与适用范围

本能力负责 Native brief 和目标 Spec 的结构完整性、正式产物路径与阶段推进约束。它保留 Native 当前文档集合，不新增强制设计或实施计划文件。验收项集中记录在当前 change 的 brief，以下要求解释这些验收项的完整行为。

## Requirement: Brief 完整性

Runtime 在准备 Shape 确认及最终确认时必须读取当前 change 的 brief，检查八个既有章节：Outcome、Scope、Non-goals、Acceptance examples、Constraints and invariants、Decisions、Open questions、Verification expectations。兼容产品已有中文对应标题，不强制中文用户改用英文。

文件必须存在，章节必须有有效正文；空白、注释或单独的模板提示、占位内容不能算完成。无非目标、无额外决定、无待解决问题时，允许明确说明无相关事项，不能迫使用户编造内容。真实 blocking 问题仍阻止确认。任意正文里合法出现 TODO 等词语不能单凭关键词就否定整份文档。

Shape 内仍允许分次编辑尚未完成的文档。检查失败必须说明文件、章节、原因和恢复动作，不得进入 Build。

## Requirement: Spec 或明确豁免

改变产品行为的需求必须提供完整目标 Spec；不改变产品行为的工作允许在 brief 中保存明确且非占位的豁免理由，纳入用户 Shape 确认。未提供 Spec 且未明确记录适用理由时不能推进。Spec 已声明但缺失、为空或为占位内容时不能用一个泛泛理由忽略它。

删除 capability 沿用正式删除声明，不要求为被删除能力编写不存在的目标文件。不改变产品行为的判断仍需模型与用户审查，Runtime 不宣称能仅凭自然语言理由证明豁免适用。

## Requirement: 正式产物路径

正确路径由项目 artifact_root 与当前 change 决定：brief 位于 change 根目录，目标 Spec 位于 specs/<capability>/spec.md。状态与验证报告继续由 Runtime 管理。

Hook 对能明确归属于当前 change 的正式产物错误路径拒绝写入，并给出正确位置。归属需要明确的当前 change 路径或已有正式产物引用等证据；仅文件名相同、目录名含 docs 或内容看起来像需求文档不构成充分证据。不扫描并猜测整个仓库的 Markdown 用途。

普通项目文档继续遵守既有阶段规则；合法正式产物写入继续遵守正式需求变化和回 Shape 的现有机制。多目标动作整体裁决。无法归属的工具事件保持既有中立行为，不宣称已保护宿主没有上报的写入。

## Requirement: 阶段检查独立于 Hook

即使宿主没有触发 Hook，Runtime 的 Shape 文档检查仍然生效。准备确认之后文档改变，最终确认必须拒绝过期共识或按现有恢复机制要求重新准备确认，不沿用旧文档结果进入 Build。

## Requirement: 兼容已有需求

新建需求和任何重新确认 Shape 的需求适用新检查。升级前已经确认且仍在 Build、Verify 或待归档阶段的需求不因新增文档规范自动丢失进度，也不在保持原需求的后续推进中被追溯要求补齐。回到 Shape 后必须满足新约束再确认。已归档需求保持读取与恢复兼容，不批量改写历史文档。

## Requirement: 证据与边界

结构和路径检查不替代需求语义完整性、独立 Verifier 或用户确认。实现必须让 Skill 说明、错误提示与 Runtime 的有效约束一致；源码测试、生成 Runtime、打包产物及真实宿主证据分开记录。任何未执行的验证不算通过。

## Requirement: 全流程文档检查

新约束适用于当前需求后，必须贯穿其后续阶段，不能只在 Shape 检查一次。旧需求继续遵守上述兼容规则。

Build 提交候选前检查必需文档存在、完整且位置正确；不满足时拒绝候选，但允许合法补写或通过公开动作返回修复阶段。需求变化仍按既有机制回 Shape 重新确认。

Verify 接受通过结论前核对正式文档、已确认需求与候选的绑定关系。缺失或漂移时不能沿用旧通过结论，必须给出修复或重新确认动作。语义遗漏由独立 Verifier 判断。

Archive 执行前核对正式文档、当前验收结论与待发布 Spec 的一致性。verification.md 缺失或版本过期时，由 Runtime 从有效状态重建，不要求 Agent 手写报告，也不因单纯重建报告重跑仍有效的检查。

## Requirement: 每类新增阻塞必须可恢复

每类新增拒绝必须说明具体文件或状态、失败原因、正确路径或预期内容，以及当前可以执行的修复动作。需要返回 Shape 或 Build 时提供有效的公开 Runtime 动作，不要求手改状态文件、删除锁、伪造通过或绕过 Hook。

修复步骤不能依赖尚未满足的同一个文档检查。合法补写、正式文档恢复和必要的阶段恢复动作必须可执行；不得出现“先修复才允许返回修复阶段”的循环，也不能只推荐不存在、参数失效或仍被同一规则拒绝的命令。

恢复动作必须可安全重试，保留已有工作。可确定性重建的报告由 Runtime 修复，不能编造丢失的需求或跳过独立验收。需要用户提供可信来源、解决权限或选择归属时，明确具体所需输入与恢复后下一步；外部条件未满足时准确保持未完成。

每类新增阻塞都必须有“触发拒绝 → 按提示修复 → 重试推进成功”的回归验证。只验证拒绝发生不算完成；恢复路径不能执行时不得验收通过。

## Requirement: 恢复上下文提示

恢复任务时明确当前阶段、配置决定的正式文档路径、缺失或失效项及可执行的下一动作。无问题时正常继续，不重复询问已有决定。存在问题时保留当前需求和已有工作，不以新建同名 change 或重新开始整个流程作为常规修复办法。
