# Outcome

同一能力可在多个 change 中持续迭代。change 保存本次增量与验收轨迹，项目总 Spec 表达归档后的完整能力；新需求不会把历史已实现内容重新变成实施待办。

本 change 当前只进行 Shape 澄清，以下完整目标规格为待最终确认的草案。

# Scope

1. 将稳定 capability 身份与 change 名称分离，支持多对多演进关系。
2. 为 Native 增加显式版本化的增量规格语义，覆盖新增、修改、删除、重命名；稳定需求标识独立于 change 内的 A1…An。
3. 基于总 Spec 基线生成可检查的完整目标结果；归档预览、冲突处理、原子应用和中断恢复共同保证历史内容不被意外覆盖。
4. 区分本次实施范围、历史背景和受影响行为回归范围。
5. Native 与 Classic 复用现有项目知识召回，发现已有能力并建立准确关联；Classic 保留现有 OpenSpec delta 归档机制。
6. 有界检索、按需正文、索引新鲜度检查，以及旧 Native 格式的明确兼容策略。

实施顺序：先完成 Native 身份与增量模型，再接入基线对齐、验收与归档，最后补两种工作流的能力发现、性能和兼容验证。拆分检测结论：沿用单个 Native change，分阶段顺序实现。增量模型、完整目标生成、验收范围和关联确认共同依赖同一份规格契约，跨 Child 反复同步和集成的成本高于当前收益；不创建 Supervisor 或 Child。

# Non-goals

不重写 Classic 的 OpenSpec 合并器；不合并 Native/Classic 状态机或总 Spec 命名空间；不自动重写历史归档；不把历史 change 的全部需求重新导入本次待办；不新增 Dashboard 管理页面；不引入新的检索服务或全量历史扫描作为新建 change 的前置条件。

# Acceptance examples

正式验收场景统一位于 specs/spec-capability-evolution/spec.md；本节不重复生成验收项。核心例子：已有密码登录，新 change 增加短信登录，归档后的总 Spec 同时描述两种方式，本次实施只增加短信登录和必要的兼容调整。

# Constraints and invariants

- 沿用当前 0.4.1 分支与 D:/Project/Comet 目录，比较基线为 243e4aac4b8907ae39777c9adcbf606b2fbfa866。
- 当前 Native v4 会识别同名能力为 modify，但归档写入完整目标文本；不能把新增量文本直接交给旧路径覆盖总 Spec。
- 当前 Classic 通过 OpenSpec 执行 delta 归档；项目知识语料已覆盖 Native/Classic 总 Spec 与归档。
- 新格式必须可识别，旧格式保留原语义。首次修改旧能力时的标识建立必须可预览，不自动批量迁移历史记录。
- 关联建立之前核对真实 Spec 与路径；检索排名不等于授权修改或已实现的行为证据。
- 校验已确认范围中的真实行为；单元测试、生成 Runtime、浏览器和真实模型 Eval 的结论分别记录。
- 当前澄清使用现行 Native 要求的完整目标 Spec 描述待开发功能；不会提前使用尚未实现的 delta 格式管理本 change。

# Decisions

- 已由用户确定：使用 Comet Native 开启本需求澄清，沿用当前分支。
- 已由前序讨论确定：优先解决 Native 总能力累积；Classic 复用已有机制；两者都考虑能力发现与关联。
- 已由用户明确关注：性能，以及关联历史能力后不得重复实施历史需求。
- 方案待完整 Shape 确认：稳定 capability/需求标识、版本化增量、基线校验、可预览归档、实施与回归范围分离、复用现有召回、旧格式兼容。
- Q1 已确认 A：基线变化后，互不影响的增量自动重新合并并重新验证；修改同一需求、删除/重命名冲突、共享约束冲突或无法判断影响时暂停并说明冲突，不自动选一方覆盖。文本不重叠不能单独证明语义无冲突。
- Q2 已确认 A：未显式指定能力且只有一个高置信有效候选时，自动形成可见、可撤销的关联草案，纳入最终 Shape 确认；多个候选时询问。草案不修改总 Spec，也不代表实施授权。
- 新建 Native change 默认使用新版本增量协议；升级前活跃 change 保留旧整份目标规格语义，采用新协议必须显式转换并预览基线与稳定标识。
- 关联候选首屏最多 5 个，正文按需展开并复用既有上下文预算。显式指定能力走直接校验路径；无新输入或来源变化时复用当前关联，不重复召回。
- 召回没有足够置信度时不强行自动关联；用户可拒绝全部候选并明确创建新能力。检索失败不等于没有历史能力，降级不擅自切换项目配置的 Provider。
- 归档时自动对齐若改变已确认的用户目标或实施范围，回到 Shape；仅保留已确认范围且合并结果变化时重新验证，旧结果不得直接复用。
- 沿用当前目录中的单个 change，按上述依赖顺序实现；是否运行独立 Verifier 仍遵循 Native 正式验收协议。

# Verification expectations

用至少两个顺序 change 验证增量累积和旧能力保留；覆盖增删改名、无效目标、重复操作、并发基线变化、中断恢复、旧格式与历史读取。验证历史需求不会转化为新实施项。对 Native/Classic 的候选召回、陈旧索引、歧义与无索引降级进行集成验证；测量固定语料规模下的检索耗时、正文读取量和热路径重复 I/O，不把 Runtime 性能测试表述为模型端到端收益。
