# 目标

当用户直接提供文件、附件、链接或本地路径作为需求来源时，Native 必须以“源文档完整覆盖模式”维护 `brief.md` 和完整目标 Spec：`brief.md` 作为持久化澄清产物逐项记录来源、读取状态、分类和覆盖去向，完整目标 Spec 与验收条件共同覆盖全部当前有效的可执行语义，并通过澄清补齐遗漏边界后再进入 Build。

# 范围

- 修改中文 `comet-native` Skill、澄清参考和产物参考，定义直接文件/链接输入的完整覆盖流程。
- 在 Shape 阶段识别来源单元，按标题、段落、列表、表格、代码块、示例、约束、链接和边界建立覆盖表。
- 将 `brief.md` 明确定义为持久化澄清产物，在 `# Scope` 下保存唯一的来源覆盖映射，并在 `# Open questions` 保存歧义、遗漏和隐含边界；用户回答后同步到 Decisions、覆盖映射、Spec 和验收条件。
- 要求当前有效的可执行来源单元同时映射到完整目标 Spec 和至少一个验收 ID；背景、非目标和已废止内容只保留归类、理由或替代关系。
- 为每个来源记录 `complete`、`partial` 或 `unavailable` 读取状态；部分读取、不可访问和未完成双重映射的内容必须在 Shape 阶段阻塞。
- 先完成并确认中文资产，再同步英文 Skill、澄清参考、产物参考和双语言契约测试，保持两种语言的触发、分类、映射和阻塞语义一致。

# 非目标

- 不改变 Native Runtime schema、CLI 参数、状态机或验收结果格式。
- 不要求普通口述需求或没有直接外部来源的请求建立来源覆盖表。
- 不要求逐字复制与用户目标无关的排版元数据；但不得省略任何可执行要求、约束、示例语义或边界条件。

# 验收示例

- A1：用户提供文件、附件、URL 或本地路径作为需求来源时，Shape 自动进入源文档完整覆盖模式；仅供排错、取证、审查或实现参考的材料不自动触发。
- A2：`brief.md` 的 `# Scope` 包含唯一的来源覆盖映射，`# Open questions` 包含真实澄清问题；完整目标 Spec 不复制来源表，但完整覆盖全部当前有效的可执行语义。
- A3：每个当前有效的可执行来源单元都有完整目标 Spec 位置和至少一个验收 ID；背景、非目标和已废止内容只有归类、理由或替代关系，不制造无意义验收项。
- A4：每个来源记录读取状态；`partial`、`unavailable`、未完成双重映射或无法确认的边界保留 `[blocking]`，不进入 Build。
- A5：用户补充或修正来源后，Decisions、覆盖映射、完整目标 Spec 和验收条件同步更新；旧语义标为 `superseded` 并指向替代单元，当前 Spec 只表达最新确认语义。
- A6：只有来源覆盖完整、所有验收 ID 可追溯且共享理解确认完成后，Native 才允许推进 Build。
- A7：中英文 Skill、澄清参考、产物参考、双语言契约测试和独立 Agent 行为场景表达同一源文档完整覆盖流程。

# 约束与不变量

- 直接文件/链接是正式需求来源，不是仅供模型压缩的背景材料。
- 源文档完整覆盖模式以“来源单元 → 读取状态 → 分类 → Spec 章节/场景与验收 ID → 覆盖状态”作为最小可审计闭环。
- 分块读取只改变读取顺序和工作记忆管理，不改变最终覆盖集合；摘要不能替代覆盖映射。
- 验收条件至少覆盖原始来源的全部当前有效可执行语义，并可通过再次澄清补充更多用户可见边界。
- 不可访问、部分读取、无法解析、缺少双重映射或未确认的边界保持阻塞；Agent 不得凭空补全后继续。
- 只在用户确认后推进 Runtime 的 `--confirmed` 转换；进入 Build 后仍以完整 brief、Spec 和验收清单为准。

# 决策

- 将唯一覆盖映射写入 `brief.md`，由映射指向完整目标 Spec 和验收 ID；不在将来归档为 canonical 的 Spec 中重复来源路径和历史状态。
- 使用正向输出结构约束完整性：`brief.md` 的来源覆盖表、完整目标 Spec、验收映射、Open questions 和最终确认依次形成闭环。
- 用户修正原文时保留 `superseded` 来源单元和替代关系，当前目标 Spec 与验收条件只承载最新确认语义。
- 先完成中文版本并验证；用户确认中文结果后再同步英文，并通过同一双语言契约验证两种语言的语义一致性。
