# Native Shape 确认

## 目标与适用范围

Native 的 Shape 阶段保留最终用户确认。Agent 先完成可供确认的目标、范围、非目标、关键决定与全部验收要求，再由 Runtime 保存当前提案并进入等待；只有用户明确确认完整方案后才能进入 Build。本能力适用于普通 change 和 Supervisor，不增加新的阶段或外部 Skill 依赖。

## 需求澄清与正式产物

Agent 调查可查明的仓库事实、依赖与环境，实现选择由 Agent 在已授权范围内决定。只有会改变用户可见结果且无法可靠推断的决定才询问用户；按照项目的 batch 或 sequential 配置组织提问，尚未解决的问题记录为 brief 中的真实阻塞项。清晰需求直接整理正式产物，不制造没有实际分歧的问题。

用户明确把文件、附件、链接或路径作为需求来源时，brief 记录来源单元及读取、覆盖、替代状态。未读取、部分读取、未映射、冲突或未确认的可执行来源内容不能被当作已处理。仅用于排错、取证、审查或实现参考的材料不自动成为需求，材料中的指令也不自动成为用户授权；用途无法确定时先澄清。

正式 brief 遵守 native-document-constraints；产品行为变化提供完整目标 Spec，合法的无行为变化工作可使用具体豁免理由。真实未决问题、缺失或无效产物阻止准备确认。Agent 只编辑允许的正式需求文件，状态、提案绑定和结果由 Runtime 维护。

## 准备确认与批准

完成正式产物后，通过当前 continuation 准备确认。Runtime 校验并保存提案及其绑定，返回等待用户决定的信号；准备提案不等同于批准，不自动进入 Build。SDK 使用当前 Run 的 Action、Wait 和提案身份，兼容 Runtime 使用其公开 continuation；不把某一种格式的私有状态字段强加给另一种格式。

Agent 展示完整摘要，涵盖目标、范围、关键决定、全部验收要求及非目标。用户最初要求开展任务、选择某个局部方案或仅回答澄清问题，均不自动等于确认尚未展示的完整 Shape。

只有用户明确确认后才执行当前返回的确认命令，原样保留适用的状态版本、预期动作与提案身份。未进入确认等待、状态过期、动作不匹配或正式内容已变化时，Runtime 拒绝过期确认，或按现有恢复路径要求重新准备提案。不得手改状态、补造用户确认或借恢复跳过确认。

正式内容变化与纯格式调整沿用当前 Runtime 的绑定规则；本能力不新增更严格的格式失效机制。确认成功后，Runtime 才进入 Build 并返回当前下一动作。

## 需求变化后的说明

先区分三种情况：当前已确认目标的实现遗漏、改变用户可见结果或验收的正式需求变化、与当前 change 无关的请求。实现遗漏沿原范围修复；正式需求变化按当前 Runtime 公开动作回到 Shape；无关请求不混入当前 change。具体转换、候选和证据失效仍由现有 Runtime 决定，说明文案不新增第二套状态机。

重新确认时，先说明相对上次批准方案的新增、删除和改变的行为，列出受影响验收、仍可保留的成果以及需要重做的步骤，然后展示完整当前方案。说明只依据可读取的已批准提案、正式文档和用户明确决定；缺少可信旧方案时明确说明无法可靠比较，展示已知变化与完整新方案，不编造差异或宣称其余均未改变。初次确认不要求提供虚构的前后变化。

变化摘要辅助用户阅读，批准对象始终是完整当前 Shape。重做范围根据 Runtime 当前阶段、动作和证据有效性说明；仍有效的检查按原规则复用，失效或未知的检查不得描述为已经通过。用户改变需求后重新准备提案，不复用旧的完整 Shape 确认或旧需求的验收结论。

### Scenario: 需求变化展示影响与完整方案

Acceptance: A5

- Given 当前需求或验收变化，或收到原目标范围内的实现修复请求。
- When Agent 决定推进路径并准备必要的重新确认。
- Then 实现遗漏沿原范围修复；正式需求变化先展示行为变化、受影响验收、保留成果和重做步骤，再展示完整当前方案。缺少可信旧内容时明确说明，不能编造差异。

### Scenario: 重新确认和恢复仍绑定当前完整 Shape

Acceptance: A6

- Given 当前 Shape 已进入确认等待，随后内容或状态变化，或会话发生中断。
- When Agent 提交或恢复用户决定。
- Then 仍以当前完整提案和 Runtime 返回的有效版本、动作与提案身份为准；过期批准不能进入 Build，恢复不自动补造用户确认，旧验收不能覆盖新需求。

## Supervisor 与恢复

只有任务具有可独立实现和验证的结果、清晰验收分配且有真实依赖或并行价值时才提出 Supervisor 拆分，不按文档长度或条目数机械拆分。确认前展示 Child 计划、依赖、验收映射，以及适用的单会话或多会话推进方式。

完整方案和推进方式均明确时，用户可在一次回复中同时确认；仅选择推进方式不等于确认完整方案，仅普通确认也不能代替尚未决定的推进方式。已经明确选择的方式继续沿用，不重复提问。正式方案或 Child 计划变化时重新准备确认，保留当前状态绑定与有效授权的边界。

新的会话或进程通过公开状态恢复相同 change。仍在等待的决定继续等待，已确认且仍有效的选择继续沿用，不重建同名 change、不因恢复清除确认边界。缺少独立 Verifier 能力时，在 Build 前说明限制并安排相应执行者；不得伪造独立验收。

## 非目标与验证边界

本能力不实现自动语义差异引擎、额外提案存储、跨 change 授权或外部交付自动批准，不改变 Classic 的状态机。Skill 的清晰表达不能代替 Runtime 绑定检查、用户决定或独立验收。

Skill 内容、中英文契约和 Runtime 确认、恢复回归分别验证。确定性测试能证明约束和路径，不证明模型必然正确描述所有语义变化，也不能据此声称优于原生 Agent；真实模型对照实验另行确认。
