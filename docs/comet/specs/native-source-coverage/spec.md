# native-source-coverage

## 目标

Native 在用户直接提供文件、附件、链接或本地路径作为需求来源时，必须生成可追溯的完整需求闭环。原始来源的可执行语义进入完整目标 Spec 和验收条件；澄清只补充歧义、遗漏和隐含边界，不得用压缩摘要替代来源覆盖。

## 需求

### Requirement: 直接来源触发完整覆盖模式

当用户消息包含作为需求来源的文件、附件、URL、文档路径或其他明确外部来源时，Native MUST 在 Shape 识别该来源，并进入源文档完整覆盖模式。仅用于排错、取证、审查或实现参考的材料 MUST NOT 自动触发；用途无法可靠判断时 MUST 先澄清。分块、分页或分段读取 MAY 改变读取顺序，但 MUST 保持最终来源覆盖集合完整。

#### Scenario: 用户提供本地文件

- **WHEN** 用户直接提供一个文件或本地文档路径作为需求来源
- **THEN** Native 读取文件的全部可访问内容，并建立来源清单
- **AND** 将标题、段落、列表、表格、代码块、示例、约束和边界作为可追踪来源单元

#### Scenario: 用户提供链接

- **WHEN** 用户直接提供一个 URL 作为需求来源
- **THEN** Native 读取链接可访问的完整文档内容，并记录 URL 和可识别的章节/锚点
- **AND** 链接不可访问或内容不完整时保留 `[blocking]`，不得用推测内容替代

### Requirement: 来源覆盖映射

Shape 形成的 `brief.md` MUST 包含唯一的来源覆盖映射。每个来源单元 MUST 具有来源定位、读取状态、保留语义、覆盖状态，以及按分类适用的 Spec 位置、验收 ID、归类理由或替代关系。完整目标 Spec MUST 完整表达所有当前有效的可执行来源语义，但 MUST NOT 重复来源路径和历史状态表。

#### Scenario: 来源单元全部映射

- **WHEN** Shape 准备最终共享理解确认
- **THEN** 每个当前有效的可执行来源单元都能定位到完整目标 Spec 的章节或场景
- **AND** 每个可执行来源单元至少关联一个验收 ID
- **AND** 每个背景、非目标或已废止来源单元都有明确归类、理由或替代关系，并且不要求 Spec 位置或验收 ID

#### Scenario: 来源单元未映射

- **WHEN** 任一当前有效的可执行来源单元缺少 Spec 位置或验收 ID，或者其他来源单元缺少归类和理由
- **THEN** Native 将其作为 `[blocking]` 的覆盖缺口
- **AND** Native 不推进 Build

### Requirement: 澄清文件保留完整来源语义

`brief.md` MUST 作为持久化澄清产物：在 `# Scope` 下的 `## Source coverage` 先呈现已识别的完整来源需求和覆盖状态，再在 `# Open questions` 呈现按决策树整理的问题。问题 MUST 聚焦于真实歧义、遗漏或隐含边界；用户回答后 MUST 同步到 Decisions、来源覆盖映射、完整目标 Spec 和验收条件。

#### Scenario: 来源存在边界歧义

- **WHEN** 原始文件没有明确说明一个会改变用户可见结果的边界
- **THEN** Native 保留已经识别的原始要求，并提出带推荐和影响的澄清问题
- **AND** 该边界保持 `[blocking]`，直到用户明确回答或正式规则可靠确定

#### Scenario: 用户补充边界

- **WHEN** 用户补充或修正来源范围、例外或验收要求
- **THEN** Native 更新同一覆盖映射、Decisions、brief、完整目标 Spec 和验收 ID
- **AND** 被修正的旧单元标为 `superseded` 并指向替代单元，来源历史不被删除或隐藏
- **AND** 完整目标 Spec 和验收条件只表达最新确认的有效语义

### Requirement: 来源读取状态阻塞不完整覆盖

每个来源 MUST 记录 `complete`、`partial` 或 `unavailable` 读取状态。`partial` 或 `unavailable` MUST 保持 `[blocking]`；Agent MUST NOT 将已读取片段的映射误报为完整覆盖。

#### Scenario: 链接仅能部分读取

- **WHEN** URL 只能读取部分页面、附件或章节
- **THEN** 来源覆盖映射将读取状态记录为 `partial`
- **AND** 未读取范围保持 `[blocking]`，直到来源完整可用或用户明确提供缺失内容

### Requirement: 完整目标 Spec 与验收条件一致

完整目标 Spec MUST 描述来源在归档后应具有的完整行为，而不只是相对旧文本的变化。每个当前有效的可执行来源单元 MUST 同时进入完整目标 Spec 和至少一个验收 ID；背景、非目标和已废止来源只保留归类、理由或替代关系。验收条件 MUST 至少覆盖原始来源的全部当前有效可执行语义，并可以增加由澄清得到的边界条件。只有来源读取完整、分类完整、双重映射完整且共享理解确认完成后，Native 才能推进 Build。

#### Scenario: 可执行来源进入验收

- **WHEN** 原始来源包含功能、约束、示例行为或失败边界
- **THEN** 完整目标 Spec 为其写出完整行为、场景和结果
- **AND** 验收条件为其提供至少一个可观察的验收 ID

#### Scenario: 只有摘要没有覆盖表

- **WHEN** Agent 只能提供来源摘要，但不能说明原始内容单元的完整去向
- **THEN** Native 保持 Shape 阻塞
- **AND** Native 不把摘要当作完整 Spec 或验收条件

### Requirement: 中文先行并保持双语言一致

本轮 MUST 先更新中文 `comet-native` Skill、澄清参考、产物参考和中文契约测试。英文 Native 资产 MUST 在中文结果得到确认后再同步；同步完成后，中英文资产和双语言契约测试 MUST 保持同一触发条件、覆盖结构、分类分支、阻塞条件和验收语义。

#### Scenario: 双语言契约验证

- **WHEN** 用户确认中文结果并完成英文同步
- **THEN** 中英文 Skill、澄清参考、产物参考、双语言契约测试和独立 Agent 行为场景共同表达源文档完整覆盖模式
- **AND** 英文资产不得改变已确认的触发、分类、映射或阻塞语义

## 非目标

- 不改变 Native Runtime schema、CLI 参数、状态机、验收结果格式或机器 Runtime 布局。
- 不要求没有直接文件/链接来源的普通口述需求建立来源覆盖表。
- 不要求逐字复制与用户目标无关的排版元数据，但不得省略可执行要求、约束、示例语义或边界条件。
