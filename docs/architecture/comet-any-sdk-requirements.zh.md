## 需求来源与当前基线

- 来源是本会话中的架构讨论、用户对 Native 的纠正，以及将全部工作写成需求文档并通过 Supervisor 推进的指令。Native 增加流程，不建设内部组件替换机制；Classic 可以调整 Skill 编排。
- 工作分支为 `045`。2026-10-03 已推送基线 `be097ae07ca93f37a3dbb8f7e9e2feaba3e31c29`，本地、upstream、远端 SHA 一致。
- 基线包版本为 `0.4.5`，当时远端 master 为 `0.4.4`。发布时重新核对，不能把今天的版本比较当作未来发布事实。
- 当前源码的临时生成脚本实验确认了越序完成、结构化产物未被实际校验、必需 Skill 证据仅检查字符串，以及 Native 生成包初始化失败。该证据不是完整 Creator 发布链、npm 发布包或真实平台验收，也不等于已还原用户的历史生产事故。
- SDK 已提供 Run、Action、Wait、定义固定、校验和恢复机制；Native 与 Classic 的现有应用仍需提供可组合的应用接口及相应加载和恢复路径。

## 产品范围与执行边界

用户调用生成的 Skill 后，由宿主获取 Run 的当前工作，执行已绑定的 Skill 或工具并提交真实结果。生成物包括入口 Skill、应用定义、执行与验证绑定、依赖信息、必要适配代码和验证报告。原生 Agent loop、模型请求和工具执行仍由宿主提供。

三种起点全部属于本轮范围：Native 的可选扩展、Classic 的 Skill 编排、独立 SDK 工作流。下面的 R01 至 R26 是完整需求条目，Q1 至 Q7 的决定已纳入对应条目。

## R01 用户目标与交付物

comet-any 根据用户目标和真实 Skills 生成可调用的工作流 Skill。支持基于 Native 增加流程、调整 Classic Skill 编排，以及创建独立工作流；交付完整 Workflow Application 包和实际验证结果。

验收示例：三种起点均能形成可运行的 Application 包；入口 Skill 能启动并继续对应流程，展示实际验证范围。

## R02 职责与运行权威

SDK Run 是一次执行唯一可推进的权威状态。comet-any 负责理解与创作，组合器负责装配应用，Native 和 Classic 各自负责业务规则，宿主负责推理、工具和交互。生成包不得复制另一套状态机。

验收示例：从入口、CLI 和恢复入口访问同一 Run；修改说明文件或投影视图不能绕过已声明的执行规则。

## R03 应用加载与归属

应用具有独立身份，加载时固定定义、执行绑定与验证器版本；CLI、当前 change 选择、Hook 和状态诊断能找到同一应用与 Run。不得仅改工作流名称而沿用仅接受内置应用的恢复判断。

验收示例：定制应用经公开入口启动、查询和继续均路由正确；同名不同项目或 worktree 不会串用 Run。

## R04 定义与依赖固定

固定工作流、Skill 内容及其引用资源、适配契约、验证器和所需 Runtime 的版本或摘要。活动 Run 使用原定义；缺失或内容漂移时给出可操作的恢复说明，不静默换用新实现。

验收示例：修改同版本定义、依赖 Skill 或资源后，活动 Run 拒绝按新内容继续；恢复原依赖后可以沿原记录恢复。

## R05 动作与恢复协议

复用 SDK 的 Action 领取、尝试、Outcome、Wait、revision 和并发提交机制。未满足依赖的越序回报、错误归属、陈旧确认和冲突回报被拒绝；合法派发的独立并行 Action 可按任意完成顺序回报。重复的同一合法结果按协议幂等处理；未知执行必须核对后继续。

验收示例：未满足依赖的越序回报、旧 attempt、错误 Action 归属和陈旧提案不能推进；合法并行 Action 可按任意完成顺序回报；断连后保留原 Action，已发生的外部操作不被自动重发。

## R06 Native 新增流程

Native 保留自身实现和默认无外部 Skill 依赖的主流程。定制应用可以在明确的业务位置增加可独立恢复的步骤；新增必需步骤通过后才能推进原流程，默认 Native 行为保持不变。

验收示例：Native 样板增加候选审查后，未通过审查不能进入后续验收；未配置扩展的 Native 不新增外部 Skill 依赖。

## R07 Native 执行指导

允许给 Builder 等实际工作附加指导 Skill，声明作用范围并把所需内容传给执行者。加载记录与产物符合规范的验收分别保存，不能以加载声明代替质量检查。

验收示例：Builder 获得指定版本的指导和范围；产物违反可检查的指导要求时，即使已经加载 Skill 也不能通过对应验收。

## R08 Native 验收与修复

新增检查绑定当前候选和输入工件；候选或相关输入变化时相应证据失效。业务审查失败进入明确修复路径，保留现有工作；不绕过 Native 的确认、独立 Verify、交付和 Archive 条件。

验收示例：审查失败可回 Build 修复；新候选重做已失效的检查；额外审查通过不能直接跳过 Native 独立验收或取得交付授权。

## R09 Native 需求变更

新增步骤改变已确认需求、设计工件或验收条件时，遵循基础应用重新校验和确认路径。纯实现修复与需求变化分别处理，不能错误复用旧授权。

验收示例：扩展引入需求变化会返回 Shape 重新确认；未改变确认范围的实现修复沿修复流程继续。

## R10 Native Supervisor 产品覆盖

生成的 Native 扩展覆盖普通 Native、Supervisor 父级、Child 和集成验收全链路。新增步骤、执行指导、附加验收和恢复要求必须传递到实际执行层，不能仅在父级生效。

验收示例：普通 Native、Supervisor 父级、Child 和集成验收中的扩展均有效；跨会话继续仍保留要求，父级加载一次 Skill 不能代替 Child 的执行与验收。

## R11 Classic Skill 编排

Classic 支持替换符合原工作契约的 Skill 绑定、增加步骤和调整允许的顺序。保持所选 full、hotfix、tweak 流程必要工件、授权、验收和恢复规则；不修改第三方原始 Skill。

验收示例：定制 Classic 在各受影响 profile 中可完成真实流程；无效替换或顺序变化被解释并拒绝，不用文本成功声明替代领域验收。

## R12 Classic 失败与恢复

Classic 定制工作仍由其 Application 与 SDK 推进。失败修复、需求修订、工件失效、审批与中断恢复沿同一 Run 执行，组合步骤不能在基础流程之外独立放行。

验收示例：Classic 新增或替换的工作发生失败、工件变化和中断时可恢复；基础命令不能绕过组合应用新增的必需检查。

## R13 独立工作流

支持不依赖 Native 或 Classic 阶段的独立应用，使用 SDK 表达顺序、分支、明确 join、子工作流和有界修复；业务规则由自身定义。以报告生成、用户审批和发布为完整样板。

验收示例：独立报告流程在审批前不发布，拒绝或修改后走声明路径，跨进程继续同一 Run；不宣称自动继承 Native 独立验收语义。

## R14 真实 Skill 发现与适配

读取 Skill 的真实说明、脚本和必要资源，区分执行指导、产出动作、检查动作、完整子流程。适配契约声明输入、输出、范围、宿主能力、用户交互、结束条件、失败与恢复；名称不能代替能力调查。

验收示例：真实内容不支持所要求能力、依赖缺失或输入输出不匹配时不能生成虚假可运行承诺；第三方原文件不被改写。

## R15 冲突与证据能力

识别多个 Skills 对职责、工件、确认、工具和副作用的冲突。完整外部流程必须显式适配为子工作流或可隔离工作。不能保证的行为如实说明，必需且无法满足的能力阻止运行。

验收示例：含有自行发布或接管审批逻辑的 Skill 不能作为普通指导绕过父流程；加载、自报完成、机器检查和独立评审能被区分。

## R16 确定性应用组合

在用户确认的方案和固定依赖下，装配流程定义、纯转移处理器、执行绑定、验证器和恢复身份。按同一组合结果生成入口说明和安装内容；不只修改图而沿用不匹配的转移处理器。

验收示例：相同方案与依赖生成一致的有效产物；未声明转换、缺失验证器及重复或冲突身份在执行前被发现。

## R17 输入输出与候选验证

Schema 必须真正校验结构，业务验证器核对实际产物、当前候选和内容摘要。只存在文件、存在字段或自行填写 completedChecks 不能等同于验收通过。

验收示例：非法 JSON、缺失必填数据、过期工件、错误候选和伪造完成字符串无法满足相应检查；拒绝后保留现场并给出修正动作。

## R18 Creator 可恢复创作

comet-any 自身使用固定的 SDK 创作流程，保存目标、方案、决定、依赖和产物之间的关联。完成分析、确认、编译、验证和交付；子代理按工作量组织，不要求固定六个角色。

验收示例：在方案确认或编译验证期间中断后能继续同一次创作；方案变化使受影响的确认和验证失效，不重复执行已明确完成的外部工作。

## R19 用户体验与确认

向用户展示具体步骤、绑定 Skill、产物、验收、失败路径和能力限制，内部 Bundle、注册和协议名不作为使用前提。确认绑定当前方案，安装前展示目标与文件变化，沿用已有有效授权。

验收示例：用户能从自然语言需求完成创作；看到实际流程和安装预览；方案或安装目标漂移时原确认不能被复用。

## R20 宿主执行与平台支持

产品支持 Codex 与 Claude Code 的宿主适配。宿主加载固定版本 Skill、领取和执行 Action、传递必要上下文、取得用户决定并提交真实结果。按用户 2026-10-04 的补充，本轮真实宿主和模型验收只在 Claude Code 执行；其他安装平台不计入本轮正式支持范围，Codex 的真实模型执行不计入本轮完成条件。

验收示例：Claude Code 完成真实 Skill 调用、必要交接和中断恢复；必需能力缺失时明确阻塞，不静默跳过。Codex 适配保留对应的本地契约与回归检查，报告明确未执行其真实宿主和模型验收。

## R21 外部操作与凭据

支持只读、本地工作区修改，以及可查询或具备核对适配的外部操作；首版不执行无法核对结果的外部操作。任何操作都不能扩大用户授权；外部操作和本地 Run 不假设原子提交，未知结果按适配契约核对后继续。凭据只由执行上下文注入，不进入包、Run、报告或生成配置。

验收示例：外部操作结果丢失后可按适配契约查询或核对，不盲目重复发送或部署；没有核对能力时明确阻塞；产物和持久化记录不包含凭据。

## R22 安装分发与升级

支持项目级安装、用户级安装和完整包导出，不建设远程 Git 发布安装或团队集中分发服务。安装提供预览、依赖检查和冲突处理；新 SDK 应用的活动 Run 所需旧定义保持可用，升级不静默迁移，卸载不能悄悄破坏在途任务。

验收示例：真实导出包在项目级与用户级目标安装后均可启动和恢复；同名冲突、升级与有活动 Run 的卸载按明确规则处理；不要求远程分发服务。

## R23 旧生成链退出

用户已明确不必考虑旧版使用。移除旧生成链，不为已发布旧包、workflow-protocol 状态或旧在途 Run 保留兼容层、旧版维护及迁移工具。新产物只使用 SDK 应用链；遇到旧格式时明确提示重新生成并保留用户文件。该决定不取消 R22 对新 SDK 应用自身升级和活动 Run 的保障。

验收示例：新产物只走 SDK 应用链，产品不再依赖旧生成和推进逻辑；旧格式被明确拒绝并提示重新生成，不被静默加载或自动转换，用户文件不被自动删除。

## R24 分层生产验收

分阶段完成定义检查、定向测试与故障注入、生成 Runtime、npm 打包消费者、真实宿主 Hook/交接及真实模型 Eval，并分别记录绑定当前候选与依赖的证据。Claude Code 覆盖 Native 普通与 Supervisor、Classic full/hotfix/tweak、独立流程，以及对应的创作、安装、执行与恢复；覆盖失败修复、中断恢复、候选或依赖漂移和旧确认失效。外部操作在隔离服务中验证已执行但回传中断与确认未执行两类恢复。本轮使用 Claude Code 2.1.251、glm-5.3[1M]，主代理与子代理同模型，正式矩阵六种流程各重复 2 次，共 12 个样本，最多并行 1 个，总时限 10 小时；Native 前置样板独立限时 1 小时，不计入正式矩阵。实际模型以进程轨迹为准，不能把费用遥测当金额硬限。规定样本必须全部通过，保留失败及超时记录，不以多次中的一次成功代替全通过；候选变化后重验受影响部分，仍匹配的证据可复用。预算到限或环境不可用的项目保持未完成；追加预算须取得用户决定，不重置已有记录。

验收示例：Claude Code 的全部指定流程及恢复场景在当前候选上满足已确认矩阵中的所有规定样本；外部结果核对后操作计数为一；未运行、失败、超时或缺少真实宿主及模型证据时不能完成生产验收。

## R25 实施顺序与不回归

按契约、Native 垂直样板、Native 扩展、Classic 与独立流程、组合器、Creator、分发验收七步推进。宿主执行、授权与未知结果核对契约在基础阶段确定；第一个样板同时验证公开入口、参考宿主真实 Skill 执行和冷恢复；默认 Native、Classic 和既有 SDK 消费者保持有效。

验收示例：先完成能运行、失败可修复和冷恢复的 Native 样板，再扩展生成能力；基础应用和 SDK 既有契约通过相关回归检查。

## R26 文档与发布范围

中文需求与 Skill 先完成并确认，再同步英文；README 仅保留必要入口并链接详细文档。按最终用户可见变化写英文 Changelog，发布前核对 master 和当前版本；保留无关修改，不改 website 或第三方原 Skill。

验收示例：产品文档与真实行为一致；中英文 Skill 同步后再更新对应发布说明；检查与修改范围可追溯。
