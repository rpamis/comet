# 核心流程的历史故障与回归约束

## 为什么这些问题会集中出现

这些报告涉及不同表现，但共同风险在于同一个契约分散到多层维护：状态机决定可执行动作，continuation 拼命令，CLI 检查参数，验收器重新核对证据，交付再解释文件和提交范围。单独验证某个函数或正常流程，不能证明这些层在 blocked、冷启动、旧 Run、并行 change 和分拆提交时仍保持一致。

本轮重点修复契约边界，不以删除安全检查换取通过：

- **恢复状态与命令必须一致**：公布的命令必须携带当时必需的 revision/proposal 参数，并确实支持当前普通 change 或 Supervisor 状态。
- **验收内容有结构边界**：Markdown 的 section 和 list item 是不同层级，后续标题不能自动变成最后一个验收项的正文。
- **检查输入不等于交付所有权**：检查可能读取完整工作区上下文，但不能因此要求将另一个 change 的草稿一起提交。
- **交付依据是批准的范围**：实现与归档可以形成线性提交序列；必须检查整个序列和最终内容，不能只检查 HEAD，也不能顺便携带未经批准的路径。
- **执行配置必须贯穿入口**：项目默认、显式 CLI 参数、复用收据和组合式 SDK 执行器需要采用一致的超时语义。
- **输出排除必须明确**：Classic 的 Git 默认输入本来就排除未跟踪且 ignored 的文件。新增能力是显式声明 ignored 输入时仍能绑定它，以及主动选择输出预设；不是把所有生成文件都当成无关缓存。

## 可执行的回归入口

在仓库中先构建，再执行：

```sh
pnpm build
pnpm test:core-regressions
```

查看已有组或只验证一个 issue：

```sh
pnpm test:core-regressions --list
pnpm test:core-regressions --case 505
```

该入口不下载依赖，不自动修改生成物，不重跑整仓全部测试。它先检查生成 Runtime 是否与源码一致，再顺序运行有限的回归组，每组至多两个文件 worker，保留 JSON 报告到 `coverage/core-regressions/`。失败、空选择、缺失结果、必需用例未执行都不能报告通过；每次执行前删除对应旧报告，避免误用上一次结果。

这些用例也遵循仓库既有 `test/**/*.test.ts` 发现规则，不依赖另外启动一个监控任务。

## 历史故障映射

### #500 / #501：内容、环境和快照完整性

`native-check-evidence` 保留跨 shell 提交、旧收据升级、Next 类型和生产输入变化、缓存变化、检查期间源码漂移及完整性不足等正反向用例。会话环境变化不能冒充候选内容变化；真实输入变化、不完整快照和损坏收据也不能冒充有效证据。

### Classic 重开验证和命令身份

`classic-continuity` 覆盖 Full、Tweak、Hotfix 的源码和独立进程生成 Runtime。重开验证后仍能归档及交付；旧批准、被篡改的文档和换掉的检查程序不能被复用。

### #502：检查配置与显式输入

`classic-check-policy` 与 `classic-composed-timeout` 分别覆盖 public CLI 和公开 SDK 工厂。项目超时与 CLI 覆盖均有实际执行测试；未声明输出导致漂移、显式输出保持中立、tracked 文件不能被 gitignore 隐藏、显式 ignored glob/目录必须进入证据，均有对应断言。

预设是命令主动声明的输出，不是通用“忽略错误”开关。若某个检查读取构建产物，就不能把该输入所在目录选成输出预设。显式 glob 应尽量使用准确目录前缀，避免把整个依赖树声明为检查输入。

目录本身不再作为当前 per-file manifest 之外的隐藏摘要项，避免仅创建输出父目录就使证据变化。旧 pre-manifest 摘要保留原算法；少数旧 SDK 目录摘要可能一次性失效，必须通过新的验证轮次恢复，不能承诺所有旧证据无感复用，更不能自动重放一次性检查。

### #503：多 change 与多提交交付

`classic-delivery-scope` 覆盖停在 Shape 的 Native 草稿与另一个 Classic hotfix 共存，兼容 `delivery --verify` 入口，以及分离的实现/归档提交。允许正常线性提交范围不代表允许任意历史：每一个提交的路径、最终字节、批准基线和远端身份仍要验证。

### #504：Markdown 验收边界

`native-acceptance-boundaries` 覆盖中文/英文标题、同级/更高标题、嵌套列表与标题、表格、代码块、setext 标题、重复章节、实际验收内容变化和旧批准快照。

这里有一个必须明确的边界：修复最后一个验收项误吞章节，不等于授权修改已确认的整份 Shape。独立计划表不再被误称为某个验收项的变化，但若它仍写在已确认正式文档中，修改它仍受原 Shape 批准约束。没有通过忽略所有未知附录来绕过要求；不能凭当前已修改文本猜测原来批准了什么。

### #505：blocked 后可用的恢复

`native-blocked-recovery` 逐字执行 continuation 给出的命令，验证候选和一次性检查保留、冷启动后复验、过期批准/状态拒绝、旧 Run 的精确迁移以及完整的再次验收。仅出现一个 pending Verifier 不算恢复成功；新的独立 Verifier 必须能提交结论，旧 attempt 的 blocked 结果不能被误认为新 attempt 的同一会话。

## 证据层级和维护要求

1. 新 bad case 先复现，再增加行为测试，说明被修复的契约和不能削弱的反例。
2. 修改状态、命令、持久格式或审批字段时，覆盖实际 public 入口及旧记录读取，不手工伪造一条正常流程来掩盖缺口。
3. 修改 Runtime 后同步生成物；源码测试与用户安装的 bundle 必须分别验证。
4. 此回归集合减少已知同类问题再次出现的风险，不保证未来永远没有未知缺陷。实际 Windows/macOS、真实 Agent 平台、外部工具与生产负载仍是独立验收层级。
5. 不能把测试过滤、浏览器不可用、依赖缺失或超时当作通过。修正测试夹具时必须保留原安全语义，并记录为何旧夹具不再代表被测场景。
