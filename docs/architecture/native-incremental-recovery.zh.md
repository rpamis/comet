# Native 增量验证与恢复

来源：`report:2026-10-25-native-incremental-recovery`。用户要求允许修改代码和文档后增量推进，减少重复检查与模型上下文，并避免归档、文件锁和工作区冲突造成没有恢复入口的阻塞。

## 行为要求

1. Build 内修改保持 Build。Verify 后修改实现生成后继候选，保留已确认 Shape、原检查收据与修复原因；正式需求、验收项或子任务契约改变仍须重新确认 Shape。
2. 当前 Agent 对照已批准原文判断正式文档变化；契约未变时保留批准。普通编辑不增加独立审查 Agent，不根据扩展名、注释语法或排版推断语义；目标、验收或授权实质变化时才请求相关决定。
3. 同一候选、完整输入与执行上下文不变时复用检查。输入变化时，由当前 Agent 判断影响并明确列出仍适用的原检查；Runtime 绑定实际变化、原执行、计划、环境和日志。普通命令保留完整项目输入，不能用一个未经核对的文件列表代替实际变化观察。
4. 复用收据保留原 Action、尝试、候选和日志来源，不能把历史执行描述成新执行。原收据不完整、过期、损坏或执行结果未知时不能复用；新 Verifier 仍需覆盖全部验收项。
5. 遗留收据不具备范围证明时执行当前检查建立新证据。过程捕获不稳定、非 Git 输入、子模块与路径异常遵守已有完整读取与候选绑定规则。
6. `status`、`next`、`archive` 与 `doctor` 使用同一恢复结果结构，包含具体原因、受影响路径、持有者、诊断命令、恢复命令和前提、保留的候选与批准。只读查询不获取写锁或执行恢复。
7. 活跃锁等待原操作；已证明原进程退出的锁按文件身份恢复；未知归属锁须核对停止事实并绑定精确记录，不能只因过了一段时间就自动删除。
8. Archive 继续原事务和 Action。只读预检可以重试；未知执行先核对；恢复不重复已完成副作用。外部权限或 Git 冲突须报告路径和处理条件，不能声称命令未做任何改动。
9. 不新增 `.comet/config.yaml` 文件数量、大小等预算，也不保存第二套推进状态。机器证据留在按 workspace 隔离的用户级 Runtime 目录。
10. 领取身份错误或文档已变化时，原 Verifier claim 仍可记录实际执行失败，结束原 Action 并保留候选、Shape 与检查；失败不是验收结论。后继验收仍核对独立身份与完整证据，文档恢复原批准内容或重新确认后才能继续通过。

## 接入方式

- `native-portable-checks.ts` 捕获文件原始字节、路径及执行模式，将 Git 元数据单独记录。捕获覆盖实际输入及适用的生成文件，不解析项目代码、不调用项目编译器；读取失败、目录身份变化或输入不稳定时返回不完整观察，不能复用旧检查。
- `native-sdk-checks.ts` 在原 Run 中查找与当前检查匹配的完整原始收据，结合当前 Agent 对全部差异的判断核对后复用。没有适用证据时执行当前计划；整体候选和输入仍由原检查前后指纹约束。原有可证明完整范围的执行器收据保留兼容，不能据此限制新观察支持的项目语言。
- `workflow-contract/edit-review.ts` 保存原始变化和当前 Agent 判断；`comet edit-review observe` 合并连续保存，`record` 明确记录语义、影响及保留的检查。判断只覆盖已绑定的内容，再次编辑后只补处理新增变化。
- `native-recovery.ts` 投影恢复契约；`native-command-recovery.ts` 将只读文件锁观察、现有归档收尾结果与 continuation 汇总到同一结构。状态转换仍由原领域 Runtime 执行。

## 修改后的推进判定

| 当前修改                            | 推进方式                              | 需要重新建立的证据                                     |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------ |
| Build 中修改实现                    | 保留 Shape，在当前 Builder 中继续     | 提交候选时绑定当前内容                                 |
| Verify 后修复实现                   | 保留 Shape，交给 Builder 提交后继候选 | 变化输入涉及的检查，以及新 Verifier 对全部验收项的判断 |
| 补充语义未变的测试计划或说明        | 当前 Agent 判断后保留批准             | 只补实际受影响的检查，不新增独立审查或确认             |
| 已接受结果、尚未归档时修改普通说明  | 原 Run 补检查，保留报告与批准         | 当前 Agent 证明原验收仍适用，再执行原固定可重复命令    |
| 改变需求、验收标准或任务契约        | 重新确认 Shape                        | 新契约下的候选、检查和独立验收                         |
| Archive 时实现或 Specs 与证据不一致 | 保留原事务与证据，报告具体偏差        | 按偏差类型回到实现修复或契约确认，不自动接受旧结论     |

文件哈希复用、检查结果复用和模型上下文复用分别处理。文件哈希缓存绑定实际文件身份、大小、模式及高精度时间，并在所有补读和 Git 范围核对后复查原目录观察；不能仅凭 Git 显示干净或开始捕获时文件未变化就复用。检查结果必须匹配检查计划、执行环境和原日志；输入差异只能由覆盖当前内容的 Agent 判断保留，最新失败、中断和未知结果持续遮蔽旧成功。Builder 修复上下文提供失败验收项、前一候选、已确认 Shape 和检查引用；权威历史仍保留在原 Run，不能把新增修复上下文直接宣称为已减少模型输入。

内容观察不依赖检查命令的语言。当前 Agent 可判断测试、构建或任意命令是否受变化影响，但必须明确关联原执行和实际差异；判断摘要不能替代原文、实际检查结果或缺失的输入。已接受候选另有独立输入基线，补检查运行中出现的新编辑不能被新的通过结果自动接纳。

批准后补检查使用观察返回的 `refreshInputTemplate` 和 `comet edit-review refresh-checks <native|classic> <change> --file <file> --json`，按响应继续原 Action。原报告、接受决定、Run 和归档事务保持原关联。相同请求返回原真实结果；能证明尚未启动的异常在原 Action 记录未执行证据后重试，结果未知时先核对原执行，不能通过更换检查 ID 或请求 ID 重放副作用。

## 阻塞后的处理

1. 先读取状态、原 Action 和锁记录，返回原因、路径、持有者、诊断命令与恢复前提。没有 Run 或非 Native 应用时，诊断也不得创建 Native 目录或取得写锁。
2. 活跃写入者仍在时，返回等待条件。已证明退出的本机写入者允许安全恢复；未知或损坏记录须在明确停止确认后，使用精确令牌重新核对文件身份。记录被替换即拒绝旧令牌。协调锁本身阻塞时，恢复不能再次请求同一个协调锁。
3. 区分项目锁、投影锁、Run 写锁与应用协调锁，诊断实际阻塞的层级。Git 锁单独报告，不能用文件年龄代替进程停止事实。
4. 归档失败时读取原事务，核对 prepare、apply、finalize 的持久收据。已完成的步骤只核对，不重复执行；结果未知时先恢复原 Action。恢复命令重复调用后仍返回同一归档结果，不重新检查或重复应用 Specs。

权限不足、外部文件占用和仍活跃的写入不能承诺自动消失。完成条件是阻塞原因可定位、原工作不丢失、前提满足后有可执行且经过验证的恢复入口。

## 验收

每个新增行为登记到 `config/workflow-regressions.json`，精确关联可执行断言。验收覆盖：后继候选只重跑受影响的可靠范围检查、任意命令保守重跑、环境/包声明/日志变化不误复用、旧收据兼容、正常独立验收与归档、并发修改、活跃/陈旧/未知/损坏锁、执行输出给出的恢复命令，以及归档中断后不重复副作用。

模型是否实际减少 token 需要当前候选的真实模型 Eval；确定性测试只证明 Runtime 复用次数、推进路径和上下文结构。Windows 文件系统回归、生成命令 bundle、npm 包与真实平台事件分别记录证据。
