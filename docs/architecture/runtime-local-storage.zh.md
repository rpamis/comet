# 本机 Runtime 存储

Native 与 Classic 把本机执行状态放在用户数据目录，项目只保留协作、跨设备恢复和正式审计需要的内容。此目录是持久状态，不能当缓存删除。

## 目录与隔离

默认目录为 `~/.comet/workspaces/<workspace-id>/runtime/`。`COMET_DATA_DIR` 可将 `~/.comet` 替换为明确指定的数据目录；测试使用临时目录。运行中的工作区不要随意更改这个环境变量。

workspace 身份从规范化的真实项目路径、目录创建身份和 Git 元数据目录创建身份生成完整 SHA-256。相同仓库的不同 clone、主工作区与 linked worktree 分别保存本机状态；通过符号链接访问同一个真实工作区不会创建第二份运行状态。Git origin 不是隔离键。分支切换、Git gc/repack 和进程重启保持身份稳定；删除后同路径重建工作区，或保留项目目录但替换 `.git`，都会使用新身份，旧用户目录原样保留。项目搬家也需要通过可移植状态恢复，不会按仓库地址接管旧执行器。

在非 Git 项目执行 `git init` 也会切换本机身份，应先停止旧 CLI/Agent 执行器。SDK 可用有效的 YAML checkpoint 恢复，未明动作仍需核对结果；Native v4 的便携状态会先恢复缺失的本机执行投影，再继续后续操作。旧 compat Run 若没有可恢复的完整便携状态，则会停止并提示缺失本机 Run，需要保留原 Runtime 备份另行恢复。本次不承诺这类身份变更能无感续跑。

Classic `comet-state.yaml`（历史 `.comet.yaml` 原地兼容）另保存稳定的 `change_id` 实例身份，保证归档移动和 Git 分支切换后仍能找到本机记录；归档后复用同名 change 会得到不同身份。它是随 change 保存的恢复事实，不保存执行日志。

本机目录包括 SDK Run、change 归属、状态投影锁、Native 执行证据与事务，以及 Classic 的 run state、检查日志、checkpoint、Skill snapshot 和协调状态。CLI 的 status、show、inspect、Doctor 继续是查看这些状态的入口。

项目中仍保留一个被忽略的 `.comet/current-change.json` 入口选择文件，供现有 Router 选择当前工作；本次不改变安装和路由配置布局。协作产物包括配置、brief、spec、验证报告、Native `comet-state.yaml`、Classic `comet-state.yaml`（历史 `.comet.yaml` 原地兼容），以及需要随 change 保存的 handoff 和正式归档/交付凭据。是否应提交 Git 取决于用途，不取决于扩展名；不是所有 JSON 都是可删除缓存。

## Classic 状态文件命名

Classic SDK 新 change 与 Native 一样创建 `comet-state.yaml`。历史 `.comet.yaml` 保持原地读取、写入、恢复与归档，不自动迁移文件名；显式 compat 初始化继续使用 `.comet.yaml`。同一个 change 下两个文件同时存在时（包括其中一个是失效符号链接），入口、SDK Store、Guard、Hook 和诊断都会拒绝歧义，不能静默选择其中一个或覆盖状态。先备份并核对来源，再处理冲突。两种 workflow 的目录与状态 schema 仍各自独立。

跨设备应同步实际使用的状态文件、change 文档、引用工件、代码及项目配置；`run_checkpoint` 保存已记录的阶段与确认，但不包含独立子 worktree 和未提交代码。换机前结束旧执行者，并确认最新状态已写入文件。

## 已有项目迁移

从 `0.4.5` 升级到 `0.5.0` 前，建议先用旧版完成并归档所有活跃 Native、Classic 任务。本次不保证旧活跃任务跨版本续跑；下述迁移用于安全处理升级后保留的本机数据，不代替旧任务的完成与归档。

升级已有项目后，先在项目中运行 `comet update`，刷新包括 Classic-only 项目在内的忽略规则。旧规则 `.comet/runtime/` 只能忽略目录，不能覆盖新的文件型兼容标记；不要通过删除标记来消除 Git 提示。

第一次使用新 Runtime 时会检查旧本机目录，核对文件与安全路径，复制并校验后才切换到用户目录。不通过软链接重定向运行状态，不把新旧两处都作为写入权威。

每个工作区在旧 Runtime 根位置保留很小的兼容标记；已有子目录迁移后也保留对应标记，用来阻止旧版 CLI 再创建目录或写入旧状态。标记受 Git 忽略规则保护；后续状态只写入用户目录。完成核验与切换前，不删除旧数据。旧活跃锁、正在执行的动作、未完成事务或无法证明一致的目录会阻止迁移，应先停止原执行器或用原版本完成恢复；不要手动删除锁来强行继续。

迁移中断会保留恢复现场；重试时，只有确认原迁移进程已退出，并且备份、标记和目标均通过记录中的身份与内容校验，才会自动续迁。未知 owner、内容冲突或无法核对的部分副本继续阻止操作，不凭文件年龄、未知 PID 或不完整数据猜测成功。旧程序已持有的任意裸文件描述符无法由新版本撤销，因此升级前应结束旧 CLI/Agent 进程。

如果迁移完成后用户目录丢失，属于当前工作区且目标匹配的标记不会阻挡便携恢复，也不会伪造空记录。SDK 可用有效的 YAML checkpoint 恢复进度；旧 compat Run 若只有 `run_id` 而没有可恢复的完整状态，会明确报错，不能当作新 Run 重建。日志、执行证据和未完成现场仍需从本机备份恢复。

## SDK 文件数量

SDK 不再为每一个 revision 保存一份完整 Run。每个 Run 使用固定格式标记和一个带内容校验的当前 checkpoint；写入与压缩在可恢复的跨进程锁内进行，先比较 revision，再原子发布。revision 保持单调递增，恢复来源版本不会被压缩重置。

旧编号历史必须先通过连续性、身份和内容校验，且先阻断旧路径写入，才能提交新 checkpoint；只有被新 checkpoint 覆盖并核验过的旧文件可以清理。损坏或竞态留下的文件不会被静默跳过。崩溃不能把半份 JSON 当作已提交状态。

采用单个原子 checkpoint 而不增加增量日志，是为了保留现有读取语义，并减少日志重放与压缩切代的恢复边界。它消除的是每个 revision 重复保存完整 Run 的开销。Run 内的必要 Action、审批、收据和幂等事实仍会随实际执行增长，不能为了固定字节数任意截断。

## Native 活动与历史分区

内置 Native 任务在完整取消或正式 Archive 收尾后进入本机历史分区。取消必须确认原领取方、子 Run 和 Runtime 管理的检查进程已经停止，并释放当前选择；Archive 还必须核对已提交的归档结果、验证报告和事务收尾。暂停、等待、可重试失败、取消未完成、未知执行和未完成清理都保留在活动集合。固定的自定义 Native 应用目前保守保留在活动布局，继续原有检查与恢复协议。

封存只移动本机权威 checkpoint 和身份归属，不删除 change 文档、审批、执行收据、可移植 checkpoint 或跨设备恢复材料。封存 Run 不再接受普通写入。新的取消和 Archive 成功收尾会自动封存；旧终态记录在普通只读命令中保持原布局，不会为加速而悄悄迁移。

升级 CLI 及所有已安装平台的 Runtime、Hook 后，可以先运行普通 Doctor 查看状态，再显式迁移：

```sh
comet native doctor --json
comet native doctor --migrate-history --json
# 也可仅处理一个任务
comet native doctor <change-name> --migrate-history --json
```

迁移逐项验证，输出已封存、仍活动及验证失败的任务。它不代替停止执行、修复未知结果或清理锁；有问题的任务先按 Doctor 指引处理，再重新运行迁移。中断后可重跑同一命令，已完成部分保留。新存储格式会明确拒绝旧版写入，因此升级 CLI 后还需同步更新平台安装，不能继续使用旧 Hook 或旧 Runtime，也不要删除格式标记尝试降级。

活动 Hook 和活动任务列表只完整检查活动记录；历史只检查分区和身份元数据，发现活动/历史冲突仍会阻止操作。历史正文被外部修改的错误由显式 `show`、具名 `status`、`comet status --include-history` 及 Doctor 读取历史时发现，不能依靠空 Hook 证明所有历史正文未被改写。封存前会验证现有执行已停止，正式 Runtime 也不能从封存 Run 派发新工作；此规则不阻止其他程序绕过 Runtime 自行启动进程。

换机或丢失本机存储后，可移植恢复先重新建立本机活动状态，再按本机执行与工作区绑定重新核验。便携材料中的终态描述不能直接让新设备跳过恢复检查或自动信任为已封存。 如果新设备缺少原检查进程登记或清理证据，恢复的终态 Run 可能继续保留在活动布局并接受完整检查，直到既有正式核验条件满足；迁移结果会把它列为保留活动。布局本身不重新执行已取消或已归档的动作，已归档任务也不会因此占用新的合法流程。

## 可移植状态与归档

YAML 的 `run_checkpoint` 仍保存跨设备恢复需要的最新状态，不加入本机 revision 历史、日志或旧 checkpoint。它会去掉被拒绝结果的本机记录，并把 `running` 转为 `unknown`；另一台设备必须核对外部执行结果，不能自动重放。已经需要的审计与幂等事实继续保留，因此复杂、长期 Run 的可移植状态仍可能增长。

Classic 已完成检查的本机日志缺失时，只有当前权威 Run 与有效 checkpoint 中的完成动作、输入、claim、结果和日志引用完全对应，才能继续使用已确认结果；仍会核对当前环境、输入和验证报告。现存日志被改写、路径或类型异常都不能走此恢复路径，也不会补造原日志。

Supervisor 子工作区、未提交代码和外部工具现场不包含在父 YAML 中，需要使用受控 transfer 流程。复制或克隆项目不会访问迁移标记中记录的另一工作区数据目录。

用户目录和项目可能位于不同卷。Native Archive 的持久 journal、备份与执行状态放在用户目录，发布候选暂存在目标文件旁的 `.comet-archive-staging/`，以保持硬链接发布与回滚的同卷保证；提交或回滚完成后清理。中断的事务保留这些受忽略保护的临时文件供恢复使用。不能承诺项目在事务进行时绝对没有临时文件。
