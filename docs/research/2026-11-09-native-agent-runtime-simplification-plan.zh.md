# Native Runtime 减负实施方案

来源：`report:2026-11-09-native-agent-runtime-simplification`。

状态：已获用户授权实施、提交并推送；执行结果见同目录 native-agent-runtime-implementation 记录。Eval仍需单独授权。

## 目标与范围

Native 信任 Agent 判断需求、实现进展、检查范围、证据适用性和验收结论。普通检查使用 Agent 平台工具执行；Runtime 接收实际业务结果，维护用户决定、任务归属、状态提交和必要的副作用恢复。

重点删除内置 Native 的普通检查证明系统及重复交接，保留 SDK Run 的推进权威。沿用现有业务入口与模块，不新增第二套状态机、检查执行框架、内容证明协议或项目配置开关。

范围包括普通 Native v3、必要的 Supervisor 适配和旧 Run 续行。Classic 的独立规则、自定义 SDK 应用、website 和无关平台能力保持现状；共享层只修改明确受影响的调用。

## 保留的最小 Runtime

- Shape 用户确认、需求实质变化后的重新确认、最终结果接受，以及各自独立的 Git 交付授权。
- 当前 workflow/change/Run、真实会话和工作区归属，全部已确认验收项，以及用户明确要求的独立审查。
- 失败、blocked、未运行、超时与结果未知的真实区别；未知执行不得自动重放。
- 单一权威 Run、外部输入一次边界校验、原子状态提交和必要的写入协调。
- 受保护写入、无关修改保护，Archive、Spec 发布和 Git 集成等副作用的事务及恢复。
- 旧 Run 已有用户决定、已完成结果和来源；恢复不伪造批准、不重复已完成副作用。

Agent 使用平台工具运行检查后，要等待并读取原任务结果。工具等待超时不等于进程结束，缺少结果时继续追踪或报告未知。撤下 Native 的重复监管，不代表所有平台都天然具有相同的停止与恢复能力。

## 八项工作与实施顺序

| 编号 | 要做的事                                           | 批次        | 完成条件                                                     |
| ---- | -------------------------------------------------- | ----------- | ------------------------------------------------------------ |
| N01  | 撤下普通检查必须由 Native 受管执行才认可的要求     | A           | 平台工具的实际结果可直接作为业务输入，不为取得收据重跑       |
| N02  | 删除普通检查专用监管、收据、候选匹配与复用血缘证明 | A           | 普通路径不再承担配套进程与证明协议；结果归属和未知执行仍准确 |
| N03  | 取消固定的 Builder → 检查 → Builder 回合           | A           | 实现和检查完成后一次提交，直接交给验收                       |
| N04  | 删除结果二次读取及重复业务解析、状态计算           | B           | 外部输入校验一次，同次动作只计算一次                         |
| N05  | 删除同一操作内重复的目录身份、Runtime 根和分支观察 | B           | I/O 与 Git 查询减少，真实写入和工作区变化仍受保护            |
| N06  | 将观测库维护移出每次业务提交的同步等待路径         | C           | 合并写入与维护，Dashboard 语义及短命 CLI 落盘继续成立        |
| N07  | 清理旧项目内容快照、旧证明入口和遗留字段           | C           | 明确退役消费者和旧数据去向，不误删现行恢复能力               |
| N08  | 决定完整 Run 的 Portable 镜像是否改为显式导出      | D，单独决定 | 先确定跨机恢复承诺及迁移路径，再考虑删除默认镜像             |

### 批次 A：普通检查交给 Agent

从 [native-sdk-checks](../../domains/comet-native/native-sdk-checks.ts)、[执行登记](../../domains/comet-native/native-sdk-check-execution.ts)、[进程执行器](../../domains/comet-native/native-check-executor.ts)、[任务入口](../../domains/comet-native/native-sdk-task-command.ts)与[应用定义](../../domains/comet-native/native-sdk-application.ts)开始。

1. Agent 选择必要检查，通过平台终端执行，读取真实结果。优先复用已有业务字段，保存命令、目录、状态、必要结果引用和说明；新增字段前核对同概念既有名称。报告无需自制 hash、指纹或收据。
2. Runtime 接收报告并校验一次结构；检查是否充分、原结果是否仍适用，由 Agent 与实际验收者判断。真实失败、未运行、超时和未知不能算通过。
3. 从内置 Native 普通检查路径撤下额外 Node 监管、PID 身份探测、执行登记、stop 文件、停止收据；Comet 仍直接启动的其他可写副作用进程保留必要生命周期管理，不删除共享平台能力。
4. 删除普通检查的候选匹配、计划全文比较、reusedFrom 来源回溯和重复收据核对，保留当前任务身份与真实结果来源。
5. Agent 完成实现和检查后一次提交候选及结果，进入 Verify；中途调试与测试是 Agent 的实现工作，不强制拆成状态机步骤再返回 Builder 转述结果。
6. Supervisor 子任务和父级验收接收实际报告，父级仍覆盖全部验收并补足集成缺口。检查并行与次序由 Agent 按依赖和共享输出判断，必要 Git 集成串行，不引入通用检查 DAG。
7. 自定义 SDK 应用明确声明的工具步骤、固定命令与专门执行器继续按应用契约工作，不随内置 Native 一起静默移除。

本批必须走通公开 CLI 的 Shape 批准、实现回报、Verify、用户接受和授权 Archive。平台工具已经完成的检查不因进入验收而重复执行；用户要求独立审查时使用真实不同会话。

旧 Run 兼容：完成的受管结果保持可读且不重跑；运行中或未知的旧检查沿原登记核对结果或停止事实，再沿原 Run 续行。集中保留必要兼容边界，不让新 Run 继续使用整个旧证明系统。

### 批次 B：只消费一次输入和业务计算

- N04：[任务结果](../../domains/comet-native/native-sdk-task-command.ts)已由稳定读取取得对象，随后 registerNativeSdkRequestInput 再读同一文件并比较 JSON.stringify。该[登记函数](../../domains/comet-native/native-runtime-ownership.ts)当前没有登记副作用；删除第二次读取，直接消费首次对象，实施前核实所有调用者。
- N04：[Builder/Verifier Validator](../../domains/comet-native/native-sdk-application.ts)先计算业务状态，Transition 再算同一结果。让同次动作消费一次解析与状态计算；磁盘重载和外部输入仍在入口验证，不为此另建通用缓存框架。
- N05：在[受保护读取](../../domains/workflow-contract/protected-project-path.ts)、Runtime 位置解析和[Git 工作区观察](../../platform/paths/git-worktree.ts)的实际调用链中删除重复前提。真实受保护写入和 CAS 边界保留；经过外部执行或切分支后重新观察，不用永久缓存隐藏变化。

本批验证输入单次消费、畸形输入拒绝、真实分支变化、路径逃逸、原子提交与正常续行。对比新建、领取、回报的文件/Git 调用数，不能只比较代码行数。

### 批次 C：观测与旧内容快照

N06：[观测包装](../../domains/workflow-application/run-trace.ts)每次成功提交都等待[SQLite 写入和维护](../../platform/process/runtime-trace.ts)。优先按命令合并写入，集中维护连接和清理；短命 CLI 退出前完成约定落盘，不使用无人等待的 Promise 静默丢失数据。Dashboard 时间线、起止事实和乱序更新语义继续保留。

N07 先区分三种对象：

| 对象                  | 当前事实                                                                        | 处理                                               |
| --------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------- |
| 项目文件内容基线      | 旧 createNativeChange 仍有扫描和完整性阻塞；默认 SDK v3、当前 Compat 新建不调用 | 旧消费者与导出逐项退役，不把它说成当前默认启动成本 |
| workspace-config.json | 当前记录配置创建归属，旧数据可能含 hash                                         | 保留最小归属信息，不因变量名 snapshot 就误删       |
| 完整 SDK Run 检查点   | 当前仍保存流程和执行记录，用于恢复                                              | 归 N08 单独处理                                    |

清理从 [native-change](../../domains/comet-native/native-change.ts)、[native-snapshot](../../domains/comet-native/native-snapshot.ts)、旧 build-evidence/check-receipt、schema migration、guards、diagnostics 及[公开导出](../../domains/comet-native/index.ts)追踪消费者。撤下内容基线、前后内容比较、完整性阻塞与无用途的预算/策略依赖；旧 Run 仍需的只读解析与迁移集中保留。冻结实验与 fixture 不改。

旧 check-scope 及 SDK 的 inputSnapshot、logSha256、指纹字段已有部分无生产调用，并发工作正在退休相关测试，先核对现有差异。遗留清理主要减少维护面，不承诺显著提速。

本批完成条件：新建/普通续行不进入内容快照链；旧 API、归档、批准与必要恢复有明确去向；观测调整没有丢弃现有 Dashboard 功能。

### 批次 D：完整 Portable Run 镜像的取舍

建议日常只维护单一权威 Run，完整快照在显式导出/转移时生成，减少[边界镜像](../../domains/comet-native/native-sdk-state-store.ts)和[检查点编码](../../domains/engine/portable-run-checkpoint.ts)的完整处理。

这会改变复制 checkout 或本机数据丢失后，凭正式目录精确恢复原 Run、用户批准、执行记录和未知状态的承诺。首批保留该能力，不阻塞 A–C；恢复语义的取舍明确后，再删除默认镜像并准备旧检查点、导出格式和实际转移入口的迁移。

Agent 可从需求和文件恢复任务理解，不能重造丢失的批准、声称未知副作用完成，或用新 Run 冒充原 Run。不得为了删镜像又维护另一套推进状态。

## 验收与历史案例

以下均为待取得的证据，不是通过记录。每批先确定最小相关选择器，不机械运行全仓。

| 边界         | 验收要求                                                                             |
| ------------ | ------------------------------------------------------------------------------------ |
| 公开 CLI     | 最小项目走通 new、Shape 批准、实现回报、Verify、接受和 Archive；接受平台实际检查结果 |
| 执行事实     | 成功检查不重跑；失败/未运行/超时/未知不通过；未知旧执行不自动重放                    |
| 身份授权     | 错会话、错工作区、未批准 Shape、未授权交付不推进；独立要求不能由同会话满足           |
| Supervisor   | 子结果隔离、父级完整验收与集成缺口、必要集成串行；局部等待扩大阻塞单独复现           |
| 输入与恢复   | 结果只消费一次、外部格式错误拒绝、真实分支变化和受保护写入、原子提交与恢复分别验证   |
| 观测与旧数据 | 已有 Dashboard 记录可读、短命 CLI 落盘、真实旧 Run 和归档样例续行                    |

Supervisor 全局 Wait 与长内部队列目前只有源码风险，未做真实场景复现，先按实际依赖核实，不为假设并发问题扩展协调机制。

按[badcase维护规则](../../docs/architecture/badcase-maintenance.zh.md)保留本来源并拆分独立行为。用户行为修复优先取得同案旧失败、新通过证据，登记精确选择器。撤下功能/历史测试采用 feature-removed 迁移，保留旧来源、断言正文和替代契约，经 Review 确认；仍存在功能的断言不缩窄，不靠删测试换绿。

Runtime 源码改动后构建受影响 Native bundle；Entry/共享层/插件受影响时补对应构建，核对生成新鲜度。Skill 先中文，用户确认后同步英文，中英文同步后再写英文 Changelog；版本届时核对 master 和现有未发布条目，不按拆批机械加版本。

确定性测试、生成 Runtime、打包、真实平台 Hook 与真实模型各自报告。平台工具执行/回报方式要有真实平台证据；模型是否遵循简化协议需要模型证据。未获用户明确启动请求时不运行 Eval，缺口记录为未执行，不把单元测试写成模型行为通过。

## 性能对照与首批启动

前轮 Windows 小样本：直接空 Node 命令约64–70ms、Native受管约517–543ms；空Git项目领取Shape约929ms，1084次lstat、817次realpath、3次Git查询。计量有环境和仪表开销，不能当作当前候选基准或收益承诺。

实施时用相同工作区类型、CLI启动方式与检查计划对比：实际检查次数、Agent/CLI往返、文件/Git调用数、处理时长和Run读写规模。先确认重复执行/交接消失，再测固定成本；不用历史Dashboard动作跨度推算模型提速，不引入新指纹。

首批顺序：

1. 核对仓库与并发工作；通过正式入口处理已确认的Hook所有权/恢复阻塞，不手工修改Runtime状态。
2. 仅启动批次A，确认既有报告字段、默认v3与Supervisor消费者，以及必须保留的自定义应用和旧执行边界。
3. 建立最小公开CLI回归与相关反例，再修改报告接收与推进；已有完成执行不重跑，旧在途执行可核对。
4. 完成本批定向测试、构建与生成新鲜度检查，分开报告平台/模型缺口；随后推进B、C，N08保留为独立恢复语义决定。

本文保留实施前的调查与验收要求；当前实现、实测结果和未覆盖边界见[实施记录](2026-11-09-native-agent-runtime-implementation.zh.md)。
