第3轮的 `reviewInput` 是领取响应中的只读展示，不进入 Action 输入或 Run，也不增加推进状态。它携带原始请求、全部验收项、现有检查、需求原文和实际变更文本，并按目录层级补充实际存在的 `AGENTS.md`。正文只出现一份；状态查询和提交完成后的响应不重复附带正文。未修改调用方不保证全部包含，由审查者按具体疑问补读。

每个文本文件显示实际读取字节的摘要；变更文件的字节或执行权限与观察结果不符时，材料标记不完整，不交付该文件的旧正文。读取使用现有受保护路径，二进制、删除、子仓库和已声明生成物提供引用。没有新增项目预算、语言白名单或自动通过。只有实际领取者与登记的原审查会话一致，且存在有效相邻候选差异时，才交付增量范围；其他会话读取全量变化。验收提交仍执行原有候选、授权和证据核对。

## 已观察到的问题

2026-11-04 的 DeepSeek 对照中，bugfree 与 standard 原题评分都是 10/14，Verify 分别约 19 分 45 秒和 3 分 4 秒。原始运行与统计口径见[数据集对照记录](2026-11-04-dataset-comparison-integrity.zh.md#授权重跑的实际结果)。保留这轮失败结果，不将它解释成性能收益。

bugfree 的独立审查重新运行了已有的 13 项测试，又编写 26 个额外探针。第一次提交约在 14:44:30 UTC 被“复核通过的编辑尚未应用”拒绝；最后到 14:59:27 才提交成功。正式检查收据的 320ms 不包含审查者自行执行的命令，因此不能把 320ms 当作全部检查成本。

这轮还暴露了语义审查的不足：审查者接受了 Builder 对断线后行为的设计前提，两组均漏掉相同的原题约定。原始请求已交付审查者，不能把问题归结为它完全没收到指令。

## 已复现的 Runtime 缺陷

最小项目中保留一个经过 `non-behavioral` 判断、但尚未应用的正式文档编辑。文件仍是已批准原文。旧 `edit-review prepare-applied` 没有发现当前文档差异，便只查询当前候选的编辑范围；正式文档提案属于 Shape 批准范围，因此返回空列表。最终验收检查两个范围，又会拒绝该提案。准备和提交看到的待办不一致。

先增加测试再修改实现，原断言得到空列表而失败；修正后通过。准备命令现在与最终验收查询相同范围。bugfree 的续行在正式编辑尚待处理时先交给协调者，不同时提供新的 Verifier 领取模板。最终验收仍拒绝未处理提案，错误中列出文件与提案摘要。明确丢弃未应用的编辑后，同一个 Run 可以继续验收；不会自动丢弃、代替用户批准或解除候选绑定。

回归入口：`test/domains/comet-native/native-verifier-context.test.ts` 中 `surfaces an unapplied formal edit before dispatching a bugfree verifier through runtime` 与 `through public-cli`。测试同时检查准备结果、派发状态、提前提交被拒绝、原文件未改写和合法恢复后的通过。公开 CLI 测试中，历史 Builder、User 与 Verifier 身份均由夹具模拟；它不是模型效果证据。

## 审查指令调整

Runtime 的任务包要求先从原始请求、现有接口和必要调用关系判断应有行为，再核对 Spec 与最终实现。Builder 的设计取舍及新增测试同样是审查对象。交接指令要求不附加 Builder 自评，也不把设计决定改写成预期行为。

已有检查适用时直接复用。能从代码和已有证据解决的问题不额外写探针或重复执行；有无法解决的具体疑问时，由审查者决定补读或补查，不增加疑问表、固定测试轮次或第二个审查 Agent。明确要求的检查保持有效。

遇到编辑、批准或候选绑定问题时，审查者将原错误与恢复信息交回协调者。只读审查不负责修复流程记录。领取响应复用本次观察已经准备的审查输入，避免在同一响应中再次遍历项目；不跨命令缓存输入，也不改变提交时的新鲜度检查。

这些是待实评的调整，不能仅凭指令内容宣称模型已经遵守或正确率得到保持。

## 第3轮模型结果：校准预期中的遗漏

R4 使用冻结产品快照 `sha256:38633ae3a9ab4ce975a3d2e1f208b291b27586feffe91403d06b13b402eaf44b`，任务清单另行固定。正确候选标签沿用准备时的假设，不代表已经穷尽业务边界。两组使用相同业务字节、CC Switch DeepSeek 配置和公开 `comet eval` 入口；模型只做独立审查，历史 Builder/User 仍明确模拟。

第一对中，standard Run `comet-eval-77857be4-dc3d-467e-82cd-4ffffbfbc392` 原评分9/9，Runtime 判 pass；bugfree Run `comet-eval-c2342a42-fda8-4e3c-85f7-046cabdb48d4` 原评分因预期 pass 与实际 fail 不符而失败。原报告保留，不修改评分器后冒充原运行通过。

bugfree 指出的 A2 问题确实存在：未监视的 `get('a').incr('b')` 在首个 GET 断线时，INCR 尚未发送，程序却检查整个剩余队列，把尚未执行的 INCR 也当成结果未知，直接抛出 WatchError。独立控制器复现得到仅一次 GET 调用、零次重连，而请求要求安全重试。本机记录为 `candidate-a-additional-defect.json`。因此这次 fail 不能记作误报；standard 的 pass 漏掉了这个边界，原候选也不能继续称作已知正确候选。后续正例须修正该实现，并保留本次原字节、原预期和复现。

这对模型执行为 standard 192.076秒、bugfree 312.438秒，含缓存读取 token 分别1,146,478与2,506,507，工具调用34与40次。bugfree 没有额外运行业务检查，但反复定位长 JSON 中的模板、查询结果字段及 Runtime 解析源码，还重新核对文件和日志摘要。除了语义审查的额外发现，协议查找也确有可压缩成本；本轮仍未达到耗时与 token 目标。

上述耗时包含这次模型调用中的确定性历史准备，不能写成纯 Verify 阶段计时。错误 WATCH 候选的两组仍按原计划继续，结果单独记录，不以正例预期错误为由删除已有尝试。

随后核对错误候选的实际产物时发现，Run `comet-eval-45abd0ed-4e2a-40f6-a6d6-00e479920560` 实际使用的仍是 A 候选字节，镜像身份也与 A 相同。预期 B 摘要为 `4ce0e44519e27b7bb3c7df7db6eccedbd4fbc6a5fb4f109c9b592222ee9c6cf1`，实际为 A 的 `f911bb81da415e9361cc259800fbb52e6b47e148a04526d6875432dd250726f8`。因此不能将此运行判为 WATCH 漏检，它没有执行到计划中的错误候选。原始 fail 评分保留，性能和正确率对照中标为输入不匹配。它实际审查 A 后给出 pass，仍漏掉 A2 的安全重试问题。

普通组 Run `comet-eval-9e17abcb-b452-4b0d-b7e2-0338f7b07d65` 已启动；发现同样的镜像污染后，通过 Eval 管理 API 请求停止，返回 executionStatus: stopped，实验容器查询为空。该样本保留为停止的无效输入样本，不能用于普通组正确率或配对耗时。

根因是普通 authored 任务的镜像键只包含 Dockerfile 和少数依赖清单，忽略 Dockerfile COPY 的候选、初始化脚本等环境文件。两个任务 Dockerfile 相同便复用了旧镜像。第4轮在拷贝任务环境时，对实际拷贝的路径、权限与文件字节计算摘要，并将摘要作为注释追加到工作副本 Dockerfile；Dockerfile 的执行语义和源夹具不变，既有镜像键自动绑定这些输入。后装的 Skill、控制器和结果不参与摘要。回归通过相同公开 setup/build-hash 路径，在旧代码得到相同镜像键而失败；新代码随候选变化更新键，增加控制器文件则保持键。实际容器与后续模型输入仍需分别验证。

来源登记：`report:2026-11-05-authored-eval-image-cache`，案例 `eval-authored-environment-image-identity`。这次修正和后续夹具修订计入第4轮，不重置用户规定的10轮上限。
