## #552 的复现尝试与边界

1. 物化既有 0.5.2 归档准备样本后直接调用旧 CLI，先遇到旧候选输入漂移，尚未到报告中的 Specs 写入阶段。这是不同失败，不算复现 #552。
2. 使用真正 npm 0.5.2 工厂、SDK 和执行器，从新临时项目推进完整流程。用户批准与 Agent 报告明确标注 SIMULATED，状态推进、Git、Specs 写入和搬迁为真实实现；不运行模型或 Eval。
3. Windows Native@1 的非空受管检查尝试停在 `verify.checks / EXECUTION_UNKNOWN`，未达到归档，不算通过；现场保留。改用空检查计划后 Native@1、Native@3 的 docs/current create Spec 归档均成功。这里没有将失败检查改写为成功，而是另建了明确没有检查计划的独立样本。
4. WSL 使用原有真实无副作用 Node 检查的 Native@1 工厂流程，也完成 create Spec 的应用与归档，没有出现报告错误。控制器和样本保存在 `/tmp/comet-552-old/`。
5. 当前分支既有 `native-published-archive-upgrade.test.ts` 的四阶段测试通过。它们保留原 0.5.2 Run/批准及已完成副作用；不证明原报告已经自然复现。
6. 新增测试通过真实当前执行器创建 canonical Spec，再注入错误的结果字段，实际触发 `OUTCOME_REJECTED`。通过公开 `archive --recover` 补记原 Action，执行返回的普通 `archive` 完成搬迁，随后再次 `--recover`。检查 canonical 内容、inode、修改时间、原 claim、批准与拒收记录全部保留，只有一次 archive.execute。

因此 #552 当前状态为：053 相关路径回归通过，原始 0.5.2 触发条件尚缺证据。后续由维护者取得报告现场的脱敏 Run、事务和项目/Git 布局后继续精确复现；本次没有更改 Issue 状态，也没有用注入的传输失败声称原问题已修复。
