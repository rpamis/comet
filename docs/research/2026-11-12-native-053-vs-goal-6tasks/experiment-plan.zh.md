## 执行

直接调用公开内置 `comet eval --dataset ... --task ... --dataset-treatment native|goal --count 3 --agent claude-code --model deepseek-flash[1M]`。保留原题、模型与评分预算、数据集版本和评分器；不另写评分规则，补评分控制器仍调用同一内置评分器。用户随后表示最好不要有时间限制；本轮后续启动设置 `COMET_EVAL_BUILD_TIMEOUT_SECONDS=0`，已进入模型的 Goal 结果继续保留。两组均不额外注入领域 Skills。

此选项只取消镜像构建总时限，模型仍受固定计划中的逐题执行预算约束，例如 SkillsBench 的 `paratransit-routing` 为 3600 秒。已出现的执行超时原样记录，不描述为正常结束，也不未经授权重跑；本轮不能描述为模型完全不限时。

模型与路由见 `model-config.json`。主模型为 `deepseek-flash[1M]`，两组 Haiku 路由统一到主模型，其余路由相同。Claude Code 固定 2.1.318，模型容器 Node 固定 22.23.5；关闭可选 LLM Judge。凭据仅在内存与进程环境中使用。

每个 Run 使用 1 个 worker，总模型并发上限 4。先运行镜像已就绪的题目；SkillsBench 因原题镜像使用不同普通用户 UID，按相同 UID 分批调用同一公开命令。其他 Run 结束后，利用空余并发位启动 PDF 题目，选题和每题轮次不变。控制器与对应模型用户 UID 一致，模型使用镜像原有非 root 用户，工作区保留私有目录权限。隔离恢复控制器的冻结资产副本补齐了所有者写入位，以便现有安装器覆盖生成的 Skill 入口；文件内容不变。没有修改 Windows 安全设置或全局网络规则。

两组的原题内容、评分器和模型配置分别核对一致。模型耗时不含镜像准备与退出后评分；不同时间开始的任务保留实际调度记录，不把环境准备速度计入模型效率。

## Native 版本与评分恢复

Native 使用本轮启动前冻结的 0.5.3 编译包，不随共享工作区 HEAD 变化。2026-11-12 在两个运行中的 Native 容器内执行 CLI，均返回 `0.5.3`；`dist/`、`bin/`、`assets/` 共 841 个文件与控制器冻结包逐文件一致。运行期间合入的 `00956d7c`（移除 Native / Classic 文件大小限制）不包含在本轮候选中，因此不能将本轮结果描述为该提交或最新 HEAD 的评估。

各 Run 的 `launch.commit` 记录控制器启动时共享工作区的 HEAD，不表示模型内的 Native 包随该提交更新。候选版本以冻结包身份、`currentCometBuild` 与容器文件核对为准；19次 Native 真实尝试（含被替代的环境中断）均保存了模型输出，记录中没有调用本地 `comet-native*.mjs` Runtime 的命令。

安装的 Native Skill 正文及 references 与冻结源一致，但原批次的本地脚本副本来自共享工作区。缓存题第3次曾用 `grep` 查看这些 `.mjs` 文件中的 Spec 路径代码，未执行它们；保存副本中的14个脚本与冻结 CLI 资产不同。因此本轮能确认实际执行的 Native CLI 被冻结，不能声称模型可读的每个上下文文件都与冻结包逐字一致。该上下文差异保留为实验限制，不据此删除或重跑已经得到的有效低分。

早先启动的 WorkBuddy Goal 和 SkillsBench 非 PDF Goal 在模型运行期间遇到评估适配器更新，原固定计划在评分阶段拒绝了不匹配的适配器。原失败报告、模型输出及候选均保留。恢复评分时使用与各 Run 原计划校验值完全匹配的冻结适配器，调用内置 `DatasetTask.validate_dataset`，继续执行原题、原评分器、输入完整性与参考文件访问检查；不修改候选、不再次调用模型，也不改写原报告。补评分单独保存来源和结果。后续 Native 与 PDF Goal 从更新后的适配器启动。适配器改动涉及镜像构建预算及构建锁等待，不涉及原题、Agent 交互协议或评分规则。

部分 Native 样本在评分副本清理阶段失败，未形成完整报告。评分容器创建了其他用户所有的文件；以原控制器 UID 1000 清理实际副本时复现 `PermissionError: uv`，WorkBuddy 缓存题的原始失败栈也记录了 `__pycache__` 清理错误。模型原候选和原始输出另行保存，使用同一内置评分器补评分，不重跑模型，不伪造原始退出码或未执行的流程检查。制造业分类三次补评分均为0；固定版 uv 下载曾出现的 TLS EOF 失败记录仍保留。

WorkBuddy Native 缓存题第1次、Goal PDF题第1次在模型启动前失败，均仅补齐原位置。Native 留存题第2次因评估器存储扫描报错，以退出码122中断；旧候选原题满分仍保留，按用户授权替换该环境无效运行。在隔离的内置评估副本中修正临时子目录消失的扫描处理，保留真实权限错误与根目录缺失的阻断，并通过6项安装、用例选择及存储定向检查。替代运行原题满分，整份报告检查通过。新增的这次替代运行单独记录实际消耗，不将实际37次运行写成只有36次；其余准备失败均无模型调用。

## 指标

原题 reward 为 1.0 才记为完整成功，部分 reward 原样保留。每数据集每组有 3 题 / 9 次：pass@1 为 9 次的完整成功率；pass@3 为每题 3 次至少 1 次成功的题目比例；pass^3 为 3 次均成功的题目比例。Native 流程完成与原题成功单列。

原题得分与执行结束分开统计。超时运行的留存候选如果通过相同输入、参考材料访问与原题评分检查，原题满分仍计入原题 pass@k；超时标记、原始失败报告和执行退出码保留，不能描述为正常完成。内置 Eval 质量筛选后的结果另列，不用其超时排除标记将已经确认的原题满分改成答错或抹去。

缺失、评分错误或未启动模型的环境失败记为未知，保留固定分母与上下界，不能当作模型答错。有效低分必须保留。两个数据集分别报告；此六题小样本不代表完整官方榜单。

Token 和费用仅报告可观测遥测；CLI 估价不是 DeepSeek 账单。效率同时展示全部尝试与双方成功配对，不只挑选有利样本。
