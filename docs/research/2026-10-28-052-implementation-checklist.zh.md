# 052 实施清单与验收场景

日期：2026-10-28。准备基线：`052` 与本地 `origin/master` 均为 `35c9860b77b42bafa0c2d80d8d695889f888a924`，版本 `0.5.1`。本清单整理已确认的产品方向，供后续开工使用；本轮只整理文档，没有开始产品实现。

调查依据见[编辑后续行复核](2026-10-28-052-edit-continuation-review.zh.md)和[核心流程性能测量](2026-10-28-052-core-workflow-performance.zh.md)。以下为最终实施范围；其中的预期和验收条件均不是已经实现的结果。

## 核心约定

Runtime 记录文件变化、提供原始差异、保存判断与实际执行结果，并推进流程。内容含义、影响范围、检查选择与证据是否仍适用，交给当前 Agent 判断。内容检测不依赖用户代码的语言、语法解析、AST、注释识别或编译；Runtime 自身的状态文件和协议解析继续承担存储职责。

判断融入当前任务，连续编辑在下一次推进时合并处理。已有授权覆盖的工作直接继续；只有需求、验收结论或授权范围确实变化，且现有决定未覆盖时，才请求相应决定。文件字节变化本身不触发整组证据作废或恢复流程。

## 需要改什么

| 编号 | 改动                                             | 预期行为                                                                                                                                    | 主要落点                                                                             |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 1    | 提供统一的原始变化观察，将内容语义判断交给 Agent | 任意语言、文档和未知扩展名都能提供变化；语言工具链缺失不阻塞检测；原始文件和用户编辑完整保留                                                | Native 输入与候选观察、Classic 检查快照、共享变化记录                                |
| 2    | 把变化判断接入现有 Agent 和 continuation         | 当前 Agent 读取差异，判断哪些决定和检查仍适用；记录对应输入版本与处理结果；一次推进合并处理此前编辑                                         | Native/Classic 的输出、续行、编辑复核及内置 Skill                                    |
| 3    | 按影响更新证据和检查                             | 保留未受影响的需求批准、验收结果与检查；只执行 Agent 判断需要补充的检查；旧记录保留原始执行身份                                             | Native SDK checks/application/archive；Classic SDK check/archive-preflight           |
| 4    | 补齐各阶段的原地续行                             | Native Build 修改正式说明不再因没有 Verify 候选而转需求修订；Classic 正式文档普通编辑不机械要求重新批准；Verify、待归档阶段同样保留有效工作 | Native requirements/edit-review/continuation；Classic revision-readiness/application |
| 5    | 区分内容变化与 Git 身份变化                      | 相同内容仅暂存、取消暂存或空提交，不单凭 Git 状态重建实现候选；明确依赖 Git 的检查和交付身份仍按实际变化处理                                | Native 候选/输入绑定；Native/Classic 交付与归档核对                                  |
| 6    | 缩短必要核对的执行成本                           | 同一观察阶段共享输入和路径信息，减少重复全树扫描、根目录及祖先链读取、Git 查询和交付路径查找；执行前后保留各自的新鲜观察                    | Native 输入采样；共享受保护路径；Classic 快照和交付路径索引；SDK 输出装配            |
| 7    | 同步 Skill、公开 CLI、生成资产和回归记录         | Agent 能直接消费返回的下一步；说明与真实能力一致；现有用户流程通过公开入口保持可完成                                                        | 中文/英文内置 Skill、Runtime 构建、相关契约与回归用例、发布说明                      |

第 1 项逐步替换现有按内容语法或特定命令判定影响的路径，不再扩展语言适配表。第 2 项复用既有 Run、Action 和 continuation，不为每次编辑新建独立审查流程。第 3 项由 Agent 作出影响判断，Runtime 核对判断对应的输入和实际执行记录，不另用编译结果证明 Agent 的判断。

## 实施顺序

1. **先补最小复现与验收用例，再接通变化记录和 Agent 判断。** 先固定当前已观察到的行为和禁止结果，再完成第 1、2 项。确认输入版本与判断关联清楚，连续编辑能合并处理。
2. **接通 Native 与 Classic 的证据更新、阶段续行和 Git 状态处理。** 完成第 3～5 项，保留各自状态机，覆盖 Build、Verify、已批准待归档，以及 Classic 已批准 Design。
3. **在新流程上减少重复工作。** 完成第 6 项。使用已有采样定位必要核对的成本，避免为即将淘汰的语义检测路径继续做微优化。
4. **同步产品入口并验收。** 第 7 项随相关实现推进：先中文 Skill，按仓库规则确认并同步英文；构建对应 Native、Classic、Entry Runtime 并验证生成产物。全部交付项完成后再汇总结果。

普通用户编辑和结构损坏分别处理。状态或产物实际缺失时诊断具体问题；不能通过恢复旧文档、覆盖用户代码或重建整个 change 来完成普通编辑续行。

## 验收场景

下表编号只用于本清单；实施时按仓库要求登记稳定的回归 case ID 和精确测试选择器。各场景按涉及阶段选择代表路径，不机械地把每一场景与所有阶段做全排列。

| 编号 | 场景                                                                                   | 必须得到的结果                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1   | 多语言混合、未知扩展名、纯文档项目；环境不提供项目编译器                               | Runtime 提供完整原始变化，不因语言不支持而阻塞；检测路径不加载用户代码语言解析器或调用编译器。Agent 按任务自行选择的实际验证另行记录              |
| A2   | Classic 已批准设计末尾加空行；Native Build 给正式 brief 补说明性注释                   | 当前 Agent 判断未改变需求或技术决定后，在原阶段、原 Run 继续；不额外创建审查 Agent，不要求再次批准或走需求修订                                    |
| A3   | Verify 或已批准待归档时修改 README、使用说明；修改确实被某条文档检查覆盖的内容作为对照 | Agent 判断无关的检查执行次数为 0，未受影响验收和批准保留；对照场景只补相关文档检查，用户修改进入最终交付                                          |
| A4   | 修改模块 A，模块 B 与其检查不受影响；或只调整注释但该注释影响实际行为                  | 由 Agent 判断实际影响，不按后缀或注释语法预判；执行受影响检查，B 的有效检查不重跑；保留原需求确认与已完成工作                                     |
| A5   | 修改目标、验收条件或技术方案，现有授权未覆盖                                           | Agent 说明实际差异，只请求相关决定；未获决定不推进受影响工作；已完成且仍有效的工作保留，不重新收集整个需求                                        |
| A6   | 连续编辑并保存 10 次，再推进一次；重复 status/next；以相同字节重写文件                 | 待处理变化一次汇总；读取状态和相同内容重写不重复触发审查；普通编辑新增用户确认 0 次，额外独立审查 Agent 0 个                                      |
| A7   | Agent 看过差异后、提交判断前，文件再次发生变化                                         | 旧判断不能覆盖新增内容；返回尚未处理的变化，由当前 Agent 补判断；原有效工作保留，不重开整个流程                                                   |
| A8   | 检查已有成功，之后相关检查失败或中断；另一条检查仍有效                                 | 新失败或中断不能被旧成功遮蔽；Agent 的复用决定不改写真实检查结果；未受影响证据仍可保留                                                            |
| A9   | 相同内容仅暂存、取消暂存、空提交；另设明确依赖 Git 状态的检查                          | 普通实现候选不因元数据变化被整体作废；Agent 对明确依赖 Git 的检查选择必要处理；CI、Review 与交付记录仍绑定实际提交                                |
| A10  | 编辑后中断再继续；已完成检查、提交或归档后发生中断                                     | 继续同一 Run，用户文件、已完成工作和有效决定保留；已完成副作用不重复执行；结果不明时先核对事实，不盲目重放                                        |
| A11  | 普通源码/文档修改与真正缺失 Runtime 状态分别测试                                       | 前者不进入结构修复；后者定位实际缺失，并保留用户成果。现有路径替换和读取不完整的相关拒绝行为保持有效                                              |
| A12  | 固定 fixture 对照旧基线与实现后完整推进、编辑后续行、大目录与多次 Action               | 同时比较端到端耗时、命令/模型调用数、用户确认数、检查执行数、Git/文件操作数；正常路径不出现可重复的性能回退，目标热点的重复工作和对应中位耗时下降 |

A2、A3、A4 的语义判断需要真实模型证据。A7、A8 的状态和结果关联可以先用确定性测试覆盖，再通过公开 CLI 验证整条路径。A6 记录检测额外增加的调用，不把原流程本来就需要的 Builder、Verifier 算成新增审查。

## 完成标准

- **流程体验：** Agent 判断无关的编辑，新增用户确认次数为 0、未受影响检查执行次数为 0、额外独立审查 Agent 数为 0；文件与工作保留。只有受影响且确有必要的步骤重新执行。
- **运行时契约：** 定向测试覆盖完整变化观察、判断对应的输入、选择性更新、真实检查结果、状态续行与中断恢复。涉及用户问题的行为按仓库 badcase 规则保留来源、逐行为映射和旧/新证据。
- **公开入口：** 构建后的 Native 与 Classic CLI 在临时项目完成正常流程和编辑后续行。安装与路由改变时补对应安装包测试；Hook 改变时补真实平台入口验收，分别记录结果。
- **Agent 行为：** 真实模型 Eval 验证语言无关的内容判断、变化影响、检查选择和授权边界；确定性测试不能代替这一层。只重跑失败或被改动影响的用例，保留仍有效的通过证据。
- **性能：** 对同机、同 fixture、相同采样方式的原基线和当前实现作比较，报告中位数、样本范围及完整性。先确认成本变化来自流程减少还是必要核对提速，不提前承诺没有测量依据的毫秒数或百分比。
- **交付记录：** 分开列出源码、生成 Runtime、公开 CLI、安装包、平台 Hook、模型 Eval 的实际结果与未执行项；不能用其中一层替代另一层。日常改动不默认运行全量测试。

开工时重新核对 master 版本。若仍为 `0.5.1`，本轮用户可见变更统一进入 `0.5.2`，不为中间迭代另起版本；Skill 内容待中英文同步后再写英文 Changelog。本轮不修改版本或 Changelog。
