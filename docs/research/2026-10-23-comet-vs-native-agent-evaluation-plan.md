# Comet 相对原生 Agent 的收益评估方案

日期：2026-10-23。状态：研究与实验设计；尚未实施运行器改造，也未运行模型实验。基线为 `051` 的 `aeb1a659`。本文提出的实验组名称不是现有 CLI 参数。

## 要回答的问题

在固定任务分布、Agent 版本、主模型与推理配置、工具权限和总预算后，安装并使用 Comet 能否提高真实任务完成率，或在质量保持时降低成本、耗时及人工干预？

结论允许 Comet 有收益、无明显收益或退化。结论应注明任务、版本和预算，不能从局部实验推出“Comet 普遍优于 Codex / Claude Code”。第一轮比较的是正式安装后的 Skill、Runtime、Guard 及必要依赖的整体增量，不把其效果全部归因于 SKILL.md 文本。

## 实验组

每个平台独立比较；Codex 和 Claude Code 可以使用各自适合的模型，但同个平台的配对组必须使用相同主模型 ID、推理配置和原生能力。

| 组  | 配置                             | 目的                                                           |
| --- | -------------------------------- | -------------------------------------------------------------- |
| A   | 原生 Agent + 原生 Goal，无 Comet | 强原生基线，保留平台自带规划、工具及子代理能力。               |
| B   | 与 A 相同 + Comet Native         | 测量 Native 的增量。                                           |
| C   | 与 A 相同 + Comet Classic        | 测量 Classic 的增量；预先固定 full / hotfix / tweak 选择规则。 |

各组使用相同需求正文、项目规则和可见输入；B/C 额外给出使用对应 Comet 工作流的调用指令。记录 Skill 是否真实加载，未加载、安装失败及运行失败保留在所属组的整体结果中，另作归因。以后可以另测自动发现率，但不与显式使用效果混算。

先验证 Goal 与 Comet 能共同工作；若不能，报告兼容性限制。额外运行“各产品推荐配置”时单列，不能冒充保持 Goal 不变的增量实验。需要区分 Goal 与 Comet 各自贡献时，再加入两者开 / 关的四组实验。

首轮使用干净记忆状态，暂停可选的跨任务个人记忆与项目知识学习，并保持平台记忆策略一致。记忆收益以后单独实验，避免与流程收益混合。

## 任务与独立验收

先从至少两个非 Comet 仓库选 6 个试跑任务，包含普通任务和流程可能有帮助的任务。以下为任务类型，不是已制作的数据集。

| 类型       | 示例                                 | 外部验收                               |
| ---------- | ------------------------------------ | -------------------------------------- |
| 小修复     | 修复输入解析的边界错误               | 公开行为与隐藏边界用例、既有回归。     |
| 功能增加   | 新增 API / CLI 参数和错误处理        | 全部需求条件与兼容行为。               |
| 重构       | 拆分模块、保持公开接口               | 兼容测试、依赖与行为约束。             |
| 跨模块功能 | 修改数据层、接口与界面               | 集成与端到端行为。                     |
| 需求修订   | 在预先规定的共同检查点加入同一条需求 | 最终需求覆盖、返工和人工交互。         |
| 中断恢复   | 在定义好的事件点终止并恢复执行       | 最终任务正确、无重复副作用、恢复成本。 |

正式集扩大到更多仓库和未参与调优的任务。使用公共题时冻结版本并核对许可证、题意与测试一致性；同时保留新任务，记录公开题答案泄漏或训练污染的限制。不得按哪组获胜决定保留哪些任务。

每个任务必须先固定：仓库 commit、需求、公开测试、隐藏验收、原有回归、边界约束、运行资源、用户应答规则、停止条件。人工确认已知正确实现能通过，并用明显错误实现检查验证器不会无条件放行。

隐藏测试与参考解答由外部评估器保管，不出现在任何被测 Agent 的可读工作区、历史或 Skill 中。Agent 结束后提取产物，在干净环境独立运行验收。可见测试允许 Agent 使用；隐藏验收结果不在当次修复循环中反馈。

主判定为需求行为、原有回归及明确约束是否满足。Comet 的文档、阶段、状态机和归档完成单独作为诊断指标；不要求原生组产出 Comet 文件，也不把 Goal / Runtime 自报完成当作任务成功。

主表至少报告：

- 严格任务成功率：一项关键需求不满足即未完整成功；同时报告各验收项通过情况。
- 总成本、输入 / 输出 token、耗时；失败运行也计入。
- 自称完成但外部验收未通过的比例。
- 人工提问、纠正、接管次数；恢复类任务另列恢复结果和重复操作。

同一平台内设置相同外部总时限与成本或 token 上限，超限保留为未完成。主 Agent、子代理、Comet 验证 Agent、Goal 评估模型、运行中重试都计入执行预算；共用的外部判分成本另列。缺失费用或轨迹标记未知，不按零计。跨恢复调用由外部实验管理器累计，不能只依赖一次 CLI 调用的计数。

自动用户只能按预先保存的业务事实和授权策略回答，不提供解法、隐藏测试信息或无限“继续”指导。各组可提出不同问题，但获得信息的规则与上限相同，交互本身计入结果。

## 重复、统计与结论

对相同任务进行配对，随机交错组的运行顺序；每次使用新工作区、会话和独立状态。固定并记录 Agent / Comet / 依赖版本，控制网络、并行数与执行资源。

试跑规模：6 任务 × A/B 两组 × 每组 2 次 = 24 次模型执行，先选一个平台。Claude Code 有明确的非交互 Goal 入口，可作为首个运行器候选；Codex Goal 适配确认后重复同一协议。试跑只用于验证公平性、题目难度、失败模式和单次费用，不用于宣传胜率。

正式阶段可先准备每个平台 24 个未参与调优的任务，A/B/C 各重复 3 次，即 216 次执行；两平台合计 432 次。这是预算规划示例，正式样本量须依据试跑变异、希望识别的最小收益与预算决定，不能保证这些数量足以证明优势。

主分析先求每个任务的重复运行成功率，再比较配对差值。置信区间按任务成组重采样；多个任务来自同仓库时考虑仓库相关性。不把同题重复运行全部当作独立新题。预先确定主指标、值得采用的最小差异、样本量和异常处理规则，不能看到结果后改变口径或不断加样直到显著。

超时、安装失败、不可完成均保留；确认是平台服务故障时，按预先定义的对称重试和敏感性分析处理。保留原始结果、排除理由与分母。先看全体运行质量与成本，再辅以双方都成功任务的效率；后者不能替代主结果。

可用结论模板（不是实测结果）：

> 在指定 Agent / 模型版本、任务集和预算下，Comet Native 相对原生 Goal 的任务成功率变化为 X 个百分点，配对 95% 区间为 [L, U]；成本变化 Y，人工纠正变化 Z。收益集中于哪些任务，哪些任务无收益或退化。

如果区间跨零或有效任务不足，报告证据不足。若质量提高但耗时和成本增加，明确展示取舍。结果不能自动外推到新模型、其他任务和更长周期。

## 当前 Eval 可以复用什么

静态核对发现现有 `CONTROL`、`COMET_NATIVE_SDK_CURRENT` 和 `COMET_CLASSIC_DOCS_LAYOUT` 可作为配置起点；严格配对、执行指纹、轨迹、业务 / 流程评分拆分也已具备。

以下问题必须在用于产品效果对比前处理，本轮未修改代码或实跑复现：

1. `eval/local/tests/conftest.py` 的 `_build_eval_claude_md` 对 `comet-workflow` profile 无条件加入要求调用 `/comet` 的规则。规则位于 `eval/local/skills/benchmarks/dependency/claude-md/comet-workflow/CLAUDE.md`，会影响原生对照组。
2. 带 `.include-current-comet-cli` 的任务会拷入 `_eval_current_comet` 和 assets。仅把 `CONTROL.skills` 设为空，不足以证明该组看不到 Comet 内容；需审计实际文件与环境。
3. `eval/local/tasks/comet-native-workflow/instruction.md` 是 SDK 流程契约任务，要求特定文档和故意失败后恢复。它用于验证 Comet 自身正确性，不能直接当成中性业务能力题。
4. `eval/scaffold/shell/run-claude-loop.sh` 当前启动 `codex exec/resume` 和普通 `claude -p`，未见真实 Goal 激活路径。需要验证启动、续行、停止、恢复及外部预算控制，不能把模拟用户循环称为原生 Goal。
5. profile 的默认交互方式及完成判断不同；必须固定共同用户协议与业务终点。`aligned_comparison.py` 现有严格配对可保留，主成功率应使用共同业务验收，流程诊断另列。

建议复用当前 Eval 的存储和报告，增加中性业务实验协议、真实 Goal 适配和强原生配置。完成环境隔离、隐藏测试边界、预算和评分的本地检查后，先估算试跑费用，再执行模型实验。
