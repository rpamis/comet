# Issue #543：环境感知恢复确认

来源：[Issue #543](https://github.com/rpamis/comet/issues/543)。实施基线为 `203532ba348554f988dd41513b9ce4c95779959f`（053）；master 为 `356114427f28e2fa5bcb9e0242d2c75347693523`、0.5.2。当前版本保持 0.5.3。

## 复现与根因

在隔离项目中通过正式 API 创建 Native SDK change，或通过 Classic CLI 初始化 SDK change，再写入缓存过期行为的任务描述。Native 项目保留原 selection。公开 CLI 收到 `Adjust cache expiration behavior` 时，两个 workflow 都返回 `auto_resume` 和永久入口；新增的 `ask_user` 断言在旧构建上失败。

源码入口的两项对应断言也在修改前失败。记录位于本地 `.tmp/issue543/red-source.json`、`.tmp/issue543/red-public-cli.json`。这些是确定性临时项目验证，没有模拟真实模型答复，也没有在报告方工程操作。

共享入口此前直接消费单一语义相关目标的自动恢复结论。项目引导据此加载 Skill；共享 Rule 又依 selection 指示恢复，缺少“本次请求已确认进入”的条件。仅修改探针不能使两套指引保持一致。

## 实现边界

- 复用 `ask_user`、现有请求意图和 `already_in_comet_flow`；不新增项目配置、会话登记、磁盘确认记录或扫描。
- 对两个 workflow 的既有自动恢复结果统一处理。明确要求继续、验证、归档或提交指定 change（含明确指向当前 change）时保留原入口；只说“继续”、只提名称、仅语义相关或只有项目 selection 时先确认。
- 已在流程中的会话维持原快速返回，普通继续和上下文恢复不重复探测。关闭探针或无 change 的原路径不变。
- 用户确认后，Agent 直接加载返回的 `skill`，不再扫描；拒绝不改变 change、selection、原批准或 Guard。原有歧义、状态错误和 Archive 等决定仍按原协议处理，确认恢复不批准业务步骤。
- 项目引导和 Rule 使用同一确认语义；Rule 的所有权读取仍用于归属与写入约束。
