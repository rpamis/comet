# Runtime 下一轮减负与 PID 退役

来源：`report:2026-11-09-runtime-pid-removal`。用户授权实施此前六项减负，并明确要求移除 PID 机制。基线为 `053` 的 `7f016b28`；在临时 detached checkout 实施，最终合回 `053`，不新增长期分支。

移除的是 Comet 的 PID 身份、存活探测、持久绑定与恢复依赖。当前执行器可以停止自己持有的 ChildProcess；这不代表通过 PID 推断历史命令是否完成。中断后仍须依据原 Action、已提交结果及实际文件/Git 状态恢复，不能凭空认定未知副作用成功或重新执行。

## 实施清单

- [x] 共用锁和 Native 锁撤下 PID/创建身份、探测器、协调票据及等待 PID 过期；复用现有 SQLite 事务互斥，进程退出自动释放。
- [x] Native/Classic 检查及恢复不持久绑定 PID；历史字段兼容读取但不参与推进或接管。
- [x] 命令内复用已准备 Runtime/Change 路径，普通内部读写不重复做祖先全链遍历和旧布局迁移。
- [x] 新内置 Classic 普通检查采用平台报告；保留批准、完整验收、真实失败、用户接受和 Git 交付。
- [x] 合并纯内部投影与结果副本，保留实际执行、Agent/用户交接和终态恢复边界。
- [x] Native 高层任务直接投影业务包，归档预检计算一次，保留实际写入事务。
- [x] 当前归属发现与无关历史恢复隔离，中性文档不被旧归档投影故障阻塞。
- [x] 定向源码/生成 CLI、旧 Run 与恢复、性能对照、独立 Review 和 Changelog；失败与未覆盖范围分别记录。

交付要求：提交后快进合回 `053` 并推送，移除本轮临时 checkout，不新建长期分支；实际交付结果以 Git 状态为准。

## 已取得的证据

共用锁的首个回归在旧代码因记录含 PID 而失败。新实现的并行写互斥、真实子进程退出后无 doctor 重新加锁已通过。Native 锁没有 PID/创建身份或进程探测，仍拒绝同锁的第二写入者；公开 Native new 已通过。

实验中发现 Windows SQLite journal 不能直接使用长路径，已通过平台的 namespaced path 传入；SDK Run 严格目录清单同步识别锁数据库及其 SQLite 临时文件。未通过删除旧断言掩盖这些失败。

原 PID、跨主机身份及协调票据断言已完整归档和迁移，详见 [PID 退役与测试迁移](2026-11-09-runtime-pid-retirement.zh.md)。独立 Standards/Spec Review 均认可迁移：21 份旧测试正文与基线逐字节一致，六个旧 v1 夹具的 803 个 expect 断言未减少。11 条迁移保留原来源和迁移链，新增四条 badcase 分别验证锁、真实停止与旧收据、Classic v2 报告及无归属中性文档。

## 行为和兼容范围

新内置 Classic Run 使用版本 2，Build/Verify 由 Agent 运行检查，再提交 `--checks` JSON 报告。Runtime 核对报告、批准和完整验收，不重复执行同一命令。失败报告不能领取完成 Action；未运行检查需要说明。旧版本 1 Run、固定应用及其恢复入口继续原定义。

纯内部投影的合并只作用于内置 v2；SDK Run 仍逐次提交。真正的命令执行、Agent/用户交接、未知结果和终态保持落盘边界。路径准备仅在单次 CLI 内复用，不缓存文件内容；实际读取仍检查受保护路径。Native Archive 的执行器与校验器复用同一次预检，冷恢复缺少内存结果时重算，正式发布事务不变。

旧 PID 格式首次退役需要 Agent 确认实际操作已停止，之后不再要求绑定新线程或等待旧 PID 过期。新操作通过 SQLite 事务排他，进程退出自动释放；已有完成结果沿原 Action 恢复。未知命令结果保持未知，必须先核对实际副作用，不能自动重放。

这批旧失败包含已经撤下内容证明后的旧期待，也包含两个仍未解决的交付恢复阻塞：归档 checkpoint 提交后的交付恢复，以及归档后修复检查输出后的交付恢复。它们在旧基线同样返回 checkpoint 不匹配错误，不能统称为过时测试。本轮未修复这些既有问题；相应登记和断言仍保留。逐项结果见 [验证数据](2026-11-09-runtime-pid-retirement/validation.json) 和 [基线失败对照](2026-11-09-runtime-pid-retirement/baseline-failures.json)。

首次公共 core 选择器连带选中了完整历史组，已中止并改用登记器的精确选择器；中止轮次不计通过。此前因旧 PID 协议和新旧 Run 夹具混用产生的失败也不计通过，后续结果只代表已实际执行的对应修正和迁移范围。

## 性能对照

Windows、同一 Node 版本、隔离 Runtime 和临时项目。每组新旧生成 Runtime 交替运行三轮，文件数为 0 或 2000（每文件约 1 KB）。测试和构建结束后单独运行，48 次测量调用均成功；下表为含进程启动时间的中位数。测量前后 bundle 分别与 `7f016b28` 和本次提交的生成资产逐字节核对一致。[原始记录、范围及复现脚本](2026-11-09-runtime-pid-retirement/performance.json)。

Classic 重复调用仍全部复用原结果；Git 调用数没有增加。Native new 仍为 5 次、status 仍为 1 次 Git 调用。Native status 的变化接近观测波动，不能据此声称提速。首次并发负载下的预采样不用于上述结论。

这组测量证明锁与路径减负改善了指定 CLI 路径，不是 Agent 端到端耗时或模型 token 对照。新 Classic v2 还撤下普通 Build/Verify 的受管检查及收据 Action，平台实际检查由 Agent 选择；本轮没有启动真实模型 Eval，不能给出整个工作流固定提速比例。

没有启动 Eval、全量测试、安装或真实平台 Hook 验收。PID 移除能消除该机制的恢复阻塞，不能消除 Git、文件发布或命令执行到一半的事实。
