# Runtime 下一轮减负与 PID 退役

来源：`report:2026-11-09-runtime-pid-removal`。用户授权实施此前六项减负，并明确要求移除 PID 机制。基线为 `053` 的 `7f016b28`；在临时 detached checkout 实施，最终合回 `053`，不新增长期分支。

移除的是 Comet 的 PID 身份、存活探测、持久绑定与恢复依赖。当前执行器可以停止自己持有的 ChildProcess；这不代表通过 PID 推断历史命令是否完成。中断后仍须依据原 Action、已提交结果及实际文件/Git 状态恢复，不能凭空认定未知副作用成功或重新执行。

## 实施清单

- [ ] 共用锁和 Native 锁撤下 PID/创建身份、探测器、协调票据及等待 PID 过期；复用现有 SQLite 事务互斥，进程退出自动释放。
- [ ] Native/Classic 检查及恢复不持久绑定 PID；历史字段兼容读取但不参与推进或接管。
- [ ] 命令内复用已准备 Runtime/Change 路径，普通内部读写不重复做祖先全链遍历和旧布局迁移。
- [ ] 新内置 Classic 普通检查采用平台报告；保留批准、完整验收、真实失败、用户接受和 Git 交付。
- [ ] 合并纯内部投影与结果副本，保留实际执行、Agent/用户交接和终态恢复边界。
- [ ] Native 高层任务直接投影业务包，归档预检计算一次，保留实际写入事务。
- [ ] 当前归属发现与无关历史恢复隔离，中性文档不被旧归档投影故障阻塞。
- [ ] 定向源码/生成 CLI、旧 Run 与恢复、性能对照、独立 Review、Changelog、提交推送及临时 checkout 清理。

## 已取得的证据

共用锁的首个回归在旧代码因记录含 PID 而失败。新实现的并行写互斥、真实子进程退出后无 doctor 重新加锁已通过。Native 锁没有 PID/创建身份或进程探测，仍拒绝同锁的第二写入者；公开 Native new 已通过。

实验中发现 Windows SQLite journal 不能直接使用长路径，已通过平台的 namespaced path 传入；SDK Run 严格目录清单同步识别锁数据库及其 SQLite 临时文件。未通过删除旧断言掩盖这些失败。

原 PID、跨主机身份及协调票据断言需要按已授权功能退役完整归档和迁移；并行互斥、实际错误、路径归属、真实中断与无重复副作用仍须保持。最终测试与性能结果另行补齐。

没有启动 Eval、全量测试、安装或真实平台 Hook 验收。PID 移除能消除该机制的恢复阻塞，不能消除 Git、文件发布或命令执行到一半的事实。
