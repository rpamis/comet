# bugfree 模式撤下记录

日期：2026-11-05。来源：`report:2026-11-05-bugfree-retirement`。比较基线：`3c40cd26235441549e00e265881d56fb49b72c62`，分支 `052`，版本 `0.5.2`。模式最初随 `c3d0e82f` 引入，之后的改动包括已提交修复及本地迭代。

用户要求：若本次仍未达到目标，记录失败根因、全部尝试和证据，撤下 Skill 与 CLI 等入口中的 bugfree 模式。此前最多迭代 10 轮的上限没有用完：实际停在第 7 轮。用户随后清除了持续目标，并明确要求不再运行普通 Native 组。本次撤下没有启动新的模型 Eval。

## 结论及其适用范围

当前实现未达到“保持正确率，同时显著压缩 Verify 耗时和 token”的目标，按用户要求停止投入并移除产品入口。

最后一轮 bugfree 原题仍为 **10/14**，完整审查约 **131.697 秒**，输入加输出 **53,141 token**，缓存读取 **900,096 token**，合计 **953,237 token**。Runtime 内部验收为 pass 并归档，不能据此将原题失败写成成功。上一轮 bugfree 为 134.970 秒、1,091,381 token；本轮分别减少约 2.4% 和 12.7%，得分没有提高。

上一轮普通 Native 为 102.917 秒、779,483 token、10/14。最后一轮 bugfree 相比它约慢 28%、多用 22% token。但这是跨轮参考，不能替代同一冻结版本的配对实验。最后一轮普通组被用户停止，不能编造它的完整分数或配对收益。

这个结论针对本次实现、任务、模型和执行协议。实际后期模型为 CC Switch 配置映射到的 `deepseek-flash`，配置名称为 `deepseek-flash[1M]`，Claude Code 版本为 `2.1.306`。没有据此证明所有前沿模型、所有任务或语义审查方法都不成立，也没有取得跨任务统计意义上的正确率保证。

## 为什么没有达到目标

### 1. 验收正确性仍会随需求解释偏离

早期两组出现 3/14：Shape 将原题的首次 execute 内自动重连重放，解释成由调用方显式 reconnect 再 execute/replay；又排除了原题要求的 WATCH 和异常语义。用户模拟器接受了该方案，内部 Verifier 对新 Spec 给出 pass，但固定原题评分器仍判失败。

后来将原始 task 保存到 Run，交付独立审查者，并要求在同一结果内提交 `requestReview`，防止只按生成的验收项检查。有效原题对照提高到 10/14，但两组仍漏掉同样的四项原题要求。原始请求确实已交付，不能将剩余问题都解释成没收到需求。

这说明额外的“已阅读”“aligned”字段及机械校验没有自动形成足够强的语义判断。测试通过、收据完整和独立会话是真实事实，却不能代替行为正确性。普通 Native 也有这个问题；它更快不表示验得更准。

### 2. 语义审查指引没有稳定改变执行行为

bugfree 保留一个独立只读 Verifier，要求优先阅读代码并复用适用证据，有具体疑问才补查。但实际审查者仍会重跑现有测试、自建探针、读取 Git 历史、核对日志和摘要。较早的一轮重跑 13 项测试并增加 26 个探针；最后一轮也运行 unittest 并创建临时探针。

取消固定测试轮次没有消除模型为建立信心而选择的检查。增加更详细的指令和任务包，又会增加上下文、阅读与提交开销。本次没有通过禁止必要补查或自动通过来制造性能收益。

### 3. 为降低阅读成本增加了另一套协议成本

实现引入了创建时固定模式、额外输入基线、专用领取材料、原审查会话续行条件、紧凑通过集合、模式专用报告和模式比较证明。每项都希望减少重复工作，但组合后增加了需要解释、序列化、恢复和兼容的分支。

长 JSON 里同时存在新旧模板和大量状态，实际模型多次查找字段、历史 `outcomeId`、checkpoint 和日志摘要。第 6 轮 Skill 入口要求使用旧 `outcomeRequest`，而 Runtime 已提供 `resultRequest`，交接又复制了旧要求。这是具体的产品指令冲突，不能全部归因于模型。

第 7 轮已统一两种语言的 Skill，领取响应也直接提供材料和模板引用。模型确实改用 `resultRequest`，成本有所下降，但仍未取得可靠优势。最后一轮 JSON 解析失败还包含模型自行在输出后追加 `EXIT:0`、混合 stderr、截断 JSON 的命令；不能据此声称 Comet 的 `--json` stdout 自身不纯。

### 4. 协调者成本不能忽略

第 5 轮只看子 Agent：bugfree 54.131 秒、316,488 token，standard 96.281 秒、521,326 token，看起来明显改善。加入协调者后，bugfree 虽然更快，token 却略高：869,419 对 867,584。后台启动只用了约 48 毫秒，审查并没有在 48 毫秒内完成。

第 6 轮改为无必要并行工作时前台等待，协调消息从六条降到三条，子会话却变贵。单独优化一个环节没有保证完整流程更省。

### 5. 评估基础设施曾多次混入干扰因素

这些问题影响了实验可信度和开发耗时，不能作为有效性能收益，也不能被全部算成 bugfree 的模型失败：

- 校准任务缺少输入文件，没有进入 Verify。
- 校准正例本身包含未发送非幂等命令被误判的错误，bugfree 检出后不能算误报。
- authored 任务镜像键忽略 COPY 的实际环境字节，负例复用了正例镜像；输入不匹配，不能算漏检。
- 将 authored 镜像摘要注释追加到 dataset Dockerfile，触发原题环境完整性失败，reward 为空。
- 评估 CLI 和 npm 缓存进入候选输入发现，导致上百个工具文件与大缓存被反复扫描。
- 评分夹具的 PyYAML 缺失及 LF/CRLF 预期摘要不一致。
- 离线角色统计使用一次性生成器，后续字段漏记；已补算，原始报告未修改，主要 Verify 统计不受影响。
- 有历史普通组下载并读取公开参考答案，该样本单独标为污染；没有把它的高分用于有效比较。

相关通用修复保留：实际任务环境参与 authored 镜像身份；dataset 原始装配字节保持不变；CLI 只读放在受控工具目录；仅迁移真实 npm 缓存；输入或环境失配不作为正常可比较样本；原始低分不因“不好看”而过滤。

## 普通 Native 是否因为省略验收或读取答案而快

第 6 轮普通组确有独立 Agent，会话 14 条 assistant 消息、约 76.625 秒。它读取原始任务、brief、Spec、实现和测试，运行 8 项现有测试和 20 个临时探针，并提交自己的领取收据。原始记录的参考访问列表为空，产品与执行身份匹配；没有发现这一轮读取参考答案的证据。

但其结果仍为 10/14。快速执行和 Runtime pass 均不能证明验收充分。早期已发现参考材料污染的样本继续排除，不能将“本轮未发现”扩大成对所有历史运行的保证。

## 回归登记的迁移

原 case ID、来源、行为、预期、禁止结果和旧测试选择器保留，旧测试正文单独完整归档，并保留移除前实现补丁。相关清单仅追加 `testMigration`：指向本记录、用户撤下请求和当前替代契约，不将旧失败改成通过。

`feature-removed` 对应被撤下能力，执行“入口不可用、未上线定义与紧凑协议不存在、普通流程仍完整”的替代测试；不得在 PR 中宣称原模式问题已修好。原来尚未完成的模型验收保留为历史事实，不再阻塞已删除能力的发布。`tests-moved` 用于仍存在的共享能力，改执行普通 Native 的相应断言，原附加验收要求继续有效。
