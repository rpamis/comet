# #519：让用户直接看懂 Agent 做了什么

日期：2026-11-01。来源：[Comet #519](https://github.com/rpamis/comet/issues/519)。

本轮按用户要求收敛：便捷、清晰、可视化，完全不依赖 Dashboard；考虑额外 token 消耗，生成能力由项目配置显式开启，默认关闭。以下是修订后的建议，替代上一版以范围证明、版本绑定和归档机制为重点的方案；尚未实施产品功能。

## 建议：按需开启可直接打开的 HTML 变更说明

用户开启配置后，Agent 在 Build 收尾时，用已经掌握的实现上下文和实际差异整理一份变更说明，填入固定模板，生成单个 `walkthrough.html`。回复里给出“查看变更说明”的本地链接，用户用浏览器打开即可。

页面内嵌样式和必要内容，不需要启动服务、安装编辑器插件、连接外部网站或打开 Dashboard。开启时输出可视化 HTML；聊天中保留几句摘要，终端环境仍能理解结果。

首版的核心就是：一个开关、一份固定模板、一段生成指引、一个产物链接。

## 可选配置与 token 消耗

建议在 `.comet/config.yaml` 增加 Native/Classic 共用的顶层布尔字段：

```yaml
# 是否生成可直接打开的 HTML 变更说明；开启会增加讲解内容的 token 消耗。
change_walkthrough: false
```

这是待实现字段，当前版本尚不支持。名称沿用 change 与 walkthrough 的现有语义；一个布尔值即可，不增加格式、详细程度或模型参数。

- **缺省或 false：** 跳过详细生成指引、额外讲解整理和 HTML 渲染，也不为此额外读取差异或请求模型。常规实现、交接、检查及完成摘要保持原样。
- **true：** 才加载生成指引并组织页面内容。直接复用当前 Agent 的上下文、实际差异与已有检查结果，不单独启动讲解 Agent 或额外模型服务。
- HTML 由固定模板渲染，Agent 只提供少量内容，不每次重写样式和页面代码。Verify 仅补已有检查结果时可直接更新展示；修复了代码时才同步相关讲解。
- 新项目默认 false，旧项目缺少字段也按 false。`init`/`update` 补齐默认值时保留用户已有 true/false，不自动开启，也不新增交互询问。首版只提供项目开关，不新增全局或 Dashboard 设置；其他配置写回入口也须保留用户选择。

已核对当前配置入口：共用类型在 `domains/workflow-contract/types.ts`，解析、默认值、注释和合并在 `domains/workflow-contract/project-config.ts`，读写沿用 `project-config-reader.ts` 与 `project-config-writer.ts`；安装更新还经过 `domains/skill/platform-install.ts`，CLI 入口为 `app/commands/init.ts` 与 `app/commands/update.ts`。现有 `ambient_resume` 就是共用的顶层布尔配置，可参考其接入方式。

针对配置文件的 `git log --all -G` 检索未发现曾经新增或移除 walkthrough、visualization、html_report、change_report、code_explanation 等同类字段；该结论限已存在的本地 refs，未拉取远端历史。本建议是用户明确要求的展示开关，不涉及恢复 snapshot 预算。

## 用户打开后看到什么

按阅读顺序排列四部分：

| 位置     | 展示内容                                            | 默认状态 |
| -------- | --------------------------------------------------- | -------- |
| 顶部     | 一句话说明本次完成了什么                            | 直接可见 |
| 主要变化 | 按功能分组，展示“原来怎样 → 现在怎样”，简短说明原因 | 直接可见 |
| 代码详情 | 每组涉及哪些文件，关键代码片段或局部 diff           | 点击展开 |
| 底部     | 实际检查结果和未执行项                              | 简短列出 |

示意布局如下，文字仅用于说明展示方式，不代表已实现某项功能：

```text
本次改动：搜索支持按标签筛选

┌ 搜索方式 ─────────────────────────────┐
│ 原来：只能输入关键词                  │
│ 现在：关键词与标签可以一起筛选        │
│ 原因：缩小结果范围，方便找到目标      │
│ ▸ 查看涉及的文件和关键代码            │
└──────────────────────────────────────┘

┌ 空结果提示 ───────────────────────────┐
│ 原来：没有结果时只显示空列表          │
│ 现在：提示清除筛选条件后重试          │
│ ▸ 查看涉及的文件和关键代码            │
└──────────────────────────────────────┘

验证：相关测试通过；浏览器交互尚未验证
```

展示规则保持简单：

- 先讲用户能感知的行为，再展示实现细节；使用项目自身的语言，不堆砌 Runtime、指纹或快照字段。
- 按逻辑变化分组，同一个功能涉及的实现、配置和测试放在一起。文件路径清楚可见，代码片段足够用户核对。
- 新增、修改、删除、重命名使用短标签；删除说明移除了什么，重命名不虚构功能变化。
- 小改动一张卡片就够。大改动先概括主要变化，其余内容折叠，不把整份 diff 默认铺满页面。
- 只有调用或数据流确实难讲清时才加一张简单关系图；普通修改不强制画图。

## 在 Comet 中怎样接入

1. **Build 收尾按配置生成页面。** 先读开关，仅开启时加载详细生成指引，整理总览、逻辑变化、相关文件和关键片段，交给共享 HTML 模板渲染。无需独立 Agent 或额外模型服务。
2. **Verify 后按配置更新同一页面。** 开启时沿用已有检查与独立验收结果，更新底部验证说明；修复了代码，就同步更新对应卡片。完成回复提供已生成的入口；关闭时不生成或更新页面。
3. **Archive 随现有材料保存。** 已生成的 HTML 随材料保存，方便以后打开阅读；未生成时不补生成，不提示用户缺少必需产物。关闭开关无需删除已有文件。

Native 和 Classic 共用展示模板，各自在现有交接位置调用。页面放在已有运行产物位置，展示文件本身不纳入实现检查输入。展示不增加 phase、默认确认或检查重跑；生成失败说明原因并允许重新生成，不阻塞原有工作。

初版不用建设新的候选绑定、版本历史、差异归属或增量缓存系统。Agent 根据本次实际完成的工作组织内容，只保留实际生成时间和已知比较范围；有把握的内容直接讲清楚，不确定的部分用一句话说明。页面展示本次生成时的结果，需要更新时重新生成即可。

## 最小实现与验收

实现保持在以下范围：

- 一个共用布尔配置，补齐解析、默认值、双语注释和 init/update 保留用户选择的行为。
- 一份可复用的 HTML 模板，包含总览、变化卡片、可展开的代码详情和验证结果。
- 一个共享渲染函数，接受 Agent 整理的少量展示数据；不要求另存一套公开 JSON 协议。通过内嵌样式和原生折叠元素完成主要交互，代码和说明按文本转义。
- Native/Classic 的条件生成指引与结果链接，关闭时不加载详细指引；先按仓库规则完成中文协议，再同步英文。

验收先确认配置缺省/false 时不生成额外讲解和 HTML，true 时两个 workflow 均可生成，init/update 不覆盖已有选择。展示侧确认单个文件能直接打开；首屏能看懂主要变化；展开能看到具体文件和代码；验证文案符合实际结果；小改动简短、大改动可折叠；更新与归档都能继续阅读。首版做配置与模板定向测试及浏览器检查，解释质量另以实际样例检查，不能靠页面存在就声称准确。未经用户明确要求不启动 Eval。
