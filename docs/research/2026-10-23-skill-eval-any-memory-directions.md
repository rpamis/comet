# Skill、Eval、Any 与记忆能力的外部实践调研

调研日期：2026-10-23。用途：为 `051` 头脑风暴提供一手资料，不构成实施方案或发布承诺。

## 结论

现有公开材料不能证明存在统一的“2026 年主流记忆架构”，也不能用是否采用向量库或知识图谱判断产品是否先进。当前 Claude Code 仍用 Markdown 索引与按需读取主题文件；LangGraph 提供多种记忆组织方式；Zep 采用时序图与混合检索。应比较任务完成质量、旧信息误用、维护成本和检索开销，而不是只比较存储技术。[Claude Code](https://code.claude.com/docs/en/memory)、[LangChain](https://docs.langchain.com/oss/python/concepts/memory)、[Zep](https://arxiv.org/html/2501.13956v1)。

对 Skill 流程更有价值的问题是：哪些约束仍能防止真实失败，哪些步骤只增加等待和上下文？Anthropic 在 2026 年的实验中随模型能力提升移除了上下文重置和固定 sprint，并根据任务难度调整独立评估的使用。它支持用实测逐项精简流程，不能推导为所有任务都应取消阶段或审查。[Harness design](https://www.anthropic.com/research/harness-design-long-running-apps)。

以下资料只证明外部实现或研究做法。本笔记没有单独审计 Comet 源码，后文均为待核对、待实验的方向，不能把它们当作 Comet 当前缺失功能的清单。

## 对 Comet 的判断框架

以下是基于上述资料提出的产品判断与实验设计，不是来源文章对 Comet 的评价。已有能力应先在当前分支确认，优先复用而非重建。

### Skill：保留可验证约束，评估流程成本

Classic 与 Native 不应只比较步骤数量。建议按小修复、多文件功能、模糊需求、跨会话恢复四类任务，分别测量任务成功率、用户纠正次数、有效审批次数、等待时长和输入上下文大小。固定模型、任务与预算，逐项对比每个协议带来的收益，避免一次移除多个步骤后无法归因。这个方向来自 2026 年 harness 实验对流程收益随模型变化的观察。[来源](https://www.anthropic.com/research/harness-design-long-running-apps)。

可优先讨论三类改进，实施前核对现有机制：

1. 阶段上下文只提供当前目标、必须遵守的约束、下一步动作和验证要求；细节通过明确引用按需读取。记录重复加载与无关加载的成本。[按需上下文](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。
2. 将恢复包做成可验证的任务交接：当前候选、已完成证据、未决问题、下一动作和阻塞原因；用真实中断恢复实验衡量是否减少重做。这里的字段是 Comet 的候选设计，不是外部统一规范。[稳定 session 边界](https://www.anthropic.com/research/managed-agents)。
3. 区分必须由用户决定的范围、外部动作，与可由已有证据满足的机械检查。以“减少重复确认但不增加越权”为共同验收条件，不以单纯减少确认次数为目标。该项是产品推论，需结合 Comet 现有授权语义验证。

### Eval：把已有评估能力用来决定是否值得改

不预设 Comet 缺少固定用例、基线对比、重复运行、`pass@k` 或成本比较；本轮重点应是现有能力是否覆盖下列产品问题。评估应以最终产物和环境结果为主，并对判分器进行人工抽查。[来源](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

| 要决定的产品问题                       | 可对照的实验                               | 首要观察项                                     |
| -------------------------------------- | ------------------------------------------ | ---------------------------------------------- |
| Native 或 Classic 的哪些步骤值得保留？ | 原流程与逐项精简流程，任务、模型、预算相同 | 完成质量、恢复成功、用户纠正、成本与延迟       |
| 记忆究竟有没有帮助？                   | 无记忆、现有记忆、候选检索方式             | 正确完成率、旧信息误用、首个正确定位所需时间   |
| Any 的组合是否优于原 Skill？           | 原始 Skill 与组合应用，匹配任务与依赖      | 交付质量、额外失败、成本、安装后首次运行成功率 |
| 某模型升级后是否还需要原编排？         | 同任务上的模型与流程组合                   | 保持质量时可省去的步骤、重复失败与成本变化     |

负例同样需要覆盖：本不需要记忆时是否注入、不需要审批时是否阻塞、无关 Skill 是否被触发。若某条统计已经存在，优先增加任务样本与可解释报告，不重复开发指标。[正反样本](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

### Personal Memory：重点是长期正确，不只是保存与召回

可用以下问题检查现状：记忆能否说明来自哪个用户决定或已验证结果；作用域是否清晰；偏好变化后能否替换旧值；删除是否影响后续召回；用户能否理解为何被记住；平台原生记忆与 Comet 是否重复注入。Claude Code 的可审阅文件与 LangChain 的更新、删除讨论支持这类检查，但没有规定 Comet 必须采用相同自动写入策略。[Claude Code](https://code.claude.com/docs/en/memory)、[LangChain](https://docs.langchain.com/oss/python/concepts/memory)。

建议用相同用户连续多次任务进行验证：先确认一种偏好，再明确纠正；跨项目给出例外；后来删除；最后执行相关与无关任务。观察正确遵从、例外隔离、旧值复现和无关注入。这是建议新增或复用的验收场景，不表示当前实现已经失败。

### Project Knowledge：重点是事实来源与当前版本是否一致

检索结果应帮助 Agent 回到可验证的代码、文档或决定。候选改进可以包括源文件变化后的失效提示、按仓库与分支过滤、来源时间、替代关系，以及语义与关键词检索的组合对照。Zep 的时间语义提供思路，但其“较新信息优先”不能直接用于代码事实：新笔记也可能错误，应优先验证真实源码与用户确认。[时序与检索设计](https://arxiv.org/html/2501.13956v1)。

是否增加向量、重排或图关系应由具体失败决定。例如用“用户换一种说法后找不到已有决定”验证语义检索；用“函数已删除，旧知识仍引导修改”验证失效；用“同名模块跨仓库混淆”验证作用域。只有现有检索在这些任务上确实不足，才选择对应技术。

### Any：从能组合推进到可解释、可复现、能比较

Agent Skills 规范为发现和加载提供共同格式，但没有替 Comet 处理跨 Skill 的输入输出、权限、审批和失败恢复。值得讨论的产品呈现是：组合前说明各 Skill 的职责、冲突与环境要求；组合后解释实际改动了哪些阶段；保存可复现实验所需身份；安装后用用户代表任务验证。固定依赖和应用版本若当前已经具备，应继续用于升级差异、失败定位和效果对比，而不是再做一套机制。[规范边界](https://agentskills.io/specification)。

## 优先讨论顺序

1. 选少量真实任务，建立 Skill 流程、记忆开关和 Any 组合的对照；先确认哪里有收益或损失。
2. 根据结果减少高频重复步骤与无关上下文，补齐能复现的恢复或失效问题。
3. 用同一套 Eval 比较新旧方案，保留成本、延迟和质量变化；再决定是否增加语义检索、重排或图结构。

本轮未运行外部产品、Comet 真实模型 Eval 或跨平台接受测试；公开资料查阅不能替代这些证据。
