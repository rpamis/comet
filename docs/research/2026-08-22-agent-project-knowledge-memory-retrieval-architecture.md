# 面向 Agent 的项目知识与个人记忆分层研究

## 研究问题

这份研究把用户提供的 AI-Native 软件工程知识引擎文章，转化为 Comet 的产品边界：目标不是把更多文本塞进上下文，也不是替代代码阅读，而是让 Agent 在开始任务时先获得高密度、可核对的项目理解，减少反复枚举目录、全文搜索和猜测模块关系的过程。

## 文章结论的可用部分

文章把项目知识的价值归纳为三类：

1. **行为约束**：记录模块职责、兼容规则、参数语义、验证顺序和隐含工程约定，避免 Agent 找到正确文件却实现了错误语义。
2. **集成关系**：指出功能定义、注册入口、初始化路径、运行时消费方和生成物之间的关系，避免只改局部实现而遗漏生效入口。
3. **调用链传播**：帮助 Agent 沿客户端、缓存、索引、配置和测试的跨层链路核对参数、默认值和影响范围，避免类型仍可通过但边界行为不完整。

文章中的知识生产流程包括来源扫描、结构化整理、关系提取、用户修正、增量维护、共享和 Agent 消费。对 Comet 来说，这些概念需要收敛为可落地的最小能力：有限来源、项目知识单元、确定性提取、可选语义评审、来源核对和一跳关系；不直接建设通用图平台或完整源码 RAG。

文章的评测启示也被保留：应比较无知识、即时搜索、任务前召回和任务中补充四种条件，除成功率外记录首次定位、无关探索、工具调用、Token、轮次、耗时、完整变更范围和错误知识造成的锚定。项目知识只有在减少探索并保持完整修改范围时才算有效。

## 个人记忆与项目知识的边界

个人记忆和项目知识都可能出现“项目”字样，但所有权不同：

- Personal Memory 保存用户的 global/project 偏好、工作习惯和个人经验。project 作用域由现有 project key 自动召回，适用于当前用户在多个 worktree 中的连续偏好。
- Project Knowledge 保存可以由当前项目来源支持的工程事实、模块语义、集成路径、影响范围和验证方式。它服务所有得到项目访问权的 Agent，不代表某个用户的私人习惯。
- 两者在 `comet task` 中并行提供，各自有独立 plugin ID、预算、存储和管理动作；不自动复制，不共用数据库。
- 用户明确要求共享个人经验时，先删除个人信息，再打开当前来源核对，形成 draft 项目知识单元，得到确认后才写入项目维护目录。

因此，“先确认中文语义，再同步英文”之类偏好留在 project Personal Memory；“Native 与 Classic 的入口、验证顺序和生成资产边界”才属于 Project Knowledge。个人偏好不会因为发生在某个项目而自动变成团队事实。

## 面向 Agent 的对象

普通 Wiki 适合人类连续阅读，但 Agent 需要更小、更密集、能直接指导任务的项目知识单元。首期单元类型为：`project-map`、`module-overview`、`behavior-note`、`integration-path`、`change-impact`、`build-test`。每个单元包含稳定 ID、标题、摘要、来源、适用路径/操作、结论、关系、状态和验证方式。

来源分为项目维护和自动生成两类；状态只有 draft、active、retired。任何单元都不能覆盖当前代码、配置和测试。来源删除、越界、变化或不能支持结论时，单元不得进入 Agent 上下文。

## 检索原则

SQLite FTS5 适合把 Markdown section 作为候选并跨文档排序，但不能单独解决查询规划、变化文件补充和最终代码核对。Local 应采用 SQLite section 读模型 + ripgrep 强匹配/故障回退的混合方案：

- 强标识符、路径、命令、错误码和完整中文短语优先；弱中文片段不得提前耗尽候选预算。
- 中文使用完整技术短语、有限二至四字片段和 trigram 补充，不直接依赖默认分词。
- 候选经 FTS、ripgrep、单元和一跳关系融合，做来源多样性、归档降权、状态过滤和输出上限控制。
- 进入上下文前再次打开当前来源；项目知识用于缩小搜索范围，不能代替 Agent 读取代码和运行验证。

## 更新与治理

日常更新按来源发现变化、按 section/单元写差异；未变化内容继续复用，变化文件在更新期间由限定范围的 ripgrep 补充。自动语义沉淀必须来自有界来源包，且只有任务成功完成验证、来源仍然可核对、Runtime 校验通过后才可成为 active。用户显式共享是唯一把个人经验写入项目维护目录的入口。

## 非目标

首期不引入 embedding、向量数据库、完整源码分块、完整 Git 历史、聊天记录、日志、文件 watcher、通用图数据库或 Project Knowledge 规则子系统；这些会扩大数据边界和运行负担，且不能证明 Agent 真的减少探索。

## 研究结论

Comet 应把项目知识做成 Agent 服务层，而不是第二套项目规范系统：任务前主动预取，任务中精确补充，任务后基于验证沉淀；Personal Memory 负责用户连续性，Project Knowledge 负责项目共享事实。SQLite + ripgrep 是 Local 的实现手段，项目知识单元和来源核对才是面向 Agent 的产品能力。
