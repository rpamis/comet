# Native 与 Classic Skill 四项执行优化

比较基线：`053` 的 `b0a2fc5d03b0e265ba83459667e3cad30c18fe39`。本次对应用户“实现你说的4点”，来源为 `report:2026-11-08-skill-execution-optimization`。范围来自[执行重复调查](2026-11-08-skill-workflow-execution-redundancy.zh.md)的四项主要结论，不包含 Creator、独立应用调度或新增模型评估。

## 逐项实现

| 项目                                    | 实际变化                                                                                                                                                                                                                                                                                                               | 保留的约束                                                                                                                                                  |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1：首次完整检查直接由 Runtime 执行      | Native 普通 v3 的 Skill 和业务任务指令要求通过已有 `request-checks` 运行首次最终 GREEN。Classic 在原实施或验收任务中支持 `comet check run <change> build --local -- <program> ...`；Verify 使用 `verify --report <report-ref>`，先声明报告位置，检查后写真实报告。正式 complete-build / Guard 继续核对并复用匹配收据。 | TDD RED、局部调试保留；预检查不推进阶段，不代表完整验收通过。外部状态或不可重复命令不加 `--local`。未知结果沿原 Action 恢复，不自动重放。                   |
| 2：后继任务保留原计划                   | Native Builder 模板保留已声明计划，包括 argv、cwd、timeout、repeatable 和输出声明；新完整交接替换旧计划集合。Classic continuation 保留原 argv、cwd、timeout 和明确选择的复用语义；Guard 接受这些原参数。                                                                                                               | 计划不是成功证据；Runtime 仍检查当前输入、环境、日志和原始收据。失败不被更早成功遮蔽。未选择本地复用的命令不会自动添加 `--local`。                          |
| 3：Delta 生成完整目标 Spec              | 关联能力只需维护 Delta。显式准备 Shape 时根据当前正式基线生成完整目标；机器生成收据允许后续修改 Delta 后更新已知生成内容。普通读取与批准后的重新校验不生成目标。                                                                                                                                                       | 完整目标继续绑定 Shape 批准和全部验收。独立目标编辑、基线或 Delta 冲突保留文件并阻塞；写入前重新核对输入，不覆盖并发编辑。无 Delta 的旧 change 保持原规则。 |
| 4：Runtime 生成 Supervisor 验收正文索引 | v2 children 可以只写 name、depends_on、covers。Runtime 从当前验收 catalog 生成完整 index，并保存在 Shape 提案与 Run 中；不向用户 children.yaml 复制正文。                                                                                                                                                              | 完整提案仍待确认；总覆盖、无环依赖、允许的失败 Spec 修复 ID、子任务 worktree、子任务和父级验收保留。V1、显式 index 和 summary-v2 兼容，不重新解释旧批准。   |

中文七个 Skill 文件已落盘并获用户确认，随后同步英文。Native 的编辑协议副本同时同步为此前已确认的共享正文，修复已记录的八条副本一致性契约失败；没有放宽断言。版本保持 `0.5.3`：当前 `origin/master` 与上个发布 tag 均为 `0.5.2`，在现有 `0.5.3` Changelog 追加用户可感知的两项最终行为。

Classic 的准备命令在内存中装配原 Run 的待执行检查，再以一次 CAS 保存；实际命令仍沿“预留、锁外执行、提交”的原路径。没有增加第二套推进状态，也没有在测试、模型或用户等待期间持有写锁。Native 的生成只在显式 Shape 准备路径获取短写锁。

## 公开 CLI 对照

原始结果见 [性能记录](2026-11-08-skill-execution-performance.json)。旧基线从上述 commit 导出并编译，当前源码完成 Runtime 与 CLI facade 构建。两边均使用公开 `node <repo>/bin/comet.js`、独立进程、隔离 Git 项目与 HOME、项目外 Runtime 数据，关闭 daemon。每组 4 个交错样本，第 1 个作为预热，以下为其余 3 个中位数。

检查命令固定等待 5 秒并向项目外计数文件追加一次记录。等待用于控制真实进程检查时长，不是模型耗时，也不代表实际项目测试性能。准备 fixture 和批准模拟不计入测量；测量覆盖首次检查及正式 Guard 提交。

| 场景                                  |               旧流程 |             当前流程 |       差异 |
| ------------------------------------- | -------------------: | -------------------: | ---------: |
| Classic Build 首次完整检查到正式提交  | 14.340 秒，执行 2 次 | 11.632 秒，执行 1 次 | 减少 18.9% |
| Classic Verify 首次完整检查到正式提交 | 15.166 秒，执行 2 次 | 12.790 秒，执行 1 次 | 减少 15.7% |

旧流程为普通进程首次检查后由 Guard 再执行；新流程为 Runtime 首次检查后由 Guard 校验并复用。额外的 Runtime 协调也有成本，因此快速检查未必明显缩短；长检查主要省去一次真实命令的耗时。未据此推断整个 Skill 或模型端到端加速比例。

Native 的公开 CLI 等价输入另外核对了两项新增入口：

- 只编辑关联 Delta：旧基线退出 65，报目标缺少新增 requirement；当前退出 0，完整目标已生成，仍停在用户 Shape 确认处。
- children 只写 covers：旧基线退出 65，报缺少 summary / 不接受 covers；当前退出 0，仍停在用户 Shape 确认处。

这些是新行为与批准边界证据，不将旧版提前失败的较短耗时当作性能基线。所有批准均为隔离 fixture 明确标注的模拟，不代替真实 change 的用户决定。

## 限制

- 没有启动真实模型 Eval：用户未授权；模型是否稳定遵守新指令、会减少多少轮仍无真实模型证据。
- 未运行全仓测试、完整安装升级、真实平台 Hook 或发布。当前改动使用定向验证，未将其报告为全量通过。
- 原工作区 `.ruff_cache` 是架构检查不允许的既有根目录；完整 `pnpm lint` 的 ESLint 为零错误、九条既有 warning，随后架构检查因此失败。保留该目录及无关归档状态、website 改动，不删除它们换取通过。
- 生成收据保存在机器 Runtime 中。跨机器恢复后若 Delta 与已保存目标已不一致、又缺少生成来源，Runtime 保守报告独立编辑冲突，需要协调目标与 Delta；不会猜测并覆盖文件。
- 外部状态、一次性操作、变化输入和无效日志继续真实执行或阻塞；这四项优化不提供无条件缓存。
