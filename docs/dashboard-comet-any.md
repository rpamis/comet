# Observe generated Comet Any workflows

Open `comet dashboard`, select a project, and choose **Comet Any 工作流** in the workflow sidebar. This read-only view shows the runtime of Skills generated by `/comet-any`; it does not show the Skill creation wizard or change the project's default Native/Classic workflow.

The view provides searchable, paginated active/completed/all run lists across the project's Git worktrees. Selecting a run shows its current node, recorded completed nodes, declared route, stored evidence, the latest 100 history entries, and declared output artifacts. The existing Dashboard refresh cycle refreshes the selected run as well as the list.

The layout shares Native's overview, next-step banner, metric cards, three-pane workspace and node progress presentation. The left pane selects a run; the center shows nodes, artifacts and evidence; the right pane shows persisted status, recorded blockers and the selected project's Git summary. Metrics count all discovered project runs independently of search and pagination. Native-only acceptance, executor and recovery information is not inferred for Any runs.

## Data sources and meaning

- Runs are discovered from `.comet/runs/<workflow>/state.json`, the path generated for standalone workflow protocols. A generated Skill appears after its runtime has initialized this file; installing or creating a Skill alone does not create a run.
- Route and output declarations come from project-local installed `reference/workflow-protocol.json` files with a matching workflow name and state path. When no installed definition is available, `.comet/bundle-authoring/*.json` can supply a clearly labeled authoring snapshot. Conflicting definitions are reported instead of choosing one silently.
- Without a definition, the run remains visible with recorded nodes and an unknown total. Global-only installations without a local authoring snapshot therefore show reduced detail. No global Skill directories are read.
- `running` means that the persisted workflow is unfinished, not that an Agent process is currently executing. Explicit recorded `blocked`, `paused`, and `failed` states are displayed; a stored `reason` or `blockedReason` is shown when present. The current generated guard normally reports failures to stderr rather than persisting them, so those transient failures cannot be reconstructed by this view.
- Missing artifacts are shown as not generated, not automatically treated as blocked or failed. File existence and recorded evidence are not a fresh guard execution or semantic acceptance result.
- Native-backed and Classic-overlay generated workflows remain in their respective Native/Classic views. Arbitrary custom state locations outside `.comet/runs/*/state.json` are not discovered.

## Artifact and safety boundaries

Only project-relative output paths declared by enabled nodes are inspected. `*` patterns match one path segment, following the generated guard's matching convention. Non-project path bases are explicitly marked unavailable in this standalone view. Symlinks, junctions, traversal, special files, unreadable files, and oversized state are rejected without affecting other runs.

Text previews support Markdown, text, JSON, YAML and log files, up to 64 KiB per file and 256 KiB per detail response. A pattern previews its first matching file and reports when multiple files match. Discovery is bounded to 100 artifact references and 100 matches per pattern. Unsupported or oversized previews retain their artifact status without loading their content. Content is rendered as text, not executable HTML.

The Dashboard never initializes a run, reconciles Bundle hashes, executes a guard, advances a node, writes evidence, or mutates workflow files. There is no new database or migration.
