# 项目规则载体适配器与修复循环

## 目标

让项目规则在已有 Maven、Gradle、linter、测试、构建插件或 CI 中真正落地，同时保留对未知项目的安全回退；验证失败时把修复动作交给宿主 Agent，而不是让 Comet 猜测如何改代码。

## 设计

### 规则载体适配器

- 项目规则服务先发现仓库实际可用的验证入口。
- 可选适配器根据入口类型和规则提案生成普通仓库改动，例如原生配置、测试或 Agent 指令。
- 适配器必须返回可读的改动摘要和目标路径，并由现有 Git 流程负责提交、Review 和合并。
- 没有适配器时，服务保留当前 `.comet/rules/<entrypoint>.md` 提案路径；提案可被 selector 读取，但不伪造原生配置改动。
- 适配器失败不阻断基础 workflow，返回带插件/适配器标识的诊断。

### 验证与修复

- 服务运行项目自己的验证命令；命令成功即通过，即使输出包含 warning。
- 命令失败时返回结构化诊断和可读的修复上下文。
- 宿主或 Skill 可以注入 `repairVerification` 回调，由 Agent 修改项目后请求再次验证。
- `maxAttempts` 只限制“修复回调 -> 验证”的循环次数；没有修复回调时不重复伪装成自动修复。
- 修复和验证失败都保持插件隔离，不让基础 Comet workflow 失败。

## 非目标

- 不内置 Maven、Gradle、ESLint、Semgrep 等工具的完整 DSL 生成器。
- 不自动安装依赖，不把自然语言规则直接猜译成未知配置。
- 不在项目规则服务内实现通用代码修改 Agent。

## 验收重点

- 有适配器时，采纳候选会产生对应原生配置/测试改动。
- 无适配器时，仍生成可读提案且规则 selector 可以读取。
- 验证失败且提供修复回调时，Agent 修复后自动重新验证。
- 验证失败但没有修复回调时，只返回诊断，不伪造通过或无意义重复命令。
