# comet-any 流程增强判断

**多轮创作和修订属于正常现象；本次暴露的验收与评估缺口值得针对性增强。** 不需要把 comet-any 改成只能一次生成，也不需要重写已有 Creator 状态机。应让正常修订更早发生、通过正式流程留下证据，并减少测试阶段的外部补救。

本轮仅诊断，复核当前产品 Skill、Creator、组合器、阶段产物验证、宿主续行投影和本次实验记录。没有修改生产代码，也没有重新跑模型 Eval。

## 哪些属于正常流程

- 宿主 Agent 创作入口、业务 Rule、执行端口和验证器，是产品 Skill 明确规定的职责。
- 方案经讨论和检查修订后重新确认、编译、验收，也是已有流程。当前 Creator 已有 confirm-plan 的 revise、review-verification 的 retry / revise / rejected，以及模型评估和安装失败的恢复分支。
- 组合增加自身的核对记录可以合理，但须解释为何需要，不能说它是原 Skill 的必需产物。原 Skill 没有文件输出时，现有规则已经要求 noArtifactsReason。
- 在确认授权范围内多轮修订并不使产品能力证明失效。真正需要区分的是经过修订的交付、一次生成的成功率，以及运行时是否依赖包外额外指令。

## 本次暴露的缺口

### 1. 完整宿主入口与流程试跑：优先级高

现有 Creator.verify 检查实际加载、固定依赖、流程绑定和隔离产物样例，并明确记录不能替代真实宿主与完整业务验收。artifact-verification-entry 将每个待测产物步骤抽成单步骤 workflow，以样例输出领取并回报结果；没有在这一步按原图跑完整审批、子流程和宿主脚本。

因此，本次的错误 Store API、claim 字段、子流程激活和批准后完成衔接，需要额外的宿主 helper 检查才被修复。不是已有产物验收无效，而是它覆盖的对象与这些问题不同。

建议在编译后的必需本地检查中，增加受控的完整流程试跑：实际调用生成入口或辅助脚本，覆盖 start、父子推进、领取、回报、审批、完成及已声明的恢复分支。无文件阶段也必须覆盖；模拟 Skill 结果与真实模型行为的证据仍分别记录。

复用现有 run-view 的 continuation、nextRequest、claimRequest、outcomeRequest 和子流程指令。不要让每个组合重复手写同一套 SDK 字段解析。若仍提供自定义辅助脚本，就实际测试该脚本。

收益是将调用和衔接错误前移，减少昂贵的模型运行排障。成本中等，主要涉及 workflow-generation 的验证编排与 workflow-application 的宿主契约复用；不应引入第二套推进状态或放宽隔离验证器的权限。

### 2. 原 Skill 职责与组合契约核对：优先级高

当前适配器已经核对固定摘要、审查状态、能力与副作用的原文引用。它能确认引用存在，但不能仅凭引用存在确认生成的产物、审批与结束条件解释正确。本次误加 brief 是宿主创作错误，也是一个适合提前拦截的反例。

建议确认方案前逐项列出输入、产物、交互、完成条件、失败恢复的依据；原 Skill 要求与组合自己新增的要求分开说明。没有明确文件要求时不默认套用 Native 文档。对这份映射做独立语义核对，发现冲突回到现有 revise 路径。

收益是减少语义误配，成本中等。不能用机械文件名匹配代替理解，也不应禁止合理的新增包装产物；新增要求应有用户目标和方案确认依据。

### 3. 质量步骤的证据验收：优先级中

本次真实双轴评审发生并推动了修复，但生成的 implement 验证器只检查 reviewSummary 非空。这不能对未来运行保证两轴评审实际完成。

建议按应用需求，为必须执行的评审或检查提供明确证据，绑定当前候选内容、执行身份、结果及必要的修复状态，并提供“只有摘要、缺少一轴、候选变化”等业务反例。先改善生成方案和验证器的要求；不能把所有业务 Skill 一律改为代码评审流程。

收益是让质量要求减少对事后轨迹审计的依赖。成本中等，证据信任与当前候选绑定需要复用已有 Runtime 契约，不能仅用更多自报 JSON 字段假装已经强制执行。

### 4. Eval 控制器与干预记录：优先级高，职责与 Creator 分开

Runtime 挂载缺失、Windows 容器设备标识变化、审批问题识别及终止条件，是本次评估集成的问题。不能只靠修改 comet-any 正文解决，也不能据此取消真实工作区的身份隔离。

建议统一 subject、恢复与 verifier 的 Runtime 挂载和所有权检查；超时保留完整状态，恢复默认只提供位置、当前 Run 与真实上下文。增加流程或质量提醒时记录为额外引导。包修订、新建候选、控制器修复和预算变化分别保留，报告不能把辅助运行包装成未经干预的一次结果。

Creator 已有可选 Eval、失败审阅、重试、修订和显式跳过，本次走外部单用例实验不代表应再造另一套 Eval 状态机。应复用 domains/eval 的公开快照、实验与报告绑定，保留跳过或不完整状态。

收益是使评估更可复用、结论更可信；成本中等，涉及 eval 容器编排与恢复证据。应保留单用例诊断和完整应用模型验收的区别。

## 建议顺序与边界

先补完整宿主入口/流程试跑与契约语义核对，同时修复 Eval 集成和记录干预；再增强应用特有的质量证据验收。继续保留现有 revise、批准、固定包和 SDK Run 权威，不需要追加一套平行流程。

增强后的判断标准是：调用和图衔接错误在真实模型运行前被发现；原 Skill 职责不会无依据改变；质量与批准对应当前候选；中断恢复有可核对记录；成功结果明确披露修订和外部辅助。目标是可靠交付，不是禁止正常迭代。

当前证据不支持全面重构，也未验证这些建议的实现成本或跨平台效果。生产实现仍需单独确定范围并执行相应契约测试、构建及宿主验证。
