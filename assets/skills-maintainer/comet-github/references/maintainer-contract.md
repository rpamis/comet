# Comet 维护者契约

以下规则适用于 Comet 的 GitHub、交付、发布、文档和 Runtime 诊断工作。

## 证据优先

- 在复用历史结论前，刷新当前分支、worktree、GitHub 目标、head/base 和相关 CI。
- Review bot 摘要、复制来的评论、过期 Codecov 输出、Changelog 声明和静态配置都只能作为线索，不能直接作为证据。
- 需要时，将报告行为与当前源码、测试、已安装/生成的 Runtime 以及真实执行路径对照。

## 默认只读

分析可以读取本地文件、Git 状态、GitHub 元数据、CI 日志和 Runtime 行为，但除非用户明确要求，不得评论、改标签、关闭 Issue、创建 Issue、提交、推送、创建 PR、删除分支或移除 worktree。

执行已授权动作前，先明确准确目标和将要产生的变更。

## 范围与工作区安全

- 保留无关的脏文件、关联 worktree、子模块、附件和用户改动。
- 只暂存明确的目标路径；混合工作区中不得使用宽泛的 `git add .`。
- 将诊断、实施和交付分开处理。
- 活跃 Comet change 中途增加文件或行为时，先通过所属 Comet workflow 更新正式范围并重新确认。

## 验证表述

分别报告：本地聚焦检查、本地全量检查、生成资产/打包检查、准确最终 head 的远端 CI，以及未运行、超时或仍未验证的检查。

在准确最终 head 的新 CI 检查成功前，不得称 PR “CI 全绿”。

## 用户可见的文案

Changelog 和发布文档描述用户能感知到的行为及其价值。除非用户明确要求技术发布说明，不写分支内部迭代、review follow-up、测试重构、bundle/cache 细节或 Git 对象 ID。

中文术语应专业、自然。不要把 workflow 的 “gate” 翻译为“门”，应根据语境使用“检查”“协议”或“阶段”。

## Comet 边界

- Comet 代码变更使用现有 Native 或 Classic workflow，不手工编辑 Runtime 管理的状态。
- 源码影响生成 Runtime 资产时，通过仓库命令重新构建并运行对应的生成物检查。
- 跨平台结论使用规范平台注册表，不用短的硬编码平台列表替代。
- 这些仓库内维护 Skill 通过 Git 交付，除非明确要求，不发布到 npm。
