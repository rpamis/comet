# Continue after edits

When files change during Build, Verify, or before Archive, the current Agent judges their effect. File changes do not automatically revoke approval, invalidate checks, or reset the phase. Do not submit file fingerprints, hashes, or per-file retention proofs.

1. Read the actual changes, current requirements, related callers, and previous check results. Use Git differences and current files as appropriate. Retrieve missing source material instead of judging from file size, extension, or a digest. Handle consecutive saves together without adding a review or confirmation for each save.
2. Continue according to the actual effect. Keep the original Run, phase, approvals, report, and checks when explanations, comments, or formatting leave behavior and acceptance unchanged. Revise the implementation through the current workflow when behavior changes. Request only the affected decisions when changes to goals, acceptance, approach, or authorization exceed existing approval.
3. The Agent runs necessary checks with platform tools and reads actual results. Keep the original execution source when a prior result remains applicable; run only the checks that need updating. Do not require observe, prepare-applied, record, retainedChecks, or a content-proof chain. Submit actual check reports to CLI with the current Action template. Ordinary edits do not add an independent review session.
4. Preserve real failures, interruptions, timeouts, unknown outcomes, and unexecuted work. Update conclusions using actual results after repair. Do not hide a newer failure behind an older success or describe a historical check as a new execution. Do not automatically replay completed one-time operations.
5. After acceptance but before Archive, the Agent confirms that the current changes remain consistent with the original requirements and acceptance conclusion, then continues the original Archive. Repair or supplement checks according to the actual effect. Resume interrupted Archive work through the same transaction; Runtime records completed writes and directory moves so their effects are not repeated.

User confirmation, explicitly requested independent acceptance, phase permissions, and path and workspace isolation still apply. Runtime maintains steps, executors, commands, exit status, log paths, user decisions, and Archive progress. Shared SDK Action request identifiers, package digests, and Git commit IDs remain available.

Completion: the Agent has assessed the changes, necessary checks have real results, the current conclusion meets the user's requirements, and the original workflow can continue. Do not reopen Build or Verify solely for bookkeeping when no new information requires it.

## Agent Judgment and CLI Execution

The current Agent judges Native and Classic requirements, documents, and development progress. CLI executes explicitly selected operations and preserves the original Run, user decisions, actual results, and recovery progress.

- The Agent compares the user request and project requirements to judge document completeness, clarity, and the need for target Specs. Templates are writing aids. Fixed headings, phrases, language ratios, and design frontmatter do not prove completion. Fill machine-consumed acceptance, task IDs, paths, and result fields using the current response. Resolve outstanding user decisions before dependent work.
- Choose the existing workflow or preset that fits the task. Classic full retains design, implementation plans, and user approval; satisfy actual external tool requirements. Use the original Run and formal artifacts for handoff without copying the same content at each phase. Generate separate material when people or external tools need it.
- The Agent explicitly selects check commands, working directories, and scope, executes them with platform tools, reads actual exit status, and submits reports to CLI. Status and Guard read results without guessing and starting Build. Inspect the original execution when a command is running or its outcome is unknown.
- After failure, use actual changes and results to decide whether to repair, change approach, or request help. An unresolved acceptance ID set that has not shrunk does not establish lack of progress. Use existing explanations; add no progress score or proof. User budgets and actual execution limits still apply.
- Prefer the current workflow business entry and returned templates. CLI assembles SDK Action, claim, and concurrency parameters and continues already authorized internal steps. User decisions, different executors, real failures, and external waits return the actual next step. Recovery retains the original Run and execution.
- The Agent judges whether parallel work is useful and how to divide tasks. Runtime maintains actual dependencies, workspaces, task state, and Git operations. Parent acceptance covers all confirmed criteria, reuses applicable child results, and fills gaps. Retain the selected coordination mode and independent review requirements.

Completion: required user decisions are explicitly recorded, actual task results can be inspected, acceptance covers confirmed requirements, and Archive and delivery follow original authorization and actual progress. Report missing checks, failures, timeouts, and unknown results honestly; do not describe them as passed.
