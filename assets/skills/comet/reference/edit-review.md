# Reviewing edits during Verify

Read when a Verify write is denied with an edit-review instruction or continuation points to edit-review. Native and Classic retain their own workspace, candidate, and approval authority.

1. Use the current continuation. When the task is missing, run `comet edit-review show <native|classic> <change> --json`. A changed hash, extension, or syntax structure alone does not require phase rollback. Runtime handles edits it can prove locally; otherwise preserve Verify pending review.
2. In SDK, an independent session follows the returned claim command, using a stable platform task ID or execution reference for --session. The reference correlates this execution and does not authenticate platform identity. Start a new separate read-only session if the original Verifier has ended, without claiming or occupying the formal Verify Action. If the full edit is missing, save the original tool request in temporary JSON and supply claim --file. Select and review multiple proposals by their returned proposal hashes.
3. Read the current file, complete original request, exact diff, consumers, and current acceptance requirements. Fill recordTemplate with non-behavioral, implementation-changed, or requirements-changed plus concrete reasons, then execute the returned record command. Leave uncertain edits pending. Compat uses explicit user confirmation and record --confirmed rather than SDK claims; do not self-approve.
4. After non-behavioral approval, retry the identical original edit. The receipt does not perform the write; unapplied edits cannot pass verification. Rerun invalid checks and continue the Verifier and acceptance work. Implementation or requirement changes follow their original Build or requirement-confirmation path. Review approval alone is not an acceptance pass.
5. Recover the same session and proposal after interruption. Keep temporary input until applied or discard, then remove it without including it in commits or reports. Supply the real request again if its file is missing or changed; never fabricate the original. To abandon an unapplied proposal, submit decision discard using recordTemplate. Discard cannot conceal an already changed file.

Existing integrations may still submit using the current independent Verifier's SDK claim. The separate review claim supports missing, ended, or unavailable original claims. Both bind to the current candidate and reject cross-candidate replay.
