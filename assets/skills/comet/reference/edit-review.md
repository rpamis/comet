# Continuing the original flow after edits

Read when files actually change during Build, Verify, or before Archive, or when a continuation asks for a content judgement. In both Native and Classic, the current Agent judges semantics and impact; the Runtime stores the original change, the judgement, and the real check results.

1. Handle consecutive edits together at the next advance. Reuse the current change, Run, phase, Action, and existing context; run `comet edit-review observe <native|classic> <change> --session <current-session> --json` when a change list is needed. When the actual bytes are unchanged, continue the original action; for staging, unstaging, or empty commits, recheck only the checks that explicitly depend on Git, and do not re-accept identical content.
2. The current Agent reads the changed files, the original input list, available previous content or Git diffs, plus the current requirements and call sites, and judges the actual impact. Detection does not depend on file extensions, code parsers, or compilers; the Agent selects the actual verification commands based on the project and the risk at hand. When the original text needed for the judgement is missing, obtain the evidence first; never treat a summary as the original text.
3. Choose a judgement from the actual impact and record the reasons using the response's `recordTemplate`:
   - `non-behavioral`: product behavior and acceptance meaning stay unchanged; only explanation, formatting, or similar content changes. An original check consuming those bytes may become stale, which only means check evidence needs updating. In that case, keep the original report, approvals, and candidate as the existing records and supplement the necessary checks on the same Run; this alone does not require the product implementation change repair flow. Archive stays blocked until the supplemental checks have actually passed.
   - `implementation-changed`: actual product outputs, rules, or side effects change, requiring a revised implementation candidate. When explanatory text participates in actual product behavior, judge that actual impact too.
   - `requirements-changed`: the goal, acceptance criteria, approach, or authorization scope changes materially; request only the related decision when existing decisions do not cover it.

   Explicitly retain the applicable original checks through `retainedCheckActionIds` or `retainedChecks`, covering all actual changes. Fill retention for each formal material too; retaining B/one-time checks only in an ordinary-file judgment is insufficient. Selecting A does not prove that other checks still apply. Keep the original Actions, execution environments, logs and result sources, and rerun only affected or missing checks.

   If a recorded judgment omitted retention, the original Agent may `record` the same proposal again to add retained checks to the existing set, explaining the additional evidence. Runtime preserves the complete original receipt and its supplemental binding. The bytes, decision and execution identity must remain the same; do not reclassify, remove prior retention or cover new edits through a supplement. Keep the claimed Action or returned same-session claim; ordinary edits add no separate review or user confirmation. If an unselected check lacks valid reuse evidence, complete the judgment first; supplemental checks must not automatically expand the execution scope.
4. When a formal brief, Spec, Design Doc, or plan changes, run `comet edit-review prepare-applied <native|classic> <change> --session <current-session> --json`, obtain the approved original text, then judge. When the contract is unchanged, keep the original approval, phase, and acceptance items; when the goal, acceptance criteria, approach, or authorization changes materially and no existing decision covers it, only explain the affected decisions and request confirmation. Inspect each formal source. If automatic preparation returns an already handled proposal while targets not yet covered remain, use `prepare-applied --file <complete-request-JSON>` to identify the corresponding applied edit, then record the judgement. A revision command returned by the Runtime only describes an available path and does not grant user authorization. Continue on the same Run when revision is explicitly authorized; otherwise request the related decision first and preserve the original phase, accepted results, and pending work, without executing revision commands that change phase or reset results. Machine state, reports, locks, check receipts, and archive records remain managed by the Runtime.
5. In Verify, keep the original Verifier and the valid checks; a real implementation change follows the current Runtime's repair action, retaining the original requirement approval and the unaffected checks; successor candidates go through acceptance again. When results are already accepted but the archive has not run, ordinary documentation changes keep the report and the accepted results; when checks must be refreshed, fill in the `refreshInputTemplate` returned by observe, run `comet edit-review refresh-checks <native|classic> <change> --file <input-file> --json`, then perform the original Run's check action required by the response. Once every check applies, continue the original archive; a changed delivery goal or authorization still requires the corresponding decision.
6. When edits happen again after a judgement, handle only the new changes. A new failure, interruption, timeout, unknown result, or unexecuted step keeps its true state and must not be overwritten by an earlier success; verify the original execution first for non-repeatable operations. Retrying the same refresh request reuses the original Action, an interrupted archive resumes the original transaction, and completed side effects are not repeated.

Done when every current change has an applicable judgement, the necessary checks have real results, the originally valid approvals and evidence are preserved, and the current action can continue. When structure, machine state, or artifacts are genuinely damaged, use the diagnosis and recovery steps designated by the Runtime; when old records lack the original text or complete input evidence, report and handle only the specific gaps instead of fabricating historical evidence.

Explicit strict configurations and pre-existing unapplied edit requests keep the protected flow returned by the Runtime: use the returned `claim` when a claim is required; use the returned `discard` to withdraw an unapplied request; submit `--confirmed` only after receiving the corresponding decision when user confirmation is actually required. Ordinary edit judgements must not bypass these operations or add confirmation for ordinary edits.
