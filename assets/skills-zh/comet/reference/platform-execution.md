# 普通命令与检查

Build、Verify、子任务和固定应用中的开发、测试及普通命令直接使用 Agent 平台工具。Agent 根据项目约定、改动和验收要求选择检查，读取实际结果；平台负责超时、取消和进程清理。Comet 保存业务状态、任务记录、用户批准及验收报告，不启动另一套普通命令执行器。

## 执行与结果

- 同一工作区和 Run 由一个主 Agent 顺序写入 Comet 状态；前一条写入命令完成后再提交下一条。并行子任务只修改各自隔离的 worktree，并把结果返回主 Agent。主 Agent 用原任务的 Action、真实子会话、领取身份及结果模板逐个提交，任务勾选也由主 Agent 完成；不得改用主会话冒充子执行者或重新领取已完成的任务。普通流程不创建锁或执行锁恢复。
- 先运行覆盖改动的必要检查。完整验收须覆盖当前候选的全部验收项，不等于仓库全量测试；用户选择的执行方式、TDD、审查和独立会话要求继续有效。
- 已有检查是否仍适用于当前候选，由 Agent 根据实现、输入与环境变化判断。保留命令、工作目录、真实结果和日志引用；只补缺失或失效的检查，不为向 Comet 提交报告再跑一遍。
- 已派发的任务沿用同一平台任务和真实会话。等待工具超时不代表任务已失败或停止；先用平台工具核对原任务。用户要求取消时，先按平台方式取消并核对清理结果，再记录业务取消；不伪造检查通过或进程已停止。
- 大日志保存在平台日志或文件中，工具响应只保留结论、相关失败片段及可读取的位置。需要细节时再读取，不反复返回全部历史、完整日志或已交付上下文。
- Eval、下载等由 Comet CLI 自己启动的能力按其专门命令管理清理。只有用户明确要求启动 Eval 时才能执行。

## 向 Comet 提交

Native 沿用当前 Action 模板的 `checks` 和验收条目提交实际结果。Classic SDK 将报告保存为 JSON：

```json
{ "checks": [{ "name": "命令、目录与检查名称", "result": "passed", "note": "实际结果与日志引用" }] }
```

失败项填写 `failed`，未执行项填写 `not-run` 并说明原因。没有适用检查时使用空 `checks` 并填写 `checksReason`。不能把未执行、超时或结果未知写成通过。Build 使用 `comet state complete-build <change> --checks <checks-json-file>`；Verify 使用 `comet guard <change> verify --report <report-ref> --apply --checks <checks-json-file>`。Runtime 继续核对任务、批准、候选和验收要求，失败后沿返回的业务续行修复。

Classic Compat 在平台命令结束后记录实际结果：

```bash
comet state record-check <change> <build|verify> --command "<实际命令>" --exit-code <实际退出码> --cwd <实际目录>
```

该命令只记录结果，不执行命令。随后按当前阶段运行 Guard；报告不能代替任务完成、用户批准或验收。旧 `comet check run/rerun` 只返回平台执行指引，不再运行或恢复检查。

## 旧版本升级

在原 change 和原 Run 继续，使用新版入口返回的模板与续行。自动转换保留原批准、任务、候选和已接受的业务结果，不重新要求用户批准相同决定，不重播归档或交付。旧检查调度不再执行；尚未确定结果的旧平台任务，先由 Agent 在原平台核对，再补实际检查报告。旧记录中的 PID、停止回执和内容快照不作为新流程的执行或验收依据。
