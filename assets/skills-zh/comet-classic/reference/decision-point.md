# 用户决策点协议

规范路径：`comet-classic/reference/decision-point.md`

本协议由所有包含用户决策点的 comet 子 skill 共享。凡标注为“阻塞点”或“用户决策点”的步骤，都必须按本协议处理。

## 先判断是否真的需要用户决策

区分用户决策点、自动处理与停止条件：

- **用户决策点**：存在两个或更多均合法、会改变范围、行为、风险承担或不可逆结果的选项，必须由用户选择；阶段明确要求的产物/设计批准也属于用户决策点，展示批准、调整或暂缓等实际选择，不能因技术上只有一个推荐方案而自动通过
- **自动处理**：只有一个安全且在当前请求范围内的下一步，例如修复明确失败、补齐可验证状态、重试幂等检查或按已持久化配置继续；直接执行并报告，不得制造确认
- **停止条件**：依赖缺失、状态损坏、路径越界或外部命令不可用，导致当前没有合法下一步；报告阻塞原因和恢复条件，不得伪造选项
- **手动衔接**：`NEXT: manual` 只是交还控制权，不是新的用户决策点；输出 `HINT` 后结束当前调用，不再询问“是否继续”

只有第一类形成决策阻塞点。Open/Design 为消除范围、方案或验收缺口而提问时，同样按下方格式呈现问题；纯事实、路径或用户未提供的内容无法形成真实选项时，明确说明缺少什么并请求补充，不编造替代答案。相邻且可同时回答的选择必须合并；已经持久化且仍有效的选择不得重复询问。不得因预判后续工具或操作可能失败而预检、推断或筛除选项。展示本工作流支持的全部选择；用户选择后执行对应动作，若失败则停止并报告原错误。若某配置字段只剩一个工作流合法值，说明原因后直接采用，不为它单独创建停顿点；此规则不替代阶段明确要求的用户确认。

## 核心规则

暂停或停止只约束依赖该决定或阻塞的动作；同一已授权范围内其他独立且有用的调查、证据整理和已允许工作可继续。不得据此跨越阶段 Guard、提前实施待确认范围或替用户作出待定选择。

- 决策点是阻塞点。到达决策点时必须暂停，等待用户明确选择后才能继续
- 存在 `AskUserQuestion` 时，使用它展示单选/多选选项；否则在对话中提出明确选项并等待用户回复
- 若无法使用 `AskUserQuestion`，则判定本会话结构化提问不可用；本会话后续决策点不得反复重试它，直接使用文本选项降级模式
- 不得用推荐规则、默认值、历史偏好或“用户应该会同意”的推断代替当前确认
- 用户明确选择前，不得写入对应状态字段、执行对应分支操作或自动继续下一阶段

## `AskUserQuestion` 优先策略

使用结构化提问时：

- 单选决策点用 `AskUserQuestion` 的单选问题；多选决策点用多选问题
- 每个问题说明正在决定什么，并为选项携带简短标签和影响说明；有依据时标出推荐项并说明推荐理由，不能自动选择
- 若工具调用成功，等待用户通过该问题作答；不得同时再输出一套文本选项
- 若工具不存在或工具调用失败，记录“本会话结构化提问不可用”，然后进入文本选项降级模式

## 最低呈现要求

- **问题**：明确本题正在决定什么，给出足以判断的当前事实、约束或待确认产物引用；不只抛出工具名或配置字段
- **推荐与理由**：有依据时给出推荐选项，说明它为什么适合当前需求、风险与已有配置；依据不足时明确说明暂不推荐，不以历史偏好代替确认
- **选项与影响**：给出清晰可选项，逐项说明选择后执行什么、改变什么范围/行为、承担什么代价或风险；需要用户单选时，选项必须互斥且可执行
- 文本降级模式必须明确写出“单选”或“多选”、编号选项、每项影响，并要求用户回复编号；随后停止流程，等待用户回复
- 联合提问时，每个问题分别满足问题、推荐理由与各选项影响要求；不能只为整组问题写一条笼统推荐
- 如有推荐，只能作为说明，不能替代用户确认；工具返回空答案、用户未回复或只收到无明确选择的答复时，待定决定保持未确认
- 用户选择后，再执行对应命令或状态更新

### 批量文本提问格式

一次用文本提出多个问题时，保留 `Q1`、`Q2` 编号，每题使用独立的加粗标题、正文、选项和推荐区；用 💬 标记问题、💡 标记推荐回答，配合题间分隔线区分内容。以下问题块按题数重复，在同一条消息中完整发出：

```markdown
💬 **Q1｜<问题标题>（单选）**

<说明背景及需要决定的用户可见差异；复杂问题可以分段。>

| 选项 | 方案         | 实际影响                   |
| ---- | ------------ | -------------------------- |
| A    | <方案短名称> | <选择后改变什么及相关代价> |
| B    | <方案短名称> | <选择后改变什么及相关代价> |

💡 **推荐回答：A（<方案短名称>）**

推荐理由：<为什么适合当前需求与约束。>

---
```

题号保持稳定，追问沿用原题号；多选题标为“多选”。开放题标为“开放回答”，省略选项表，有可靠建议时给出“推荐回答”和理由；事实不足时明确“需要你补充”，只给回答所需的信息或格式，不编造推荐内容。已有固定选项表保留原标识和完整影响，放入对应问题块，不为突出推荐而重新编号或删减选项。

全部问题之后统一说明答复方式，例如 `Q1：A；Q2：A+C；Q3：补充内容`，也允许按题号给出自己的答案；示例不代表默认选择。结构化工具可用时仍优先使用工具，在其标题、说明和选项字段中承载相同信息，不要求工具呈现 Markdown 表格，调用成功后不再重复文本问题块。

## 阶段确认的归属

只有当前阶段出现以下实际决策时才加载对应阶段细节；已持久化且仍有效的授权或配置不重新确认。

- 入口/Open：目标 change 不明、PRD 拆分或工作区隔离有真实选择时成组澄清；Open 最终审视一次确认名称、范围与产物，清晰请求不先单独批准摘要或命名。
- Design：brainstorming 形成可审视方案后确认正式设计；已有有效确认只补未完成产物和状态。
- Build：写计划前仅在执行/TDD/review 配置缺失或用户要求更改时联合确认；计划完成默认继续。plan-ready 是用户主动要求的暂停，恢复收到继续指令后沿用有效计划与配置，不重新发起配置决策。
- Verify：范围内明确可修复失败自动闭环；接受 WARNING/SUGGESTION 偏差、Spec 漂移取舍或达到 Runtime 自动修复上限时才询问。CRITICAL/IMPORTANT 不可豁免。
- Archive：一次确认归档与 local/push/pr 交付方式；有效 delivery 授权存在且目标不变时只续做未完成动作，真实结果不确定时先只读核对。
- 范围改变：新增 capability、公共行为/接口、验收或风险承担改变，以及预设自身定义的升级信号，由对应阶段展示继续/调整/拆分等合法选择。任务拆细或数量增长本身不等于范围扩张。
