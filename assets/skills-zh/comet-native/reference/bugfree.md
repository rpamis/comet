# bugfree 验收

SDK 返回的 `verifyMode` 为 `bugfree` 时，按本节执行。模式在创建 Run 时确定，之后修改项目配置只影响新 Run。bugfree 只用于最终 Verify；Supervisor Child 验收和集成检查仍按原流程执行。

## 开始验收

把当前 `verificationContext` 和领取模板交给一名未参与实现的 Verifier。由它独立审查，只读代码，不修改实现，也不再派其他审查 Agent。

首轮另开会话。`session.strategy` 为 `resume` 时，继续使用登记的原审查会话；原会话无法恢复，再另开独立会话。原任务还在运行或结果不明时，先查清它的状态。

命令的完整输出保存在本地，只把当前 `pendingActions[].verificationContext`、任务领取模板和结果提交模板交给 Verifier；领取后读取 `action.input`。使用 Runtime 提供的材料，保留已确认需求、全部验收项、代码差异、检查结果和未解决问题，无需附上 Builder 自评、完整开发对话、历史 Run 或另一份完整结果模板。已有上下文仍适用于当前 Action 时直接复用，只补充缺失或失效的内容。

## 审查代码

先读需求和最终代码，再按需要查看调用关系、数据结构和配置。能从代码判断的，直接给出结论；需要运行才能确认的，再用当前 `request-checks` 模板请求必要检查。用户、项目规则或验收要求明确规定的检查，仍须有适用于当前实现的通过记录。

已有检查记录仍有效时，直接复用。修复后重点看前后两版的差异，判断修改影响了哪些行为，并确认其他验收项是否仍然成立；最终提交的结果仍须覆盖全部验收项。

上一轮由 Agent 临时增加的诊断检查，不必每轮重跑。阅读修复后的代码就能确认原问题已解决时，说明修复依据，并保留原检查失败、本轮是否重跑的事实。当前候选已登记的检查仍须通过，不能把失败、输入不完整或结果未知写成通过。

发现代码不符合需求时，判为 `failed`，写清触发条件和问题位置；缺少必要资料或环境、无法判断时，判为 `blocked`，说明缺什么。全部验收项通过且没有未解决问题时，结束审查，无需逐项补测试、堆证明材料或再审一遍。

## 提交验收结果

Verifier 用自己的会话身份领取任务并提交结果，按当前紧凑模板填写：`passedAcceptanceIds` 列出通过项的 ID，`acceptance` 只写失败项、阻塞项及原因。两部分合起来须覆盖全部当前验收项。只要有失败项，总结论就是 `fail`；没有失败项但有阻塞项时，为 `blocked`。

补查完成后，让原 Verifier 读取结果，领取后继 Action 并继续审查。领取任务和提交结果都使用当前 Action 的模板，不沿用旧候选的 claim。等待工具超时后，继续跟踪原任务；执行失败或结果不明时，按原恢复流程处理。

最终报告由 Runtime 生成。向用户说明审查结论，以及哪些检查实际执行了、哪些复用了已有记录；没有执行命令时，明确写“本轮未执行命令检查”。用户明确接受结果后，才能进入 Archive。报告生成失败时只恢复报告步骤，不重新派发审查。
