# Native 澄清参考

进入 Shape 后必须读取本文件。完成问题判定、静默假设检查和共享理解确认前，不得修改项目实现或推进到 Build。

## 是否需要提问

先区分三类信息：

- **可调查事实**：仓库现状、工具能力、依赖默认值和运行环境。由 Agent 调查；可以将彼此独立的事实调查委派给 subagent。
- **用户决定**：不同选择会实质改变输出、默认行为、失败结果、范围或不可逆影响。由用户确认。
- **实现选择**：不改变用户可见结果的算法、结构和工作方式。由 Agent 决定。

只有歧义会实质改变用户可见结果，并且无法从用户要求、正式规格或适用契约中可靠确定时，才询问用户。不要为了覆盖清单制造问题，也不要把实现选择交给用户。

把模糊行为改写为可比较的“输入 → 输出”或“触发 → 结果”。每个问题应包含：

- 问题：需要决定的用户可见差异；
- 推荐：首选项及理由；
- 影响：各选项对结果的实际影响。

## 决策树与事实调查

在提出第一道用户问题前，先建立并持续维护一棵决策树。树中只包含会实质改变用户可见结果的用户决定；可调查事实和实现选择分别作为节点的前置事实和 Agent 自有工作，不伪装成用户决定。

每个决定节点至少明确待决定的行为、父节点或前置决定、所需事实，以及它当前是等待前置条件、可提问还是已解决。父节点和所需事实都已确定的未决节点，就是当前可提问节点。多个当前可提问节点之间不得存在答案依赖。

决策树是 Agent 的工作模型，不新增 Runtime 产物或 schema；只有实际未解决的用户问题继续使用现有 `[blocking]` 行写入 brief。每次用户回答或事实调查产生结论后，立即更新受影响的节点，增加、移除或改写对应后代，并重新计算当前可提问节点。

事实调查不得阻塞无关分支。某项事实尚未确定时，只暂停依赖该事实的节点及其后代，继续处理其他当前可提问节点。不得因为当前可提问节点暂时为空，就忽略仍在等待事实或尚未检查的实质分支。

## Sequential

1. 根据决策树调查所需事实，并按上述规则隔离仍在等待事实的分支。
2. 从当前可提问节点中选择一个最上游的问题；存在多个候选时，优先选择能解锁更多后代或对用户可见结果影响更大的节点。
3. 在 brief 中保存一项 `- [blocking] <问题>`。
4. 一次只提出一个当前可提问节点并等待回答；同一轮不得再提出第二个用户决定。
5. 用户回答后立即更新 Decisions、brief 和完整目标规格。
6. 更新决策树并重新计算当前可提问节点，再开始下一轮。

模糊、部分或未回答的内容继续保持 `[blocking]`。一个答案只决定它明确覆盖的行为。

## Batch

每轮从决策树中取得完整的当前可提问节点集合：这些节点的前置决定和环境事实已经确定，且答案彼此不依赖。

1. 在 brief 中保存 `- [blocking] Q1: <问题>`、`- [blocking] Q2: <问题>`。
2. 一次提出本轮全部当前可提问节点，并分别给出问题、推荐和影响。
3. 用户回答后更新正式产物；未回答或不明确的问题继续保持 `[blocking]`。
4. 更新决策树中的已回答和未回答节点，再计算下一轮的完整节点集合。

不要把多个独立决定压缩成一道多选题，也不要把同一批问题拆成多轮。

## 持久化与最终确认

每次确认都立即写入现有 change 的 Decisions 和完整目标规格。不要只更新 brief，不要等到最终确认后再补规格，也不要为补充答案创建新 change。

只有所有已识别分支都已处理、没有可能改变用户可见行为的待调查事实、当前可提问节点为空，并且静默假设检查没有发现新节点时，才开始最终确认：

1. 检查是否仍有静默假设；
2. 向用户提供目标、范围、关键决定、验收标准和非目标摘要；
3. 在 brief 中保存 `- [blocking] CONFIRM: <确认内容>`；
4. 等待用户明确确认；
5. 确认后移除阻塞项并使用 `--confirmed` 推进。

用户最初提出需求不等于最终共享理解确认。用户补充或否定摘要时，更新正式产物并继续澄清。
